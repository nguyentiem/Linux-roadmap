1. Đặt vấn đề: Vì sao cần pipeline xử lý văn bản?

Một thiết bị Embedded Linux, một server web hoặc một CAN gateway có thể tạo hàng triệu dòng log. Đọc bằng mắt không thể trả lời nhanh: có bao nhiêu lỗi 5xx, endpoint nào chậm nhất, bao nhiêu bản ghi bị hỏng, và kết quả có đáng tin hay không?

Tư duy senior: Trước khi chọn lệnh, xác định schema đầu vào, phép biến đổi, định dạng đầu ra, cách xử lý lỗi, độ lớn dữ liệu. Một pipeline chạy thành công không đồng nghĩa kết quả đúng.

Ví dụ đời sống: nhà máy có băng chuyền phân loại hàng. grep là người giữ món hàng đúng điều kiện, cut lấy một nhãn, sort sắp thứ tự, uniq gom các nhãn đứng cạnh nhau, awk là người thống kê, còn jq đọc đúng cấu trúc phiếu hàng JSON.

Câu hỏi ngược: Nếu một món hàng thiếu nhãn trọng lượng, có nên âm thầm coi trọng lượng bằng 0? Chính là vấn đề malformed log.

2. Nền tảng Unix: stdin, stdout, stderr và pipe

Một process thường có ba file descriptor: 0 = stdin, 1 = stdout, 2 = stderr. Dấu | nối stdout của tiến trình trái vào stdin của tiến trình phải. Kernel cung cấp cơ chế pipe, shell tổ chức việc khởi tạo process và nối descriptor.

cat access.log | grep ' 500 ' | wc -l
# Có thể viết gọn, tránh cat không cần thiết:
grep ' 500 ' access.log | wc -l

> ghi stdout ra file; 2> ghi stderr; < đọc stdin từ file; >> nối thêm. Một chương trình có thể ghi lỗi ra stderr trong khi stdout vẫn được pipeline tiêu thụ.

Streaming và blocking: grep, cut, tr, nhiều chương trình awk có thể xử lý tuần tự. sort thường phải nhìn toàn bộ tập đầu vào để bảo đảm thứ tự, nên có thể dùng RAM và file tạm. Đừng nhầm việc có pipe với việc toàn pipeline có độ trễ thấp.

producer | grep ERROR | awk '{print $1}'
producer | sort | uniq -c

Phản biện: Tại sao wc -l cuối pipeline vẫn trả 0 khi grep báo không mở được file? Vì exit status mặc định của pipeline trong Bash thường là status của lệnh cuối. Ta sẽ xử lý bằng pipefail.

4. grep: lọc dòng và hiểu exit status

grep ERROR app.log
grep -n ERROR app.log             # Số dòng
grep -i error app.log             # Không phân biệt hoa/thường
grep -v DEBUG app.log             # Dòng không khớp
grep -c ERROR app.log             # Đếm dòng khớp
grep -F 'a.b' app.log             # Tìm chuỗi cố định
grep -E 'ERROR|WARN' app.log      # Extended regex
grep -w 'ERROR' app.log           # Word match
grep -R -n 'TODO' ./src           # Tìm đệ quy
grep -- '-danger' app.log         # Pattern bắt đầu bằng dấu -

grep thường trả 0 nếu có dòng khớp, 1 nếu không có dòng khớp, 2 nếu có lỗi (một số biến thể có khác biệt). Trong script, 1 có thể là tình huống bình thường, không nên luôn coi là sự cố.

if grep -q 'ERROR' app.log; then
  echo 'Có lỗi'
else
  echo 'Không tìm thấy hoặc có lỗi; cần phân biệt nếu quan trọng'
fi

Câu hỏi: Tại sao grep '500' chưa chắc tìm đúng HTTP 500? Vì nó có thể khớp IP, URL, latency hoặc một số khác. Nếu biết status ở trường 4, hãy dùng awk '$4 == 500'.

5. Regex: ngôn ngữ mô tả mẫu

Regex là cách mô tả hình dạng chuỗi thay vì liệt kê mọi chuỗi cụ thể.

| Ký hiệu | Ý nghĩa | Ví dụ | |---|---|---| | ^ | Đầu dòng | ^ERROR | | $ | Cuối dòng | done$ | | . | Một ký tự bất kỳ (trừ newline theo cách dùng thường gặp) | a.c | | * | 0 hoặc nhiều lần | ab*c | | + | 1 hoặc nhiều lần trong ERE | ab+c | | ? | 0 hoặc 1 lần trong ERE | colou?r | | [0-9] | Một chữ số | [0-9]+ | | [^,] | Ký tự không phải dấu phẩy | [^,]+ | | (A|B) | Chọn A hoặc B trong ERE | (GET|POST) | | {3} | Đúng 3 lần trong ERE | [0-9]{3} |

printf '%s\n' 'ERROR 500' 'WARN 404' 'INFO 200' | grep -E '^(ERROR|WARN) [0-9]{3}$'

BRE/ERE/PCRE: grep cơ bản dùng BRE; grep -E dùng ERE; grep -P (nếu bản build hỗ trợ) dùng PCRE. Không giả định mọi regex engine có cùng tính năng.

Shell quoting: grep -E '^[0-9]+$' đặt pattern trong dấu nháy đơn để shell không diễn giải các ký tự đặc biệt trước khi truyền cho grep. Glob như *.log là cơ chế mở rộng tên file của shell, không phải regex.

Câu hỏi phản biện: Regex [0-9]{3} có đủ để xác minh HTTP status hợp lệ? Không: 999 vẫn khớp; cần kiểm tra cả khoảng giá trị và schema.

6. ripgrep (rg) và tìm kiếm dự án

rg thường rất hữu ích khi tìm trong cây mã nguồn; mặc định nó tôn trọng nhiều quy tắc ignore như .gitignore, khác với grep -R.

rg -n 'TODO|FIXME' src/
rg -l 'can_frame' .
rg -F 'struct can_frame' .
rg --hidden 'config' .

Đừng suy ra không có kết quả nghĩa là chuỗi không tồn tại: file bị ignore, file ẩn hoặc binary có thể không được quét theo mặc định. Khi điều tra incident, phải hiểu phạm vi tìm kiếm thực tế.

7. Thiết kế fixture và hiểu schema log

Tạo dữ liệu dùng chung:

mkdir -p "$HOME/linux-lab/text"
cd "$HOME/linux-lab/text"
cat > access.log <<'EOF'
10.0.0.1 GET / 200 12
10.0.0.2 GET /health 200 2
10.0.0.1 POST /orders 500 93
10.0.0.3 GET /missing 404 4
10.0.0.2 GET /orders 503 110
EOF

Schema: IP METHOD PATH STATUS LATENCY_MS (5 trường, phân cách bằng khoảng trắng). Đây là fixture đơn giản để học; access log thực tế có thể dùng quoted fields, timestamp, user agent và nhiều biến thể khác.

Trường Giá trị ví dụ Ý nghĩa
$1 10.0.0.1 IP
$2 POST HTTP method
$3 /orders Endpoint
$4 500 HTTP status
$5 93 Latency (ms)

Kiểm tra trước: awk '{print NR, NF, $0}' access.log để nhìn số trường từng dòng.

8. Phân tích HTTP status bằng pipeline

awk '{print $4}' access.log | sort -n | uniq -c

Kết quả:

      2 200
      1 404
      1 500
      1 503

Đếm 5xx:

awk '$4 >= 500 && $4 <= 599 {n++} END {print n+0}' access.log
# 2

Tỷ lệ lỗi:

awk '{total++; if ($4 >= 500 && $4 <= 599) err++}
END {if(total) printf "%.2f%%\n", 100*err/total}' access.log
# 40.00%

Cảnh báo: 40% là trên fixture chỉ có 5 request; không thể tự suy ra SLO production từ mẫu nhỏ này. Nếu log có bản ghi hỏng, mẫu số có thể bị lệch.

9. Đo latency: trung bình và giới hạn

awk '{sum+=$5; n++} END {if(n) printf "%.1f ms\n", sum/n}' access.log
# 44.2 ms

Tổng latency = 12+2+93+4+110 = 221 ms, số request = 5, trung bình = 44.2 ms.

Theo endpoint:

awk '{count[$3]++; total[$3]+=$5; if($4>=500 && $4<=599) bad[$3]++}
END {for(p in count) printf "%s count=%d mean=%.1fms 5xx=%.1f%%\n", p,count[p],total[p]/count[p],100*bad[p]/count[p]}' access.log

Với /orders: 2 request, latency 93 và 110, trung bình 101.5 ms, tỷ lệ 5xx 100%.

Phản biện: Trung bình có nói được p95/p99 không? Không. Tail latency có thể rất cao trong khi trung bình vẫn thấp. Percentile cần phương pháp và dữ liệu phù hợp; không nhầm sort -n | tail với percentile có định nghĩa rõ.

10. Mối liên hệ giữa sắp xếp và thống kê

Để đếm tần suất, pipeline phổ biến là extract | sort | uniq -c | sort -nr. Mỗi bước có một bất biến:

  1. extract tạo đúng một khóa trên mỗi bản ghi hợp lệ.
  2. sort đưa khóa giống nhau đứng cạnh nhau.
  3. uniq -c đếm nhóm liên tiếp.
  4. sort -nr xếp nhóm theo tần suất giảm dần.
awk '{print $1}' access.log | sort | uniq -c | sort -nr

Vấn đề tương tự: Đây là dạng group-by đơn giản, gần với SELECT ip, COUNT(*) FROM logs GROUP BY ip ORDER BY COUNT(*) DESC trong SQL. Với dữ liệu có cấu trúc và khối lượng lớn, database hoặc công cụ chuyên dụng có thể thích hợp hơn.

11. sort: quy tắc so sánh, locale và numeric sort

11.1. Sắp xếp số khác sắp xếp chuỗi

Giả sử file numbers.txt:

2
10
100
20
3

sort numbers.txt so sánh theo văn bản, có thể cho thứ tự 10, 100, 2, 20, 3 trong LC_ALL=C. Vì ký tự '1' đứng trước '2', chuỗi "10" đứng trước "2". Nhưng giá trị số thì 10 > 2.

sort -n numbers.txt
# 2 3 10 20 100 (mỗi giá trị một dòng)
sort -nr numbers.txt   # giảm dần

Tại sao không luôn dùng -n? Vì 001, 01, 1 có thể là ba mã định danh khác nhau nhưng cùng giá trị số. Không được suy diễn kiểu dữ liệu từ hình thức.

11.2. Sắp xếp theo cột với sort -k

alice 90
bob 70
charlie 100
david 85

sort -k2,2n scores.txt
sort -k2,2nr -k1,1 students.txt  # điểm giảm dần, tên tăng dần

-k2 dùng khóa từ trường 2 đến cuối dòng; -k2,2 giới hạn ở trường 2. Nếu bằng khóa, GNU sort có thể dùng so sánh toàn dòng để phân định trừ khi thay đổi chế độ như -s; hãy hiểu điều này nếu cần ổn định theo input.

11.3. Các chế độ thường gặp

Tùy chọn Ý nghĩa
sort Văn bản theo locale
sort -n Số
sort -r Đảo thứ tự
sort -nr Số giảm dần
sort -h Hậu tố dung lượng kiểu 10K, 2M, 1G (GNU)
sort -V Version sort (GNU)
sort -u Loại trùng theo khóa so sánh
sort -k2,2n Trường 2 là số 
printf '%s\n' 10K 2M 500K 1G | sort -h
printf '%s\n' version1 version10 version2 | sort -V
sort -k5,5nr access.log  # latency giảm dần
LC_ALL=C sort file.txt   # thứ tự byte ổn định

Câu hỏi: LC_ALL=C có phải cách sắp xếp tên tiếng Việt đúng chuẩn ngôn ngữ? Không; đó là thứ tự byte, hữu ích cho tính tái lập, không phải collation tiếng Việt.

12. uniq: vì sao chỉ gộp dòng trùng liền nhau?

Dữ liệu:

apple
banana
apple
orange
banana
apple

uniq fruits.txt không loại hết các dòng apple rời nhau. Nó chỉ so sánh với dòng ngay trước. Điều này cho phép thuật toán chỉ giữ một dòng gần nhất trong bộ nhớ.

sort fruits.txt | uniq -c
sort fruits.txt | uniq -c | sort -nr

Kết quả đếm: apple=3, banana=2, orange=1.

Nếu muốn giữ thứ tự xuất hiện đầu tiên:

awk '!seen[$0]++' fruits.txt

Cách awk giữ một associative array theo giá trị duy nhất nên có thể tiêu tốn RAM nếu cardinality rất cao. sort | uniq cũng có chi phí riêng: sắp xếp toàn bộ dữ liệu.

13. cut: chọn trường đơn giản

alice:1000:developer
bob:1001:tester
charlie:1002:admin

cut -d: -f1 users.txt
cut -d: -f2 users.txt
cut -d: -f1,3 users.txt
awk -F: '$2 >= 1001 {print $1}' users.txt

cut không hiểu CSV quoted fields:

name,address,age
Alice,"Hanoi, Vietnam",25

cut -d, -f2 people.csv trả "Hanoi chứ không phải toàn bộ địa chỉ. Với CSV chuẩn, hãy dùng parser CSV (ví dụ module csv của Python).

14. tr: chuyển, xóa và gộp ký tự

echo 'hello linux' | tr 'a-z' 'A-Z'
# HELLO LINUX
echo 'abc123xyz' | tr -d '0-9'
# abcxyz
echo 'hello    linux' | tr -s ' '
# hello linux
tr 'a-z' 'A-Z' < input.txt > output.txt

tr xử lý tập ký tự, không phải trình thay thế substring nhiều ký tự theo ngữ cảnh. Việc biến đổi Unicode có thể phụ thuộc locale và bản triển khai; đừng mặc định tr 'a-z' 'A-Z' là chuyển chữ hoa hoàn chỉnh cho tiếng Việt.

15. sed: stream editor

INFO server started
DEBUG request received
ERROR database timeout

sed 's/DEBUG/TRACE/' app.log     # thay lần đầu mỗi dòng
sed 's/DEBUG/TRACE/g' app.log    # thay mọi lần
sed -n '/ERROR/p' app.log        # chỉ in dòng chứa ERROR
sed -i.bak 's/DEBUG/TRACE/g' app.log  # GNU sed, backup .bak

Mặc định sed không sửa file gốc; -i là tùy chọn sửa file. Khi service đang ghi log, sửa tại chỗ có thể gây rắc rối do inode và file descriptor; thường nên xử lý bản sao hoặc output riêng.

CRLF: Nếu dữ liệu có \r cuối dòng, việc match $ và so sánh trường có thể bất ngờ. Quan sát bằng sed -n '1,10l' file và chuyển định dạng khi có lý do chính đáng.

16. awk: record, field, điều kiện, tổng hợp

awk '$2 >= 80 {print $1}' scores.txt
awk '{print NR, NF, $0}' scores.txt
awk -F: '$2 >= 1001 {print $1}' users.txt
Biến Ý nghĩa
$0 Toàn bộ record
$1, $2 Trường thứ nhất, thứ hai
NF Số trường hiện tại
NR Tổng số record đã đọc
FS Dấu phân cách input
OFS Dấu phân cách output 
awk '{sum+=$2; count++} END {if(count) print sum/count}' scores.txt
awk '{count[$4]++} END {for (status in count) print status, count[status]}' access.log

Associative array của awk tương tự dictionary trong Python hoặc hash map trong C++. Thứ tự duyệt for (key in arr) không phải thứ tự được bảo đảm; nếu cần thứ tự, hãy sort output hoặc dùng giải pháp khác.

Đặt câu hỏi: Tại sao awk '$4 == 500' đáng tin hơn grep 500 trong fixture này? Vì ta dùng thông tin schema: trường 4 là status.

17. Lab hoàn chỉnh: phân tích access.log

# 17.1. Lọc 5xx
awk '$4 >= 500 && $4 <= 599' access.log
# 10.0.0.1 POST /orders 500 93
# 10.0.0.2 GET /orders 503 110

# 17.2. Đếm status
awk '{print $4}' access.log | sort -n | uniq -c

# 17.3. Đếm request theo IP
awk '{print $1}' access.log | sort | uniq -c | sort -nr

# 17.4. Trung bình latency
awk '{sum+=$5; n++} END {if(n) print sum/n}' access.log
# 44.2

# 17.5. Tỷ lệ lỗi
awk '{total++; if($4>=500 && $4<=599) errors++}
END {if(total) printf "%.2f%%\n", 100*errors/total}' access.log
# 40.00%

Kiểm tra tay: Có 5 request, 2 request 5xx, latency tổng 221 ms. Những số liệu này là oracle nhỏ để đối chiếu với script.

18. Malformed log: lỗi nguy hiểm vì trông hợp lý

echo '10.0.0.4 POST /orders 500' >> access.log

Dòng 6 thiếu latency. Nếu awk cộng $5 như số, trường thiếu có thể bị chuyển thành 0; tổng vẫn 221 nhưng mẫu số tăng thành 6, cho 36.83 ms thay vì 44.2 ms.

awk 'NF != 5 {print NR, $0}' access.log
# 6 10.0.0.4 POST /orders 500

Validation tối thiểu:

awk '
NF == 5 &&
$4 ~ /^[0-9][0-9][0-9]$/ &&
$4 >= 100 && $4 <= 599 &&
$5 ~ /^[0-9]+$/ {
    sum += $5
    count++
}
END {if(count) print sum/count}
' access.log
# 44.2

Validation tốt hơn còn phải xem method, path, IP, giới hạn latency, quy tắc dấu phân cách và cách xử lý dòng lỗi. Đừng chỉ bỏ qua malformed record rồi báo cáo như dữ liệu hoàn chỉnh; hãy đếm và cảnh báo tỷ lệ malformed.

19. JSON Lines và jq: parser thay vì cắt chuỗi

cat > access.jsonl <<'EOF'
{"ip":"10.0.0.1","status":200,"latency_ms":12}
{"ip":"10.0.0.2","status":500,"latency_ms":93}
EOF
jq '.status' access.jsonl
jq 'select(.status >= 500 and .status <= 599)' access.jsonl

Đếm theo stream:

jq -n '
reduce inputs as $r (
  {total: 0, errors: 0};
  .total += 1
  | if $r.status >= 500 and $r.status <= 599
    then .errors += 1
    else .
    end
)
' access.jsonl

Kết quả {"total":2,"errors":1}. jq -s gom toàn bộ input vào một array, có thể dùng nhiều RAM với file lớn; reduce inputs giúp tổng hợp theo stream. Trong production, phải xác thực kiểu .status, .latency_ms, phân biệt null, thiếu field và dữ liệu sai cú pháp.

Vì sao không regex JSON? Vì dấu ngoặc, escaping, chuỗi chứa ký tự đặc biệt và nesting có quy tắc ngữ pháp; parser mới hiểu được cấu trúc.

20. Production: lỗi pipeline, hiệu năng, log rotation

20.1. pipefail và exit status

set -o pipefail
grep ERROR missing.log | wc -l
printf 'PIPESTATUS: %s\n' "${PIPESTATUS[*]}"  # kiểm tra ngay sau pipeline nếu cần

pipefail khiến status pipeline phản ánh một lệnh lỗi bên trong thay vì chỉ lệnh cuối. Tuy nhiên grep status 1 là không khớp, nên phải phân biệt không có dữ liệu và không đọc được dữ liệu.

20.2. SIGPIPE

set -o pipefail
producer | head -n 10

head dừng sau 10 dòng và đóng đầu đọc; producer có thể nhận SIGPIPE. Với pipefail, điều này có thể khiến pipeline báo non-zero dù 10 dòng đầu đã được lấy thành công. Đừng gắn nhãn mọi SIGPIPE là lỗi logic.

20.3. sort và dung lượng

sort có thể spill sang file tạm. Khi chỉ cần đếm 5xx, không nên sort file nhiều GB:

awk '$4 >= 500 && $4 <= 599 {n++} END {print n+0}' huge.log

20.4. tail, buffering, rotation

tail -F app.log | grep --line-buffered ERROR

tail -F phù hợp hơn tail -f trong một số trường hợp log bị rename/rotate, nhưng vẫn phải hiểu thời điểm mất/đọc lặp dữ liệu. Với dữ liệu đang ghi, việc đọc không bảo đảm snapshot nhất quán.

20.5. Filename chứa khoảng trắng/newline

find . -type f -name '*.log' -print0 | xargs -0 grep -H ERROR

NUL-delimited tránh tách sai tên file. Dùng -- khi tên file/pattern có thể bắt đầu bằng -. Tránh đưa trực tiếp dữ liệu log vào eval hoặc câu lệnh shell; đây là đường dẫn tới command injection.

21. Debug pipeline theo từng giai đoạn

Khi thống kê sai, đừng sửa cả pipeline một lúc. Tách và quan sát các bước:

sed -n '1,20l' access.log
awk '{print NR, NF, $0}' access.log
awk '{print NR, $4}' access.log
awk '$4 !~ /^[0-9][0-9][0-9]$/ {print NR, $0}' access.log

Phương pháp senior:

  1. Tạo fixture nhỏ và kết quả kỳ vọng tính tay.
  2. Kiểm tra input có đúng schema không.
  3. Quan sát output trung gian của từng stage.
  4. Phân biệt bản ghi hợp lệ, bản ghi bị loại, bản ghi malformed.
  5. Đo hiệu năng với dữ liệu thật; tránh tối ưu trước khi biết bottleneck.
  6. Viết test cho trường hợp file rỗng, thiếu cột, ký tự lạ, nhiều dữ liệu và lỗi I/O.

Liên hệ Embedded Linux/SocketCAN: ip -details -statistics link show can0 xem thống kê giao diện CAN, candump can0 xem frame. candump -L can0 tạo log có timestamp; cần hiểu định dạng thực tế trước khi awk tách trường. Đừng mặc định log CAN có schema giống HTTP.

22. Bài tập cuối bài và câu hỏi phản biện

Bài tập 1: Sắp xếp 2, 10, 100 theo số; giải thích vì sao sort khác sort -n.

Bài tập 2: Đếm số request theo HTTP status và sắp xếp giảm dần theo số lần xuất hiện.

Bài tập 3: Tìm hai request chậm nhất; kiểm tra liệu dòng malformed có làm sai thứ tự hay không.

Bài tập 4: Tính tỷ lệ 5xx chỉ trên record hợp lệ, đồng thời in riêng số record malformed.

Bài tập 5: Viết parser JSONL kiểm tra .status là số và .latency_ms không âm.

Bài tập 6: Giải thích vì sao grep '500' không tương đương awk '$4 == 500'.

Bài tập 7: So sánh bộ nhớ và I/O của sort | uniq -c với associative array awk.

Bài tập 8: Thử set -o pipefail với pipeline có grep không khớp và với head đóng pipe sớm.

Tự kiểm tra: Phần tương tác cuối tài liệu có 5 câu trắc nghiệm kèm giải thích.

23. Tổng kết và tư duy thiết kế hệ thống

Chuỗi xử lý tổng quát:

Dữ liệu thô → Lọc và biến đổi → Sắp xếp/tổng hợp → Parser cho dữ liệu cấu trúc → Validation và kết quả đáng tin cậy.

  • grep lọc theo mẫu; rg tìm kiếm hiệu quả trong dự án.
  • Regex mô tả hình dạng chuỗi, không phải parser vạn năng.
  • cut, tr, sed xử lý những phép biến đổi đơn giản và rõ ràng.
  • sort phải dùng đúng kiểu so sánh; uniq chỉ gộp dòng kề nhau.
  • awk phù hợp thống kê trên schema phẳng; jq hiểu JSON.
  • Production đòi hỏi kiểm tra schema, xử lý malformed input, lỗi pipeline, giới hạn RAM/I/O, buffering và tính nhất quán.

Kết luận quan trọng nhất: Pipeline tốt không chỉ chạy được. Nó phải có hợp đồng dữ liệu rõ ràng, phát hiện lỗi, cho kết quả có thể kiểm chứng và phù hợp quy mô thực tế. Đây là khác biệt giữa một câu lệnh thử nghiệm và một công cụ chẩn đoán đáng tin cậy.
