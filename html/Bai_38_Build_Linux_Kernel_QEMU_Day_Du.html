Bài 38 — Build Linux Kernel và Linux tối giản trong QEMU

Chuyên sâu Linux Kernel · Embedded Linux · Boot Process · Build System · Virtualization · Debugging

Mục tiêu: Tự biên dịch kernel, tạo root filesystem tối giản bằng BusyBox static, đóng gói initramfs, boot trong QEMU, quan sát PID 1, chẩn đoán lỗi và liên hệ Embedded Linux production. Bài học kết nối Bài 14 (boot/shutdown), Bài 16 (system call), Bài 23 (driver/I/O), Bài 37 (virtualization).

Phần I — Tại sao phải tự build Linux Kernel?

1. Linux có phải một hệ điều hành hoàn chỉnh?

Trên Ubuntu, chạy:

bash
uname -r
ps -p 1 -o pid,comm,args

Bạn có thể thấy một kernel 6.x.y-generic và PID 1 là systemd. Nếu xóa systemd, Linux còn chạy được không? Có, miễn là thay bằng chương trình init phù hợp. Kernel quản lý CPU, RAM, tiến trình, thiết bị, system call. systemd quản lý khởi tạo và dịch vụ ở user space. Shell giúp người dùng tương tác; ls, cat, mount là các chương trình user space.

<!--DIAGRAM:layers-->

Ví dụ đời sống: Kernel giống người điều phối máy móc trong nhà máy; hardware là máy móc; process là công nhân; init/systemd là bộ phận quản lý ca; memory/storage là kho; system call là thủ tục xin tài nguyên. Người điều phối không phụ thuộc vào một bộ phận quản lý ca cụ thể.

Câu hỏi phản biện: Nếu không bắt buộc có systemd, vì sao desktop/server thường sử dụng? Vì cần điều phối dependency, theo dõi dịch vụ, restart, logging, session, shutdown, isolation. Init vài dòng chỉ phù hợp lab.

Phần II — Build Kernel thực chất là gì?

2. Source code khác kernel đang chạy

Tải source từ kernel.org, bạn nhận được C, assembly, Makefile, Kconfig, script, chứ không phải một hệ điều hành đã sẵn sàng chạy.

text
linux/
├── arch/       # x86, arm, arm64, riscv...
├── block/      # block layer
├── drivers/    # device drivers
├── fs/         # VFS và filesystem
├── include/    # headers
├── init/       # khởi tạo kernel
├── kernel/     # scheduler, locking, signal...
├── mm/         # memory management
├── net/        # network stack
├── scripts/    # build utilities
├── Kconfig
└── Makefile

Build kernel là chuyển mã nguồn và cấu hình thành các artifact có thể nạp, thực thi hoặc debug.

<!--DIAGRAM:build-->

2.1. vmlinux, bzImage, vmlinuz, .ko

Artifact Bản chất Công dụng
vmlinux ELF kernel Debug, symbol, phân tích
arch/x86/boot/bzImage x86 boot image QEMU/bootloader nạp kernel
vmlinuz Tên kernel image thường gặp trong /boot Boot distro, thường liên quan image nén
*.ko Kernel module Nạp tính năng/driver khi chạy
bash
file vmlinux
file arch/x86/boot/bzImage

Tại sao không đưa tất cả driver vào kernel? Kích thước, RAM, attack surface và bảo trì tăng. Nhưng cắt giảm quá mức khiến kernel không truy cập được root disk.

Phần III — Kconfig quyết định kernel có gì

3. Ý nghĩa của .config

text
CONFIG_EXT4_FS=y
CONFIG_E1000=m
# CONFIG_BTRFS_FS is not set
Giá trị Ý nghĩa Kết quả
y Built-in Liên kết vào kernel
m Module (nếu hỗ trợ) Build .ko
n Disabled Không build

Một số tùy chọn chỉ hỗ trợ y/n, một số là số hoặc chuỗi.

Tại sao CONFIG_EXT4_FS=m có thể gây lỗi boot? Nếu root disk là ext4 mà module ext4 chỉ nằm trên chính root disk, kernel cần mount root để đọc module nhưng lại cần module để mount root. Đây là dependency cycle. Giải pháp: built-in =y, hoặc initramfs có module, công cụ nạp và logic mount root.

Kconfig không phải danh sách toggle độc lập: Một option có depends on hoặc select, nên lệnh bật option chưa bảo đảm kết quả sau khi giải dependency.

bash
make defconfig
make menuconfig
make olddefconfig
make savedefconfig
scripts/config --enable SOME_OPTION
make olddefconfig
grep '^CONFIG_SOME_OPTION=' .config
scripts/config --state SOME_OPTION

defconfig tạo mặc định; menuconfig chỉnh tương tác; olddefconfig cập nhật theo default; savedefconfig xuất cấu hình rút gọn. Luôn lưu .config, version, toolchain.

Phần IV — CPU architecture và toolchain

4. Tại sao kernel x86 không chạy trực tiếp trên ARM?

CPU thực thi machine instructions theo ISA, không thực thi C. Compiler tạo code cho x86-64, AArch64 hoặc RISC-V. Cùng viết bằng C không có nghĩa binary hoán đổi được.

<!--DIAGRAM:arch-->

Native build x86-64:

bash
make ARCH=x86_64 defconfig
make ARCH=x86_64 -j2 bzImage

Cross-compile ARM64:

bash
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- defconfig
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j2 Image
# Artifact thường ở arch/arm64/boot/Image

ARCH chọn kiến trúc kernel; CROSS_COMPILE chọn prefix toolchain (aarch64-linux-gnu-gcc, ...-ld). Cần cross-toolchain và host build dependencies.

Liên hệ ESP32: Firmware ESP32 không thể chạy trực tiếp trên x86. Tương tự, hai board ARM64 có thể cần Device Tree, UART, clock, IRQ, MMIO, reset, storage driver khác nhau. ISA giống nhau không có nghĩa board giống nhau.

Phần V — Device Tree và ACPI

5. Kernel biết phần cứng bằng cách nào?

Một driver UART biết thao tác thanh ghi, nhưng phải biết MMIO base, IRQ, clock, trạng thái và loại controller. Nhiều nền tảng ARM dùng Device Tree:

dts
uart0: serial@10000000 {
    compatible = "vendor,example-uart";
    reg = <0x10000000 0x1000>;
    interrupts = <5>;
    status = "okay";
};

Đây là ví dụ minh họa, không phải cấu hình board cụ thể. Device Tree là mô tả phần cứng, không phải driver. Sơ đồ bố trí nhà máy không thay cho người vận hành máy. PC x86 thường dựa vào ACPI, PCI enumeration và các cơ chế firmware khác; lab QEMU x86 không yêu cầu tự tạo DTB.

Phần VI — Initramfs và root filesystem

6. Tại sao có kernel vẫn chưa đủ?

Kernel khởi tạo CPU, RAM, scheduler, driver, sau đó cần chuyển sang user space. Chương trình đầu tiên ở đâu? Trong root filesystem, có thể được cung cấp ban đầu bằng initramfs.

text
/
├── bin/
├── dev/
├── etc/
├── proc/
├── sbin/
├── sys/
├── tmp/
└── usr/

Root filesystem là cây mount bắt đầu từ /, không đồng nghĩa một phân vùng trên SSD. Có thể dùng SD/eMMC, NFS, tmpfs, initramfs...

Initramfs là cpio archive (thường gzip) được kernel giải nén vào rootfs trong RAM:

text
initramfs.cpio.gz
  └── /
      ├── init
      ├── bin/busybox
      ├── bin/sh -> busybox
      ├── dev/console
      ├── proc/
      └── sys/

Initramfs hiện đại khác legacy initrd block-device image. Initramfs không đòi hỏi tạo partition ext4 ban đầu.

6.1. Boot sequence tương tác

<!--INTERACTIVE:boot-->

Câu hỏi: Tắt QEMU thì dữ liệu lưu ở đâu? Rootfs trong RAM mất các thay đổi không được lưu vào storage bền vững. Điều này thuận tiện cho lab nhưng production cần thiết kế persistent data, read-only rootfs, overlayfs hoặc A/B update.

Phần VII — BusyBox: một executable, nhiều tiện ích

7. Vì sao BusyBox phù hợp embedded?

Thay vì đóng gói nhiều binary của coreutils, util-linux, procps, BusyBox tích hợp nhiều applet:

bash
busybox ls
busybox cat
busybox mount
busybox sh

Symlink /bin/sh -> busybox cho phép BusyBox chạy applet shell dựa trên tên được gọi. BusyBox là user space, vẫn dùng Linux system calls (open/read/write/...).

Static vs dynamic linking: Binary static chứa code thư viện đã được liên kết và không cần dynamic ELF interpreter khi khởi chạy; binary dynamic cần loader và shared libraries đúng ABI. Static vẫn cần đúng kiến trúc và kernel API tương thích.

bash
file /usr/bin/busybox
readelf -l /usr/bin/busybox

Nếu readelf hiển thị INTERP như /lib64/ld-linux-x86-64.so.2, binary cần dynamic interpreter. Thiếu interpreter có thể gây No such file or directory ngay cả khi executable tồn tại.

Phần VIII — Lab build kernel từ đầu

8. Chuẩn bị môi trường

Giả định Ubuntu/Debian x86-64, có đủ nhiều GiB disk và RAM. Không cài kernel thử nghiệm vào boot của host.

bash
uname -m
nproc
free -h
df -h "$HOME"

sudo apt update
sudo apt install -y \
    build-essential flex bison bc libelf-dev libssl-dev \
    libncurses-dev cpio gzip xz-utils wget file binutils \
    qemu-system-x86 busybox-static

mkdir -p ~/linux-lab/{kernel,downloads,artifacts,logs}
Công cụ Vai trò
GCC / make Compile và điều phối build
flex / bison / bc Công cụ hỗ trợ Kbuild
libelf-dev / libssl-dev ELF và crypto build support
libncurses-dev menuconfig
cpio / gzip Initramfs
QEMU Máy ảo
busybox-static User space tối giản
file / readelf Kiểm tra ELF

Tại sao không chạy -j$(nproc) ngay? Build song song quá mức có thể gây RAM pressure, swap và OOM; -j2 là lựa chọn lab thận trọng.

9. Tải source có phiên bản rõ

Chọn stable release thực sự từ kernel.org. Ví dụ biến sau phải thay bằng version đã chọn; v6.x chỉ đúng với nhánh 6.x.

bash
cd ~/linux-lab/downloads
KVER="PHIEN_BAN_DA_CHON"
wget "https://cdn.kernel.org/pub/linux/kernel/v6.x/linux-${KVER}.tar.xz"

Xác minh checksum/chữ ký theo hướng dẫn nhà phát hành, kiểm tra khóa ký đáng tin cậy. Hash xác minh integrity; hash từ nguồn không đáng tin cậy không tự chứng minh authenticity.

bash
cd ~/linux-lab/kernel
tar -xf "../downloads/linux-${KVER}.tar.xz"
cd "linux-${KVER}"
make kernelversion
gcc --version
make --version

10. Cấu hình kernel cho lab

bash
make defconfig
scripts/config --enable BLK_DEV_INITRD
scripts/config --enable RD_GZIP
scripts/config --enable DEVTMPFS
scripts/config --enable SERIAL_8250
scripts/config --enable SERIAL_8250_CONSOLE
scripts/config --enable BINFMT_ELF
scripts/config --enable BINFMT_SCRIPT
scripts/config --enable PROC_FS
scripts/config --enable SYSFS
make olddefconfig
Option Vì sao cần
BLK_DEV_INITRD Initrd/initramfs được cấp lúc boot
RD_GZIP Hỗ trợ gzip initramfs
DEVTMPFS Device nodes qua devtmpfs
SERIAL_8250 UART 8250/16550
SERIAL_8250_CONSOLE Kernel serial console
BINFMT_ELF Chạy ELF executable

Kiểm tra lại sau olddefconfig, vì Kconfig dependency có thể khiến yêu cầu không thành công:

bash
grep -E 'CONFIG_(BLK_DEV_INITRD|RD_GZIP|DEVTMPFS|SERIAL_8250|SERIAL_8250_CONSOLE|BINFMT_ELF|BINFMT_SCRIPT|PROC_FS|SYSFS)=' .config

Các chức năng thiết yếu trước khi nạp module cần được built-in (=y). Serial console quan trọng: không thấy log không đồng nghĩa kernel chưa boot.

11. Build và xác minh

bash
make -j2 bzImage
ls -lh arch/x86/boot/bzImage
file arch/x86/boot/bzImage
file vmlinux

Build success ≠ boot success ≠ functional correctness ≠ production readiness. Build thành công không chứng minh đủ driver storage, rootfs, network hay tính ổn định runtime.

Phần IX — Tạo rootfs và chương trình init

12. Tạo rootfs và BusyBox static

Vẫn trong thư mục source kernel:

bash
kernel_image="$PWD/arch/x86/boot/bzImage"
rootfs_dir=$(mktemp -d "$HOME/linux-lab/rootfs.XXXXXX")
mkdir -p "$rootfs_dir"/{bin,dev,proc,sys,tmp}

BUSYBOX="$(command -v busybox)"
file "$BUSYBOX"
readelf -l "$BUSYBOX"
"$BUSYBOX" --list

Dừng lại nếu BusyBox không phải static đúng kiến trúc hoặc thiếu applet cần dùng. Đường dẫn BusyBox thay đổi theo distro.

bash
cp "$BUSYBOX" "$rootfs_dir/bin/busybox"
ln -s busybox "$rootfs_dir/bin/sh"
find "$rootfs_dir" -maxdepth 2

13. Tạo chương trình /init đầu tiên

Đặt vấn đề: Kernel đã khởi tạo CPU, memory, scheduler, giải nén initramfs. Ai là chương trình user space đầu tiên? Trong lab, kernel command line rdinit=/init yêu cầu thực thi /init, tạo PID 1.

bash
cat > "$rootfs_dir/init" <<'EOF'
#!/bin/sh
/bin/busybox mount -t devtmpfs devtmpfs /dev
/bin/busybox mount -t proc proc /proc
/bin/busybox mount -t sysfs sysfs /sys
echo 'Minimal Linux ready'
while true; do
    /bin/sh
    echo 'Shell exited; PID 1 stays alive'
done
EOF
chmod +x "$rootfs_dir/init"

13.1. Shebang và execve

Dòng #!/bin/sh được kernel xử lý thông qua BINFMT_SCRIPT. Kernel tìm /bin/sh, phân giải symlink sang BusyBox rồi thực thi shell với script /init. Nếu /bin/sh thiếu, /init có thể tồn tại mà vẫn không chạy được.

<!--DIAGRAM:shebang-->

13.2. Mount /dev, /proc, /sys

devtmpfs cung cấp device nodes như /dev/console, /dev/null, /dev/ttyS0. Device node không chứa dữ liệu file thông thường mà biểu diễn interface thiết bị. procfs cho thông tin kernel/tiến trình động (/proc/cmdline, /proc/meminfo); sysfs biểu diễn device và kernel objects (/sys/class, /sys/devices).

bash
# Chạy bên trong guest sau khi boot:
/bin/busybox cat /proc/cmdline
/bin/busybox cat /proc/meminfo
/bin/busybox ls /sys/class

Ví dụ đời sống: /proc như bảng trạng thái trực tiếp của nhà máy; /sys như danh bạ thiết bị và thông số, không phải file text được lưu sẵn trên SSD.

13.3. Tại sao PID 1 không được kết thúc?

Nếu /init chỉ echo Hello rồi exit, init của hệ thống guest kết thúc và kernel thường panic. Vòng while true tạo shell mới khi shell cũ kết thúc, giữ PID 1 sống. Nhưng đây chưa phải init production: cần reaping zombie, signal handling, shutdown, restart backoff, mount failure handling.

Ví dụ cải thiện lab (vẫn không phải production init):

sh
#!/bin/sh
BB=/bin/busybox
$BB mount -t devtmpfs devtmpfs /dev || echo 'Failed to mount /dev'
$BB mount -t proc proc /proc || echo 'Failed to mount /proc'
$BB mount -t sysfs sysfs /sys || echo 'Failed to mount /sys'
echo 'Minimal Linux ready'
while true; do
    /bin/sh
    echo 'Shell exited'
    /bin/busybox sleep 1
done

Khoảng nghỉ ngăn restart loop tiêu thụ CPU nếu shell thoát tức thì. Production phải xử lý lỗi filesystem thiết yếu rõ ràng.

14. Tạo /dev/console

bash
sudo mknod -m 600 "$rootfs_dir/dev/console" c 5 1
ls -l "$rootfs_dir/dev/console"
# crw------- ... 5, 1 ... console

c là character device, 5 major, 1 minor. Major/minor là device number giúp kernel định tuyến I/O. Console node cần có trong archive trước khi /init mount devtmpfs, vì kernel có thể cần mở console khi khởi chạy init. Nếu host cấm mknod, dùng VM build hoặc gen_init_cpio với device-node specification phù hợp.

15. Đóng gói initramfs

bash
initramfs_file="$rootfs_dir.cpio.gz"
(cd "$rootfs_dir" && find . -print0 | cpio --null -o --format=newc --owner=0:0) | gzip > "$initramfs_file"

find -print0 và cpio --null xử lý tên file có khoảng trắng/newline an toàn. newc là định dạng cpio cho initramfs; --owner=0:0 ghi UID/GID root vào archive. Đây không phải ext4 disk image.

<!--DIAGRAM:archive-->

bash
gzip -t "$initramfs_file"
gzip -dc "$initramfs_file" | cpio -it
# Mong đợi: . bin bin/busybox bin/sh dev dev/console proc sys tmp init

Phản biện: gzip -t thành công có chứng minh archive boot được không? Không: bên trong gzip có thể không phải cpio newc, hoặc thiếu /init, interpreter, permission.

Phần X — Boot Linux trong QEMU

16. QEMU làm gì?

QEMU cung cấp CPU/RAM/serial/interrupt controller ảo. Lab không gắn disk host. Guest kernel và guest rootfs độc lập với host.

<!--DIAGRAM:qemu-->

bash
qemu-system-x86_64 \
  -m 256M -smp 1 \
  -kernel "$kernel_image" -initrd "$initramfs_file" \
  -append 'console=ttyS0 rdinit=/init' \
  -nographic -no-reboot -nic none
Tham số Ý nghĩa
-m 256M RAM guest 256 MiB
-smp 1 Một vCPU
-kernel Kernel image
-initrd Initramfs
-append Kernel command line
console=ttyS0 Serial console đầu tiên trong cấu hình x86 phù hợp
rdinit=/init Init trong initramfs
-nographic Không có GUI, terminal serial
-no-reboot Không tự reboot
-nic none Không cấu hình NIC mặc định qua option này

Không cần -enable-kvm; QEMU có thể chạy bằng TCG emulation chậm hơn. Nếu không có /dev/kvm, lab vẫn có thể chạy.

17. Kết quả boot mong đợi

text
Linux version ...
...
Run /init as init process
...
Minimal Linux ready

Trong guest:

bash
/bin/busybox uname -a
/bin/busybox cat /proc/cmdline
/bin/busybox ps
/bin/busybox mount
/bin/busybox cat /proc/meminfo

uname -a phản ánh guest kernel, không phải host kernel. BusyBox shell có thể báo can't access tty; job control turned off do chưa thiết lập controlling terminal đầy đủ; đó khác lỗi boot. Có thể cải thiện bằng setsid/cttyhack nếu applet có sẵn, nhưng phải giữ đúng vòng đời PID 1. Thoát QEMU -nographic: Ctrl+A rồi X. Rootfs RAM mất thay đổi sau thoát.

Phần XI — Debug Kernel Boot theo checkpoint

18. Phương pháp senior: xác định điểm dừng

Đừng thay hàng loạt .config rồi hy vọng. Phân biệt: (1) QEMU chạy chưa; (2) kernel in log chưa; (3) giải nén initramfs chưa; (4) thực thi /init chưa; (5) mount và shell chạy chưa.

<!--DIAGRAM:checkpoints-->

19. Không có console

Các giả thuyết: kernel không chạy; kernel chạy nhưng console sai; thiếu driver 8250 console; frontend QEMU sai; panic trước console. Kiểm tra:

bash
grep -E 'CONFIG_SERIAL_8250(_CONSOLE)?=' .config
# Kernel command line:
# console=ttyS0

Trong QEMU x86 cấu hình UART COM1 legacy tương ứng, có thể thử:

text
earlycon=uart8250,io,0x3f8,115200 console=ttyS0,115200 rdinit=/init

0x3f8 không phải địa chỉ UART chung cho mọi nền tảng. Không thấy log chưa chứng minh kernel treo.

20. No working init found

Các nguyên nhân: /init thiếu, không executable, shebang sai, BINFMT_SCRIPT thiếu, /bin/sh thiếu, BusyBox sai kiến trúc, thiếu ELF loader. Debug theo chuỗi dependency:

<!--DIAGRAM:initdebug-->

bash
ls -l "$rootfs_dir/init" "$rootfs_dir/bin/sh"
file "$rootfs_dir/bin/busybox"
readelf -l "$rootfs_dir/bin/busybox"
gzip -dc "$initramfs_file" | cpio -it

Lỗi phổ biến: sửa file trong rootfs nhưng không đóng gói lại cpio; QEMU vẫn boot archive cũ.

21. File tồn tại nhưng chạy báo not found

bash
ls -l /bin/myapp
/bin/myapp
# not found

Có thể thiếu ELF interpreter:

bash
readelf -l myapp
# Requesting program interpreter: /lib64/ld-linux-x86-64.so.2

Kernel tìm executable nhưng không tìm được interpreter nên execve có thể trả ENOENT. Host library không tự xuất hiện trong guest. Cần đúng ABI, loader, shared libraries hoặc binary static phù hợp.

22. Không đọc được initramfs

bash
file "$initramfs_file"
gzip -t "$initramfs_file"
gzip -dc "$initramfs_file" | cpio -it
grep CONFIG_BLK_DEV_INITRD .config
grep CONFIG_RD_GZIP .config

Kiểm tra QEMU dùng đúng archive vừa build, không chỉ kiểm tra file gzip tồn tại. gzip hợp lệ chưa chắc cpio hợp lệ.

23. PID 1 chết

sh
#!/bin/sh
echo Hello
# script kết thúc => init hệ thống chết, kernel thường panic

Lab giữ PID 1 sống bằng vòng lặp. Production cần reap child processes, xử lý signal, restart/backoff, shutdown và filesystem cleanup. PID 1 trong container có semantics đặc biệt trong PID namespace, nhưng không đồng nhất với PID 1 host.

Phần XII — Vì sao không có systemd vẫn là Linux?

25. Kernel, distro và init system khác nhau

Thành phần Bản chất
Linux Kernel Nhân hệ điều hành
Ubuntu / Debian Distribution
systemd Init/service management suite
BusyBox User-space utilities
glibc / musl C library implementations
QEMU Emulator/VM monitor
Initramfs Initial root filesystem archive

Hệ thống có thể là Linux Kernel + BusyBox + init script; hoặc Linux + musl + OpenRC; hoặc Linux + systemd. Linux được xác định bởi Linux Kernel, không phải một init system cụ thể. BusyBox vẫn sử dụng system call để yêu cầu kernel thực hiện I/O, process, memory... Lưu ý API libc và syscall không nhất thiết ánh xạ một-một.

Phần XIII — Embedded Linux thực tế

26. QEMU x86 khác board thật

QEMU mô phỏng phần cứng được cấu hình; board thật có SoC, DDR, clock/reset, IRQ, UART, eMMC/SD, firmware, bootloader, Device Tree khác nhau.

text
Boot ROM
   ↓
SPL / early bootloader (tùy board)
   ↓
U-Boot hoặc bootloader khác
   ↓
Linux Kernel + Device Tree (nếu dùng)
   ↓
Root filesystem
   ↓
PID 1

Cùng ARM64 ISA không đủ; kernel cần tương thích board, boot protocol, driver và DT/ACPI tương ứng. QEMU không thay thế kiểm thử trên hardware thật.

27. Buildroot và Yocto

Khi cần SSH, TLS, network tools, database, Python, logging, OTA, tự copy binary và library trở nên khó bảo trì. Buildroot xây toolchain/kernel/rootfs/packages theo cấu hình; Yocto sử dụng recipe/layer/metadata để tạo distribution tùy biến với nhiều biến thể.

Tiêu chí Tự làm Buildroot Yocto
Học cơ chế Rất tốt Tốt Tốt nhưng phức tạp
Rootfs nhỏ Có Có Có
Package management lúc build Thủ công Tích hợp Recipe/layer
Độ phức tạp Thấp ban đầu Trung bình Cao hơn
Mở rộng sản phẩm Khó Phù hợp nhiều hệ thống cố định Mạnh cho distribution tùy biến

Không có lựa chọn luôn tốt hơn; tùy vòng đời sản phẩm, OTA, quy mô đội và yêu cầu bảo trì.

Phần XIV — Các vấn đề production sâu hơn

28. Build máy A chạy, máy B lỗi

Nguồn khác biệt: GCC, binutils, source, .config, dependencies, environment, target toolchain. Lưu metadata:

bash
make kernelversion > kernel-version.txt
gcc --version > gcc-version.txt
cp .config kernel.config
sha256sum arch/x86/boot/bzImage > bzImage.sha256

Repeatable build là chạy lại quy trình; reproducible build là tái tạo artifact giống nhau theo tiêu chí xác định với đầu vào/điều kiện kiểm soát. Timestamp, build path, user, metadata có thể ảnh hưởng.

29. Kernel nhỏ hơn chưa chắc tốt hơn

Tắt driver storage có thể giảm image nhưng làm boot thất bại; tắt PROC_FS làm công cụ phụ thuộc /proc không hoạt động. Phải xác định mục tiêu: flash, RAM, boot time, attack surface, maintenance. Driver dưới dạng module không nhất thiết giảm tổng firmware nếu vẫn đóng gói module.

30. Kernel module compatibility

Module .ko build cho kernel A không tự tương thích kernel B. ABI, vermagic, symbols và config khác nhau:

bash
modinfo mydriver.ko
uname -r
insmod mydriver.ko

Không giả định version gần nhau là có thể hoán đổi. Out-of-tree modules phải build/test với target kernel thực tế.

31. Root disk cần chuỗi driver đầy đủ

text
eMMC host controller
    ↓
MMC subsystem
    ↓
Block layer
    ↓
Partition recognition
    ↓
Filesystem driver (ví dụ ext4)
    ↓
Mount root
    ↓
Execute init

Kernel boot từ RAM trong QEMU không kiểm chứng eMMC controller. Initramfs có thể chứa module và tools để mount root thật, nhưng không tự chữa mọi thiếu sót driver hoặc module support.

32. Tối ưu boot time theo bottleneck

text
Firmware time + Bootloader time + Kernel init time + User-space init time = Total boot time

Có thể thêm printk.time=1 để hiển thị timestamp kernel log khi hỗ trợ. Nếu bootloader mất 3 giây, giảm shell script 100 ms xuống 50 ms ít ảnh hưởng. Đo rồi mới tối ưu.

Phần XV — Lab nâng cao

33. Kiểm tra PID 1

bash
/bin/busybox ps
/bin/busybox cat /proc/1/status
/bin/busybox cat /proc/1/cmdline

PID 1 có thể được hiển thị dưới tên init hoặc sh tùy script/BusyBox; không mặc định là systemd.

34. Kiểm tra root filesystem

bash
/bin/busybox mount
/bin/busybox cat /proc/mounts

Không có ổ cứng vẫn có filesystem: rootfs, procfs, sysfs, devtmpfs...

35. Quan sát system calls

BusyBox không nhất thiết có strace applet. Nếu muốn trace, đưa binary strace phù hợp cùng dependencies hoặc dùng kernel tracing tương thích. Ví dụ logic:

text
Shell → execve() → BusyBox cat
                  ↓
       openat('/proc/cmdline')
                  ↓
             read() → write(stdout) → close()

36. Thử kernel command line

text
console=ttyS0 rdinit=/init loglevel=7
console=ttyS0 rdinit=/init quiet

Thay đổi lượng log không đồng nghĩa thay đổi tình trạng kernel.

40. Năm nguyên tắc

  1. Hiểu dependency trước khi debug: /init phụ thuộc shebang, interpreter, ELF, loader.
  2. Phân biệt boot stages: lỗi trước kernel khác lỗi khi PID 1 chạy.
  3. Không đồng nhất build success với correctness: phải boot và kiểm thử.
  4. Luôn có observability: serial console, log, artifact metadata.
  5. Thiết kế reproducibility: người khác phải tái tạo được kết quả.
