1. Đặt vấn đề — tại sao Linux cần phân quyền?

Một máy Linux có thể chạy đồng thời web server, cơ sở dữ liệu, ứng dụng điều khiển động cơ, tài khoản lập trình viên và các tiến trình hệ thống. Nếu mọi tiến trình đều có quyền đọc, sửa và xóa mọi dữ liệu, một lỗi nhỏ có thể ảnh hưởng toàn hệ thống.

Ví dụ đời sống: Một tòa nhà có nhiều phòng. Thẻ nhân viên là danh tính; quyền mở từng cửa là permission; bảo vệ và quy định an ninh tương ứng với những tầng kiểm soát bổ sung.

Câu hỏi: Nếu ứng dụng chỉ cần đọc cảm biến, tại sao phải cho phép nó sửa /etc/shadow? Không có lý do hợp lý. Đây là nền tảng của least privilege.

2. User, UID, Group và GID

Linux dùng số UID để biểu diễn user và GID để biểu diễn group. Tên như alice hoặc developers là biểu diễn thuận tiện cho con người, thường được phân giải qua NSS.

id
id alice
getent passwd alice
getent group developers
cat /etc/passwd

/etc/passwd chứa metadata tài khoản; mật khẩu dạng hash thường nằm ở /etc/shadow trên các hệ thống truyền thống. Không phải mọi tài khoản đều bắt buộc xuất hiện trong file cục bộ vì NSS có thể tra cứu nguồn khác.

Thuật ngữ Diễn giải
UID Định danh số của user
Primary GID Group chính của user
Supplementary groups Các group bổ sung
Root Tài khoản đặc quyền, thường UID 0 trong user namespace ban đầu
Service account Danh tính dành cho daemon, thường không cho đăng nhập tương tác

3. Credentials của tiến trình

Quyền truy cập được kiểm tra dựa trên credentials của tiến trình, không chỉ dựa vào tên đăng nhập hiển thị. Linux có real/effective/saved-set UID/GID và filesystem UID/GID; trong các thao tác filesystem, fsuid/fsgid có vai trò quan trọng.

cat /proc/self/status | grep -E '^(Uid|Gid|Groups|Cap)'
ps -eo pid,user,group,comm | head

Một user được thêm vào group sau khi tiến trình đã khởi chạy không làm credentials của tiến trình cũ tự thay đổi. Vì vậy, khi sửa group cho daemon, cần tạo lại tiến trình, thường bằng cách restart service.

4. Quyền truyền thống: owner / group / other

Ví dụ:

-rwxr-x--- 1 alice developers 1024 main.sh

Ba bộ rwx lần lượt dành cho owner, owning group và other. Linux không đơn giản cộng cả ba bộ quyền: trước tiên xác định lớp phù hợp, sau đó kiểm tra quyền của lớp đó. Với ACL mở rộng, quy tắc chọn entry và mask chi tiết hơn.

Ký hiệu File thường Directory
r Đọc nội dung Liệt kê tên entries
w Sửa nội dung Tạo/xóa/đổi tên entries, nếu điều kiện khác thỏa
x Thực thi file phù hợp Search/traverse directory

Tại sao file 666 vẫn không mở được? Vì có thể thiếu quyền search trên một directory cha hoặc bị một chính sách khác từ chối.

5. Directory permission — điểm dễ nhầm nhất

Đối với directory, x là quyền tra cứu tên, không phải quyền chạy directory. r cho phép liệt kê tên; w kết hợp với x thường cần để thay đổi directory entries.

mkdir -p /tmp/perm-demo
touch /tmp/perm-demo/report.txt
ls -ld /tmp/perm-demo
namei -l /tmp/perm-demo/report.txt

Quyền xóa file phụ thuộc chủ yếu vào directory cha, sticky bit và những giới hạn khác; file writable không có nghĩa có thể xóa file đó. Ngược lại, file không writable vẫn có thể bị unlink khi directory cho phép.

6. Path resolution và symlink

Để mở /srv/project/a.txt, kernel phải đi qua /, /srv, /srv/project rồi mới kiểm tra đối tượng đích. Thiếu search permission ở bất kỳ directory nào có thể gây EACCES.

namei -l /srv/project/a.txt
readlink -f /srv/project/a.txt
stat /srv/project/a.txt

Symlink là một bước phân giải tên khác; quyền trên đối tượng đích và các directory trong đường dẫn đã phân giải mới là những yếu tố quan trọng. Cần cẩn trọng với symlink race khi làm việc trong directory không tin cậy.

7. chmod: symbolic và octal

Mỗi quyền có giá trị r=4, w=2, x=1. 755 nghĩa là owner rwx, group r-x, other r-x.

chmod 640 config.ini
chmod u+x deploy.sh
chmod g+w shared.txt
chmod o-rwx secret.key

Phản biện: chmod -R 777 có phải cách xử lý Permission denied? Không. Nó mở rộng quyền quá mức, làm mất thông tin thiết kế bảo mật và vẫn không sửa được read-only mount, MAC denial hoặc sandbox.

8. chown, chgrp và ownership

sudo chown alice:developers report.txt
sudo chgrp developers report.txt
stat -c '%n %u:%g %a' report.txt

Thay ownership không tương đương với cấp quyền. UID/GID số là dữ liệu cốt lõi trên inode; tái sử dụng UID cũ có thể vô tình trao quyền với những file còn tồn tại. Trên NFS/container, ánh xạ UID/GID cần được kiểm tra kỹ.

9. Group và quyền thiết bị

Ví dụ:

crw-rw---- 1 root dialout ... /dev/ttyUSB0

Một daemon muốn mở UART có thể cần thuộc group dialout hoặc có ACL phù hợp.

ls -l /dev/ttyUSB0
id motorapp
sudo usermod -aG dialout motorapp

Cờ -aG rất quan trọng: dùng -G mà thiếu -a có thể thay thế danh sách supplementary groups. Khởi động lại service để credentials mới được áp dụng. Không mặc định chmod 666 /dev/ttyUSB0 vì quyền thiết bị sẽ bị mở rộng và node có thể được udev tạo lại.

10. umask — quyền mặc định

Khi tạo file, ứng dụng đưa ra requested mode. Trong trường hợp không có default ACL, mode được giới hạn bởi umask:

regular file: requested 0666
directory:    requested 0777
umask:        0022
result file:  0644
result dir:   0755

umask
umask 0002
touch demo.txt
mkdir demo-dir
stat -c '%a %n' demo.txt demo-dir

Lưu ý: Ứng dụng có thể chủ động yêu cầu 0600, nên umask 0002 không đảm bảo mọi file group-writable. Default ACL cũng ảnh hưởng cơ chế hình thành quyền.

11. Setgid directory và kế thừa group

sudo mkdir -p /srv/project
sudo chown root:developers /srv/project
sudo chmod 2770 /srv/project
ls -ld /srv/project

drwxrws--- cho biết setgid bit trên directory. Trên Linux, file mới trong directory thường kế thừa owning group từ directory, nhưng không kế thừa owner. Quyền mode của file không đơn giản sao chép từ directory cha.

11.3. Điều gì được kế thừa? Alice tạo file: owner thường là Alice, group là developers. Bob tạo file: owner Bob, group developers. Tuy nhiên Bob chỉ sửa được file Alice nếu quyền group/ACL cho phép.

/srv/project       root:developers   2770
├── main.c         alice:developers  0664
└── test.c         bob:developers    0664

Các mode 0664 chỉ là ví dụ, không được bảo đảm bởi setgid một mình.

12. POSIX ACL và Default ACL

ACL cho phép named user và named group có quyền riêng, vượt ra ngoài owner/group/other truyền thống.

getfacl /srv/project
sudo setfacl -m g:developers:rwx /srv/project
sudo setfacl -m d:g:developers:rwx /srv/project
sudo setfacl -m d:m::rwx /srv/project

Access ACL kiểm soát đối tượng hiện tại; Default ACL trên directory làm khuôn mẫu cho ACL đối tượng mới. Requested mode của ứng dụng vẫn giới hạn quyền mới; default ACL không tự cấp execute cho regular file được tạo với mode 0666.

user::rw-
user:bob:rwx
group::r--
mask::r--
other::---

Trong ví dụ, named user Bob có quyền hiệu lực r-- vì mask giới hạn rwx. Owner entry và other entry không chịu mask theo cùng quy tắc. Khi có ACL mở rộng, chmod g-w có thể thay đổi ACL mask.

13. Setuid, Setgid executable và Sticky bit

  • Setuid executable: có thể làm effective UID khi thực thi lấy từ owner file nếu các điều kiện cho phép.
  • Setgid executable: tương tự với effective GID.
  • Sticky bit directory: giới hạn quyền unlink/rename entries của người khác, điển hình /tmp.
ls -ld /tmp
# drwxrwxrwt root root /tmp

mkdir -p /tmp/sticky-demo
chmod 1777 /tmp/sticky-demo
ls -ld /tmp/sticky-demo

Đừng sử dụng setuid executable chỉ để chữa một lỗi quyền thông thường: lỗi bảo mật trong chương trình có thể dẫn đến leo thang đặc quyền.

14. sudo, root và least privilege

sudo áp dụng chính sách cho phép thực thi lệnh với danh tính khác, thường là root. Nó không phải một permission bit của file.

sudo -u motorapp id
sudo -u motorapp test -r /var/lib/motor-controller/state.db

Root không tự động vượt qua mọi giới hạn: SELinux/AppArmor, read-only mount, seccomp và namespace có thể tiếp tục hạn chế. Một daemon chỉ cần đọc UART và ghi state không nên mặc định chạy root.

15. Linux capabilities

Capabilities chia một phần đặc quyền thành những đơn vị nhỏ hơn.

Capability Công dụng tiêu biểu
CAP_NET_BIND_SERVICE Bind privileged ports
CAP_NET_RAW Một số thao tác raw socket
CAP_CHOWN Thay ownership trong phạm vi cho phép
CAP_DAC_OVERRIDE Vượt qua nhiều kiểm tra DAC
CAP_SYS_ADMIN Tập hợp thao tác rất rộng, cần tránh cấp tùy tiện 
grep '^Cap' /proc/self/status
capsh --print
getcap /usr/local/bin/myserver
sudo setcap cap_net_bind_service=+ep /usr/local/bin/myserver

Việc cấp capability cho file phụ thuộc filesystem, mount flags, namespace và chính sách thực thi. Không xem capabilities là cách thay thế sudo trong mọi trường hợp.

16. Lab tổng hợp cộng tác

Chỉ chạy trong VM hoặc môi trường lab. Kiểm tra trước để tránh đụng tài khoản/đường dẫn có sẵn.

getent passwd labalice
getent group labteam
test -e /srv/linux-team-lab && echo 'Already exists'

sudo groupadd labteam
sudo useradd -m -s /bin/bash labalice
sudo usermod -aG labteam labalice
sudo install -d -o root -g labteam -m 2770 /srv/linux-team-lab

sudo -u labalice sh -c '
  umask 0002
  printf "hello\n" > /srv/linux-team-lab/note.txt
'
ls -l /srv/linux-team-lab/note.txt

Tạo lỗi có chủ đích:

sudo chmod 2700 /srv/linux-team-lab
sudo -u labalice cat /srv/linux-team-lab/note.txt
# Permission denied
sudo chmod 2770 /srv/linux-team-lab

Thử ACL mask: phải dùng named user khác owner để quan sát mask chính xác, vì owner entry không chịu ACL mask theo quy tắc của named user.

17. Debug Permission denied theo tầng

Một senior engineer không bắt đầu bằng chmod -R 777. Họ tìm syscall thất bại, pathname, credentials và tầng kiểm soát đang từ chối.

17.1. Danh tính:

id
systemctl show myapp.service -p User -p Group -p SupplementaryGroups

17.2. Kiểm tra file:

ls -l /var/lib/motor-controller/state.db
stat /var/lib/motor-controller/state.db
stat -c '%n %a %U:%G %F' /var/lib/motor-controller/state.db
stat -c 'UID=%u GID=%g MODE=%a' /var/lib/motor-controller/state.db

-rw-r----- root:motorapp cho phép group đọc nhưng không ghi. Tuy nhiên, nếu file chưa tồn tại và ứng dụng dùng O_CREAT, quyền trên directory cha mới là trọng tâm.

17.3. Kiểm tra toàn bộ pathname:

namei -l /var/lib/motor-controller/state.db

17.4. Kiểm tra ACL:

getfacl /var/lib/motor-controller/state.db

17.5. Mount/read-only:

findmnt -T /var/lib/motor-controller/state.db
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS

17.6. SELinux/AppArmor:

getenforce
sudo ausearch -m AVC,USER_AVC -ts recent
sudo aa-status
sudo journalctl -k

17.7. systemd sandbox:

systemctl cat motor-controller.service
systemctl show motor-controller.service -p ProtectSystem -p ProtectHome -p ReadWritePaths -p StateDirectory -p DynamicUser

17.8. Syscall và errno:

strace -f -e trace=%file ./motor-controller
# openat(..., O_WRONLY|O_CREAT, 0644) = -1 EACCES
Errno Ý nghĩa
EACCES Quyền truy cập bị từ chối
EPERM Thao tác không được phép
EROFS Filesystem read-only
ENOENT Không tìm thấy file/thành phần đường dẫn
ENOTDIR Thành phần đường dẫn không phải directory
ELOOP Vấn đề vòng lặp/giới hạn symlink

Câu hỏi phản biện: Root cũng không ghi được có chắc do SELinux? Không. Có thể do read-only mount, immutable attribute, AppArmor hoặc sandbox.

18. Các tình huống production

UART: /dev/ttyUSB0 có mode crw-rw---- root:dialout; kiểm tra id motorapp, group và udev.

File writable nhưng không xóa được: unlink phụ thuộc directory cha, sticky bit và chính sách khác.

Shell chạy được, systemd lỗi: kiểm tra ProtectSystem=strict, ReadWritePaths, StateDirectory, ProtectHome, credentials và mount namespace.

Readonly filesystem: chmod không giải quyết EROFS; cần sửa kiến trúc lưu dữ liệu hoặc mount configuration.

19. Case study Embedded Linux — BLDC motor controller

Ứng dụng cần mở UART, ghi trạng thái và phát log, nhưng không cần root toàn cục.

sudo useradd --system --home-dir /var/lib/motor-controller --shell /usr/sbin/nologin motorapp
sudo usermod -aG dialout motorapp

Ví dụ unit file (cần điều chỉnh cho distribution và group thực tế):

[Unit]
Description=BLDC Motor Controller
After=network.target

[Service]
Type=simple
User=motorapp
Group=motorapp
SupplementaryGroups=dialout
ExecStart=/usr/local/bin/motor-controller
StateDirectory=motor-controller
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
NoNewPrivileges=yes
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target

StateDirectory= quản lý directory dữ liệu. Với log, có thể sử dụng stdout/stderr và journald để giảm quản lý file riêng. Trên thiết bị nhúng, cân nhắc dung lượng flash và tần suất ghi log.

Không nên bật PrivateDevices=yes khi chương trình cần trực tiếp thấy /dev/ttyUSB0 nếu chưa có thiết kế cấp thiết bị phù hợp. Thiết bị USB có thể đổi tên sau khi cắm lại; nên xem xét udev stable symlink.

Bảo mật phần cứng: quyền truy cập motor controller có thể gây tác động vật lý, vì vậy group dialout cũng là một quyền đáng cân nhắc.

20. Các chủ đề liên quan

Container: UID/GID số và user namespace mapping quyết định quyền bind mount; username giống nhau không đảm bảo UID giống nhau.

NFS: ánh xạ danh tính, export policy và root squash ảnh hưởng quyền thực tế.

Immutable attribute: lsattr file.txt có thể cho biết thuộc tính làm hạn chế sửa/xóa, dù mode bits cho phép.

TOCTOU: kiểm tra access() rồi mới open() có thể tạo race nếu pathname thay đổi; cần ưu tiên thao tác an toàn trên file descriptor và các API phù hợp.

21. Tự kiểm tra kiến thức

  1. File 0666 nhưng không ghi được — tại sao? Có thể do directory cha, read-only mount, MAC, sandbox hoặc immutable attribute.
  2. User vừa được thêm group nhưng shell cũ vẫn bị từ chối — vì sao? Credentials của tiến trình cũ chưa đổi.
  3. Setgid directory có đảm bảo group-writable không? Không; còn requested mode, umask và default ACL.
  4. chmod g-w làm named ACL user mất quyền ghi — tại sao? ACL mask có thể thay đổi.
  5. Root có ghi được vào read-only filesystem không? Không tự động.
  6. Vì sao strace hữu ích? Vì nó cho biết syscall, pathname, flags và errno thực tế.

22. Checklist production

  • Service chạy bằng UID/GID đúng.
  • Supplementary groups đã áp dụng cho tiến trình mới.
  • Owner/group/mode của file đúng.
  • Từng directory cha cho phép search.
  • ACL và ACL mask đúng.
  • Filesystem và mount namespace cho phép thao tác.
  • SELinux/AppArmor không từ chối ngoài dự kiến.
  • systemd sandbox có ngoại lệ ghi cần thiết.
  • File không có immutable attribute gây cản trở.
  • Đã xác định syscall và errno.
  • Không sử dụng chmod -R 777 để chữa triệu chứng.
  • Có phương án rollback khi thay đổi ownership hoặc ACL.

23. Tổng kết và tài liệu tham khảo

Mô hình tư duy:

Access decision
  ├── Process credentials (UID/GID/groups)
  ├── Path traversal + file type + mode
  ├── ACL / capabilities
  ├── Mount / filesystem properties
  ├── MAC / sandbox / namespace
  └── Syscall semantics → Allow / Deny / Error

Đây là mô hình chẩn đoán, không phải thứ tự kiểm tra nội bộ cố định của kernel.

man 7 credentials
man 7 path_resolution
man 5 acl
man 7 capabilities
man 2 open
man 2 umask
man 5 systemd.exec

Nguyên tắc kết thúc: Đừng hỏi “chmod bao nhiêu để chạy được?”; hãy hỏi “syscall nào thất bại, trên đối tượng nào, với credentials nào, và tầng nào đã từ chối?”.

Phòng thí nghiệm tương tác — mô phỏng bằng JavaScript

Các mô phỏng sau chạy hoàn toàn trong trình duyệt, không thay đổi quyền trên máy tính của bạn.

1. Quyền owner / group / other

Thay đổi danh tính và quyền file để xem kết quả truy cập theo DAC truyền thống (không có ACL).

2. Quyền directory

Chọn quyền trên directory và thử thao tác. Mô phỏng giả định không có sticky bit, ACL hay MAC.

3. umask

Requested mode giả định: file 0666, directory 0777; không có default ACL.

4. ACL mask

Mask giới hạn quyền của named user entry (không phải owner entry).
