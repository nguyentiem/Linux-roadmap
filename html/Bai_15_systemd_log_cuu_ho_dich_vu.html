1. systemd quản lý gì, và systemctl đứng ở đâu?

Một chương trình chạy bằng terminal chưa phải dịch vụ có khả năng tự khởi động, giám sát, phục hồi và điều tra lỗi. Process là một lần thực thi chương trình có PID; daemon thường chạy nền; service là công việc được quản lý theo vòng đời. Kernel quản lý tài nguyên, còn systemd ở user space tổ chức các unit.

bash
ps -p 1 -o pid,comm,args
command -v systemctl
systemd --version
systemctl show -p Version

Có binary systemctl không chứng minh systemd là PID 1, đặc biệt trong container. Unit file là định nghĩa trên đĩa, unit mà manager đã nạp có trạng thái riêng.

Loại unitVai tròVí dụ
.serviceChạy ứng dụng hoặc công việcHTTP server
.socketĐiểm giao tiếp, có thể kích hoạt serviceSocket activation
.timerKích hoạt theo thời gianBackup mỗi ngày
.mountQuản lý mount/srv
.targetNhóm mục tiêumulti-user.target
.pathTheo dõi đường dẫnKích hoạt khi file thay đổi
💡 systemctl --user điều khiển user manager; lab này sử dụng system unit ở /etc/systemd/system và tài khoản linuxlab.

2. “Cần B” có giống “chạy sau B” không?

Dependency trả lời có kéo B vào giao dịch không; ordering trả lời nếu cả A và B cùng được lên lịch thì A có phải chờ B không. After=B không tự start B; Wants=B không tự buộc A chờ B; Requires=B kết hợp After=B ràng buộc chặt hơn.

Yêu cầu start A
↓
Wants / Requires = B
Kéo B vào giao dịch
After = B
Quy định thứ tự
Cấu hìnhKéo B vào?Chờ B?
After=BKhôngCó nếu B cùng được lên lịch
Wants=BCó, mềmKhông
Requires=BCó, chặt hơnKhông nếu thiếu After
Wants=B + After=BCóCó
Requires=B + After=BCóCó, và lỗi start B có thể chặn A
❓ Nếu network.target đã đạt, DNS và Internet có chắc hoạt động? Không. network-online.target cũng không bảo đảm server từ xa khỏe.
bash
systemctl show linux-lab-http.service -p Wants -p Requires -p After
systemctl list-dependencies linux-lab-http.service

4. Lab: tạo HTTP service cục bộ có danh tính riêng

HTTP là giao thức request/response. curl là client; Python http.server là server. Bind 127.0.0.1 chỉ lắng nghe loopback IPv4 trong network namespace hiện tại, không phải cơ chế xác thực. Cổng 8080 phân biệt endpoint.

💡 Chỉ thực hành trên VM lab, kiểm tra đối tượng đã tồn tại trước khi tạo. Python http.server chỉ phù hợp lab, không dùng làm web server production cho dữ liệu nhạy cảm.
bash
command -v python3
command -v curl
command -v nologin
python3 --version
getent passwd linuxlab
getent group linuxlab
systemctl cat linux-lab-http.service
ls -ld /srv/linux-lab-web
ss -ltn 'sport = :8080'

Nếu user, group, unit hoặc thư mục đã tồn tại, dừng và xác nhận nguồn gốc. Nếu cổng bị chiếm, chọn cổng khác và sửa đồng bộ unit lẫn URL curl.

bash
sudo useradd --system --user-group --no-create-home \
  --shell /usr/sbin/nologin linuxlab
getent passwd linuxlab
getent group linuxlab
sudo install -d -o root -g root -m 0755 /srv/linux-lab-web
printf 'Linux lab ready\n' | sudo tee /srv/linux-lab-web/index.html >/dev/null
sudo chmod 0644 /srv/linux-lab-web/index.html
ls -ld /srv/linux-lab-web
ls -l /srv/linux-lab-web/index.html

Quyền 0755 trên thư mục cho phép đi xuyên; 0644 trên file cho phép user linuxlab đọc nhưng không sửa. Với đường dẫn, quyền x trên mọi thư mục cha rất quan trọng. sudo tee ghi bằng quyền sudo, còn sudo echo > file không nâng quyền cho phép redirection của shell.

ini
[Unit]
Description=Linux course HTTP lab
After=network.target

[Service]
Type=simple
User=linuxlab
Group=linuxlab
WorkingDirectory=/srv/linux-lab-web
ExecStart=/usr/bin/python3 -m http.server 8080 --bind 127.0.0.1
Restart=on-failure
RestartSec=2s
NoNewPrivileges=yes
PrivateTmp=yes

[Install]
WantedBy=multi-user.target

Type=simple không đợi HTTP readiness. WorkingDirectory là cơ sở cho đường dẫn tương đối. ExecStart không tự chạy qua Bash, nên |, >, && không tự là cú pháp shell. Restart=on-failure không sửa lỗi cấu hình cố định. NoNewPrivileges giới hạn việc lấy thêm đặc quyền; PrivateTmp tách góc nhìn khu vực tạm, không cô lập toàn bộ filesystem.

systemctl start
↓
systemd: user, group, cwd, môi trường
↓
Python → bind 127.0.0.1:8080
↓
curl GET / → index.html → Linux lab ready
↘ journal: sự kiện và lỗi
bash
sudo systemd-analyze verify /etc/systemd/system/linux-lab-http.service
sudo systemctl daemon-reload
sudo systemctl enable --now linux-lab-http.service
systemctl is-enabled linux-lab-http.service
systemctl is-active linux-lab-http.service
systemctl status linux-lab-http.service --no-pager

journalctl -u linux-lab-http.service -b -n 30 --no-pager

Ba lớp kiểm chứng: enabled (chính sách kích hoạt), active và danh tính process (vòng đời), curl trả đúng nội dung (nghiệp vụ). HTTP 200 không đảm bảo nội dung đúng.

bash
pid=$(systemctl show linux-lab-http.service -p MainPID --value)
ps -p "$pid" -o pid,user,group,args

5. Lab lỗi CHDIR: tìm nguyên nhân trước khi restart

Drop-in là file bổ sung NAME.service.d/*.conf, được hợp nhất với unit chính. Thử sau khi service lab đã hoạt động. Xác nhận đường dẫn sai không tồn tại trước khi thử.

bash
sudo systemctl edit linux-lab-http.service
ini
[Service]
WorkingDirectory=/srv/linux-lab-does-not-exist
bash
sudo systemctl daemon-reload
sudo systemctl restart linux-lab-http.service
systemctl status linux-lab-http.service --no-pager
journalctl -u linux-lab-http.service -b -n 40 --no-pager
systemctl show linux-lab-http.service -p WorkingDirectory -p Result -p ExecMainCode -p ExecMainStatus -p NRestarts

Lỗi status=200/CHDIR là mã systemd cho bước đổi thư mục làm việc, hoàn toàn khác HTTP 200 OK. Trạng thái có thể đang activating (auto-restart) hoặc failed do rate limit. NRestarts không phải toàn bộ lịch sử từ lúc cài.

Chẩn đoán theo dấu hiệu

Dừng vòng thử, sửa drop-in về thư mục đúng, nạp lại, xác nhận cấu hình rồi start lại:

bash
sudo systemctl stop linux-lab-http.service
sudo systemctl edit linux-lab-http.service
# Đổi WorkingDirectory trở lại /srv/linux-lab-web
sudo systemctl daemon-reload
systemctl cat linux-lab-http.service
systemctl show linux-lab-http.service -p WorkingDirectory
sudo systemctl reset-failed linux-lab-http.service
sudo systemctl start linux-lab-http.service
curl --fail http://127.0.0.1:8080/
❓ Vì sao reset-failed không phải sửa lỗi? Vì nó chỉ xóa trạng thái và bộ đếm; đường dẫn sai vẫn sai.

6. Đọc log: từ trạng thái đến lịch sử sự kiện

Một service có thể crash lúc 10:00, được systemd restart lúc 10:00:02 và active khi kỹ sư kiểm tra lúc 10:05. Status hiện tại không kể hết lịch sử. Journal lưu các sự kiện và metadata, journalctl truy vấn chúng.

bash
journalctl -u linux-lab-http.service
journalctl -u linux-lab-http.service -b
journalctl -u linux-lab-http.service -b -n 30 --no-pager
journalctl -u linux-lab-http.service -f
journalctl -u linux-lab-http.service --since "2026-10-11 14:20:00" --until "2026-10-11 14:40:00"
journalctl -u linux-lab-http.service -p warning -b
journalctl -u linux-lab-http.service -n 5 -o verbose

Các trường verbose có thể gồm _BOOT_ID, _SYSTEMD_UNIT, _PID, _UID, _GID, _COMM, MESSAGE. Không có dòng GET 200 không chứng minh server chưa chạy; có thể chưa có request, không đủ quyền đọc hoặc log được cấu hình khác. Chỉ grep error có thể bỏ qua failed, timeout, denied, exception và các dòng ngữ cảnh.

7. Log sau reboot: volatile, persistent và retention

Journal có thể lưu ở /run/log/journal (thường volatile) hoặc /var/log/journal (thường persistent). Storage=auto phụ thuộc điều kiện, đặc biệt thư mục persistent. Persistent không đồng nghĩa giữ mãi hoặc giữ được mọi dòng trước mất điện.

bash
journalctl --list-boots --no-pager
journalctl -b -1 -n 50 --no-pager
journalctl --disk-usage
systemd-analyze cat-config systemd/journald.conf
ls -ld /run/log/journal /var/log/journal
StorageÝ nghĩa
volatileLưu runtime
persistentLưu bền vững khi có thể
autoTùy điều kiện thư mục và cấu hình
noneKhông lưu vào journal files
ini
[Journal]
Storage=auto
SystemMaxUse=200M
SystemKeepFree=500M
MaxRetentionSec=1month

Các giá trị giới hạn là ví dụ, không phải khuyến nghị chung. Embedded Linux dùng SD/eMMC cần cân nhắc ghi flash, dung lượng, mức log và dữ liệu nhạy cảm. Ví dụ 100 bản ghi/giây tạo 8.640.000 bản ghi/ngày; giả sử 200 byte/bản ghi thì khoảng 1,728 GB/ngày dữ liệu logic.

❓ Không có journal boot trước nghĩa là boot trước không lỗi? Không. Dữ liệu có thể chưa ghi được hoặc đã bị xóa. Kernel panic và mất nguồn có thể cần serial console, pstore, kdump hoặc thông tin watchdog/reset reason tùy nền tảng.

8. Phân tích boot chậm bằng systemd-analyze

Thời gian từ cấp nguồn đến ứng dụng sẵn sàng gồm firmware, bootloader, kernel, init và startup ứng dụng. systemd-analyze không nhất thiết đo toàn bộ chuỗi trên mọi nền tảng.

bash
systemd-analyze time
systemd-analyze blame
systemd-analyze critical-chain
systemd-analyze critical-chain linux-lab-http.service

Blame xếp thời gian kích hoạt, không tự chỉ ra nguyên nhân boot chậm. Các unit có thể chạy song song. Nếu A=15s, B=10s, C=8s cùng khởi động độc lập, thời gian không phải 33s mà gần 15s trong mô hình lý tưởng.

A15s
B10s
C8s

Critical-chain hiển thị chuỗi ordering ảnh hưởng mốc, nhưng Type=simple có thể được coi started trước khi ứng dụng ready. Đo readiness bằng curl hoặc endpoint /ready; không xóa service chậm nếu chưa hiểu yêu cầu dependency.

❓ network-online.target đạt có bảo đảm server từ xa sẵn sàng? Không; cần timeout, retry, backoff và health check ở ứng dụng.

9. Rescue mode, emergency mode và initramfs

Rescue mode là môi trường sửa chữa hạn chế; emergency mode tối thiểu hơn. Console trực tiếp/VM rất quan trọng vì SSH có thể không hoạt động. Initramfs shell có thể xuất hiện trước khi root filesystem thật được chuẩn bị, khác emergency shell của systemd sau switch-root.

Chế độMục tiêuLưu ý

initramfs shellChuẩn bị root filesystem thật/ có thể là root tạm
💡 Không thử systemctl isolate rescue.target hoặc emergency.target trên máy production/SSH; có thể dừng dịch vụ và mất phiên. Dùng VM snapshot và console.

journalctl -b -p warning --no-pager

10. fstab, UUID, mount và fsck: cứu hộ có bằng chứng

fstab mô tả nguồn, mount point, loại filesystem và lựa chọn. UUID giúp giảm phụ thuộc vào tên /dev/sdX biến đổi, nhưng UUID có thể bị trùng hoặc trỏ nhầm sau khi clone image.

fstab
UUID=1234-ABCD /data ext4 defaults 0 2

Nếu fstab tham chiếu UUID=OLD và journal báo timed out waiting for device, dùng lsblk -f để đối chiếu. Không tự thay bằng UUID đầu tiên trong danh sách: phải xác minh đúng thiết bị và dữ liệu. findmnt --verify kiểm tra khai báo/khả dụng theo công cụ, không kiểm tra tính toàn vẹn filesystem.

bash
lsblk -f
findmnt -T /srv/linux-lab-web
findmnt --verify --verbose
cat /etc/fstab
💡 Không chạy mount -a mù quáng vì có thể thay đổi nhiều mount point. Không chạy fsck ở chế độ sửa trên filesystem đang mounted; root chỉ đọc vẫn là mounted. Xác nhận loại filesystem, đúng device, backup và môi trường unmounted phù hợp. XFS có quy trình riêng, không dùng e2fsck cho mọi loại.
❓ Nếu lỗi chỉ là UUID sai trong fstab, fsck có sửa được không? Không. Công cụ sửa cấu trúc filesystem không chữa đường dẫn nguồn trỏ sai.

11. Systemd timer và cron: chạy việc đúng thời điểm

Cron chạy lệnh theo lịch và môi trường cron. Systemd timer kích hoạt unit, thường là service, nên tận dụng status, journal và dependency. Không cấu hình cron và timer trùng backup nếu chưa có khóa chống trùng.

Tiêu chíCronSystemd timer
Cấu hìnhCrontabTimer + service
Lịch ngày giờCóOnCalendar
Thời gian tương đốiTùy cách triển khaiOnActiveSec và các monotonic timer
Trạng thái/logCần tổ chức thêmTích hợp unit/journal

[Unit]

[Service]

[Unit]

Tạo hai file /etc/systemd/system/linux-lab-tick.service và .timer sau khi kiểm tra tên. OnActiveSec đo từ lúc timer kích hoạt; AccuracySec là dung sai, không bảo đảm chính xác tuyệt đối. Oneshot có thể inactive sau khi hoàn tất thành công.

bash
sudo systemd-analyze verify /etc/systemd/system/linux-lab-tick.service /etc/systemd/system/linux-lab-tick.timer
sudo systemctl daemon-reload
sudo systemctl start linux-lab-tick.timer
systemctl list-timers --all linux-lab-tick.timer --no-pager
# Sau khoảng 10–12 giây:
journalctl -u linux-lab-tick.service -b -n 10 --no-pager
systemctl show linux-lab-tick.service -p Result -p ExecMainStatus

Lịch calendar ví dụ mỗi ngày 03:00:

ini
OnCalendar=*-*-* 03:00:00
Persistent=true
bash
systemd-analyze calendar '*-*-* 03:00:00'

Persistent=true có thể chạy bù một lần nếu bỏ lỡ calendar timer, không chạy riêng từng kỳ đã bỏ lỡ. Timezone và DST ảnh hưởng lịch. Timer không tự tạo instance song song mới của unit đang active; vẫn phải cân nhắc khóa nếu nhiều cơ chế cùng gọi công việc.

bash
sudo systemctl stop linux-lab-tick.timer linux-lab-tick.service
# Chỉ xóa nếu chính bạn tạo hai file:
sudo rm -- /etc/systemd/system/linux-lab-tick.timer /etc/systemd/system/linux-lab-tick.service
sudo systemctl daemon-reload

12. Thiết kế service production trên Embedded Linux

Một SBC có thể có sensor reader, CAN communication, data logger, HTTP API và remote monitoring. Không mặc định mỗi chức năng cần một process; chọn ranh giới theo cô lập lỗi, giao tiếp, hiệu năng và bảo trì. Áp dụng least privilege: mỗi service chỉ được cấp quyền device node, file và network cần thiết.

SocketCAN là network interface của Linux nhưng network-online.target không bảo đảm can0 đã được cấu hình bitrate, đưa lên và bus sẵn sàng. Kiểm tra:

bash
ip link show can0
ls -l /dev/ttyUSB0
id linuxlab

Nếu thiết bị serial thuộc group dialout, có thể xem xét SupplementaryGroups=dialout sau khi xác nhận chính sách và quyền thực tế. Không chuyển mọi service sang root chỉ để vượt một lỗi permission.

ini
[Service]
Restart=on-failure
RestartSec=2s
# Ví dụ nâng cao, chỉ dùng khi ứng dụng hỗ trợ notify:
# Type=notify
# WatchdogSec=30s

Restart không chữa process treo nhưng vẫn sống, trả dữ liệu sai, filesystem đầy hoặc cấu hình sai cố định. Watchdog có thể phát hiện thiếu heartbeat nếu ứng dụng thực sự hỗ trợ và heartbeat phản ánh sức khỏe nghiệp vụ.

13. Dọn lab và các lỗi thường gặp

Nếu còn học networking, bảo mật, system call hoặc performance, nên giữ HTTP lab. Nếu dọn, disable/stop trước, kiểm tra unit/drop-in, process và tài khoản; chỉ xóa file do bạn tạo.

bash
sudo systemctl disable --now linux-lab-http.service
systemctl cat linux-lab-http.service
ps -u linuxlab
