Bài 14 — Toàn bộ quá trình Boot và Shutdown trong Linux

Từ lúc nhấn nút nguồn đến khi Linux sẵn sàng chạy ứng dụng — và chiều ngược lại khi shutdown. Giải thích theo tư duy kỹ sư Embedded Linux: vai trò, lý do tồn tại, lỗi thường gặp và cách khoanh vùng.

Bắt đầu học ↓

1. Đặt vấn đề: Ai chạy chương trình đầu tiên khi bật nguồn?

Khi máy đang chạy, kernel quản lý CPU, RAM, driver và process; scheduler chọn task; filesystem đọc/ghi dữ liệu; systemd quản lý service; shell thực thi lệnh. Nhưng nếu tất cả chưa chạy, ai khởi động chúng?

c
int main(void)
{
    printf("Hello Linux\n");
    return 0;
}

Để chạy chương trình C cần hệ điều hành hỗ trợ executable, process và system call. Nhưng ai nạp kernel vào RAM? Ai truy cập ổ đĩa khi driver chưa chạy? Ai khởi tạo phần cứng?

1.1. Boot là gì?

Boot (bootstrap) là quá trình đưa hệ thống từ trạng thái chưa có hệ điều hành đang chạy đến trạng thái hệ điều hành và các dịch vụ cần thiết đã sẵn sàng. Đây là quá trình hệ thống tự xây dựng môi trường để vận hành.

Nghịch lý: muốn chạy chương trình cần môi trường thực thi, nhưng muốn tạo môi trường thực thi lại phải chạy một chương trình trước đó. Giải pháp: chia thành nhiều giai đoạn, mỗi giai đoạn chuẩn bị cho giai đoạn tiếp theo.

1.2. Ví dụ đời sống: Mở cửa nhà máy

Bảo vệ mở cổng → kỹ thuật viên bật điện → vận hành máy móc → quản lý phân công → dây chuyền sản xuất. Không thể yêu cầu công nhân chạy máy khi chưa có điện. Linux cũng cần chuỗi khởi động có thứ tự.

1.3. Sơ đồ tổng quan Linux Boot Process

Câu hỏi phản biện: Có phải mọi máy Linux đều đi qua đủ bảy giai đoạn? Không. Thiết bị nhúng có thể dùng U-Boot thay GRUB; có thể boot không initramfs; có thể dùng init khác systemd. Hãy hiểu vai trò logic, không học thuộc tên chương trình.

2. CPU làm gì sau Reset?

2.1. CPU không tự biết Linux ở đâu

CPU lặp chu trình fetch → decode → execute → cập nhật Program Counter → fetch. Khi bật nguồn, điểm bắt đầu thực thi phụ thuộc kiến trúc CPU và SoC, thường gọi là reset vector hoặc reset entry.

text
Fetch instruction
      ↓
Decode instruction
      ↓
Execute instruction
      ↓
Update program counter
      ↓
Fetch next instruction
  • Cortex-M: vector table chứa stack pointer ban đầu và địa chỉ Reset_Handler.
  • x86 truyền thống: CPU bắt đầu tại địa chỉ reset do kiến trúc quy định, dẫn vào firmware.
  • Nhiều ARM SoC: Boot ROM thực thi trước để tìm và nạp stage tiếp theo.

2.2. Liên hệ STM32

c
void Reset_Handler(void)
{
    SystemInit();
    /* Initialize .data and .bss */
    __libc_init_array();
    main();
    while (1) {}
}

Ví dụ đơn giản hóa: Cortex-M đọc vector table rồi chạy Reset_Handler để chuẩn bị môi trường C và gọi main(). Linux có gọi main() ngay sau reset? Không. Hệ thống Linux thường phải trải qua nhiều stage để chuẩn bị RAM, phần cứng và kernel.

2.3. Boot ROM là gì?

Boot ROM là chương trình do nhà sản xuất SoC cung cấp, thường nằm trong ROM hoặc vùng chỉ đọc trong chip. Nó có thể đọc boot strap, chọn SD/eMMC/SPI flash, nạp stage tiếp theo, xác minh chữ ký nếu nền tảng hỗ trợ.

Power On
   ↓
CPU Reset
   ↓
Internal Boot ROM
   ↓
Read boot configuration
   ↓
Find boot image on eMMC
   ↓
Load next-stage firmware

Tại sao Boot ROM không nạp thẳng Linux? ROM nhỏ và ít linh hoạt; kernel cần DRAM, boot arguments, Device Tree và nhiều driver. ROM thường chỉ làm việc tối thiểu.

3. Firmware: BIOS và UEFI khác nhau thế nào?

3.1. Firmware là gì?

Firmware là phần mềm gắn với nền tảng phần cứng, thường lưu trong flash không mất dữ liệu. Nó có thể khởi tạo RAM, CPU/chipset, khám phá thiết bị, chọn boot entry và chuyển quyền thực thi. BIOS và UEFI là hai cơ chế firmware phổ biến trên PC.

3.2. Legacy BIOS

BIOS Firmware
     ↓
Boot sector / MBR boot code
     ↓
GRUB và các stage liên quan
     ↓
Linux Kernel

MBR truyền thống là sector 512 byte; thường có 446 byte vùng boot code, tiếp theo là bảng phân vùng và chữ ký. Quá nhỏ để chứa GRUB đầy đủ nên mã đầu phải chuyển sang stage khác.

3.3. UEFI

UEFI Firmware
     ↓
EFI System Partition (ESP)
     ↓
EFI executable
     ↓
GRUB / EFI stub / UKI
     ↓
Linux Kernel
text
EFI/
├── BOOT/
│   └── BOOTX64.EFI
└── ubuntu/
    ├── shimx64.efi
    └── grubx64.efi

Đây là ví dụ Ubuntu x86-64. Đường dẫn thực tế phụ thuộc kiến trúc, distro và Secure Boot.

3.4. So sánh BIOS và UEFI

GPT không chỉ dành cho UEFI, MBR cũng không tuyệt đối chỉ dành cho BIOS. Dùng UEFI có bắt buộc GRUB? Không: có thể nạp kernel EFI stub hoặc UKI.

4. Bootloader: Tại sao cần GRUB hoặc U-Boot?

4.1. Định nghĩa

Firmware giống người mở cửa kho; bootloader là người chọn đúng kiện hàng, chuẩn bị thông tin và giao nó đến nơi cần dùng. Bootloader có thể chọn kernel, nạp kernel/initramfs, truyền command line, cung cấp Device Tree và chuyển quyền thực thi.

4.2. GRUB trên PC

text
GNU GRUB

Ubuntu
Advanced options for Ubuntu
UEFI Firmware Settings
grub
menuentry "Linux" {
    linux /boot/vmlinuz root=UUID=xxxx ro quiet
    initrd /boot/initrd.img
}

linux chọn kernel; root= định danh root; ro yêu cầu mount read-only ban đầu; quiet giảm thông báo; initrd chọn image initramfs. Đây là ví dụ minh họa.

4.3. U-Boot trên Embedded Linux

Boot ROM
   ↓
SPL / early firmware
   ↓
U-Boot
   ↓
Linux kernel + DTB + optional initramfs
   ↓
Linux userspace

SPL (Secondary Program Loader) thường chạy trong SRAM nội bộ nhỏ, khởi tạo DRAM rồi nạp U-Boot đầy đủ. Nếu DRAM chưa sẵn sàng, bootloader lớn chưa thể dùng nó.

4.4. ODROID XU4

ODROID XU4 dùng Samsung Exynos 5422. Chuỗi điển hình có thể bao gồm:

Exynos Boot ROM
       ↓
BL1
       ↓
BL2
       ↓
U-Boot
       ↓
Linux Kernel + Device Tree
       ↓
Root filesystem
       ↓
Init / systemd

Các boot stage và cách đóng gói tùy image. Không phải mọi stage nằm trong partition mà ls nhìn thấy: một số nằm ở sector/vùng lưu trữ đặc biệt. Chỉ copy kernel Image vào SD/eMMC chưa đủ đảm bảo boot.

4.5. Kernel command line

bash
cat /proc/cmdline
text

Tham sốCông dụng

Tại sao cần root=? Một máy có thể có Windows, Linux, backup, EFI trên nhiều phân vùng; kernel/initramfs cần biết root nào là mong muốn.

5. Kernel khởi động như thế nào?

5.1. Kernel image

Kernel image là mã kernel build cho kiến trúc và định dạng boot cụ thể. Các tên thường gặp: vmlinuz, bzImage, Image, zImage, uImage, fitImage. Chúng không hoàn toàn tương đương; chẳng hạn uImage là định dạng legacy U-Boot có header.

5.2. Kernel initialization

Kernel entry
    ↓
Architecture-specific setup
    ↓
Memory management
    ↓
Interrupt / timer initialization
    ↓
Scheduler initialization
    ↓
Driver and subsystem initialization
    ↓
Root filesystem preparation
    ↓
Start first userspace program

Đây là thứ tự logic, không phải thứ tự chính xác mọi hàm. Trong source Linux, start_kernel() là một hàm khởi tạo trung tâm:

c
asmlinkage __visible void __init start_kernel(void)
{
    /* Many architecture and kernel initialization steps */
}

5.3. Vì sao scheduler phải khởi tạo sớm?

Scheduler cần runqueue, timer, cấu trúc task, cơ chế context switch để điều phối nhiều task. Giống công ty phải lập bộ phận phân công trước khi cho hàng trăm nhân viên hoạt động.

5.4. Vì sao cần memory management?

Kernel phải thiết lập physical/virtual memory, page table, mapping, allocator và cache. Không thể tùy tiện gọi malloc() của libc khi kernel còn đang tự khởi tạo.

5.5. Device Tree trên ARM

dts
uart0: serial@10000000 {
    compatible = "vendor,soc-uart";
    reg = <0x10000000 0x1000>;
    status = "okay";
};

Ví dụ giả định, không phải địa chỉ UART ODROID XU4. Device Tree mô tả địa chỉ thanh ghi, interrupt, clock, GPIO, trạng thái và quan hệ thiết bị. Tách mô tả phần cứng khỏi logic driver; PC thường dùng ACPI và cơ chế khám phá như PCI.

6. Initramfs: Vì sao Linux cần root filesystem tạm?

Kernel muốn mount root từ ổ đĩa nhưng driver storage có thể nằm ngay trong root chưa mount được. Vậy lấy driver ở đâu? Initramfs giải quyết một phần bài toán con gà và quả trứng này.

6.1. Initramfs là gì?

Initramfs (initial RAM filesystem) là filesystem ban đầu, thường đóng gói dạng archive cpio có thể nén, chứa chương trình và công cụ cho early userspace.

text
initramfs/
├── init
├── bin/
├── sbin/
├── lib/
├── etc/
└── usr/

6.2. Ổ đĩa mã hóa LUKS

SSD
 └── LUKS encrypted partition
       └── ext4 root filesystem

Để mount ext4 bên trong LUKS, hệ thống phải tìm device, nạp thành phần, mở khóa, tạo block device đã giải mã rồi mount root. Công cụ cryptsetup có thể nằm trong initramfs.

Kernel
   ↓
Initramfs → /init
   ↓
Find encrypted disk
   ↓
Unlock LUKS
   ↓
Mount real root filesystem
   ↓
Switch to real root
   ↓
Start real init

6.3. RAID và LVM

/dev/sda2 ─┐
           ├── LVM volume group
/dev/sdb2 ─┘       ↓
                Logical volume
                    ↓
                 ext4 root

Nếu root trên LVM, initramfs có thể kích hoạt volume trước khi mount. LVM không mặc định ghép hai physical volume theo kiểu RAID; hình chỉ mô tả các tầng.

6.4. Initramfs khác /boot?

Thành phầnVai trò
/bootThường lưu kernel, initramfs image và boot files
InitramfsFilesystem ban đầu trong early userspace
/Root filesystem của hệ thống đang chạy
ESPPartition chứa EFI executable trên UEFI

/boot/initrd.img-6.x là file image trên storage; khi boot, kernel sử dụng nội dung image tạo môi trường rootfs ban đầu trong RAM. Không nên hiểu /boot chính là initramfs.

6.5. Có bắt buộc initramfs?

Kernel
  ↓
Built-in MMC driver
  ↓
Built-in ext4 support
  ↓
Mount root from eMMC
  ↓
Start /sbin/init

Không. Nếu driver storage và filesystem cần thiết đã built-in và root truy cập trực tiếp được, có thể boot không initramfs. Distro vẫn thường dùng để hỗ trợ nhiều phần cứng, encryption và storage.

7. Chuyển từ initramfs sang root thực

7.1. Root filesystem là gì?

text
/
├── bin
├── boot
├── dev
├── etc
├── home
├── proc
├── sys
├── usr
└── var

Root filesystem là filesystem được mount tại / trong mount namespace liên quan. Nó chứa ứng dụng, thư viện, cấu hình và dữ liệu. Một số hệ thống có thể dùng RAM root mãi mãi, nhưng distro thông thường chuyển sang root trên storage.

7.2. switch_root

Initial rootfs
    /
    ├── init
    └── ...
         ↓
Mount real root at /newroot
         ↓
switch_root
         ↓
Real root becomes /
         ↓
exec /sbin/init

switch_root không đơn giản là chroot: chroot thay đổi cách một process phân giải đường dẫn root, không tự hoàn tất việc thay root của boot.

7.3. PID 1 có bị thay thế?

c
execl("/sbin/init", "init", (char *)NULL);

Trong đường boot mà /init đang là PID 1 và exec init thực, PID vẫn là 1. fork() tạo process mới; execve() thay program image trong process hiện tại. Không có hai PID 1 được tạo theo cách này.

8. PID 1: Process đặc biệt nhất trong user space

8.1. PID 1 là gì?

Kernel và root đã sẵn sàng nhưng mạng, SSH, database, desktop và ứng dụng chính có thể chưa chạy. Init system điều phối các việc đó; trên nhiều distro hiện đại là systemd.

bash
ps -p 1 -o pid,comm,args
text
PID  COMMAND  COMMAND
1    systemd  /sbin/init

8.2. PID 1 đặc biệt ở đâu?

  • Khởi động và theo dõi service.
  • Quản lý dependency và target.
  • Thu nhận trạng thái kết thúc của các process con được nhận nuôi.
  • Điều phối shutdown và có các quy tắc signal đặc biệt.

9.1. Target là gì?

Target là systemd unit dùng để nhóm hoặc đồng bộ các unit khác, giống cột mốc vận hành: hệ thống cơ bản, nhiều người dùng, hoặc đồ họa.

11. Shutdown: Điều gì xảy ra khi poweroff?

11.1. Shutdown là gì?

Shutdown đưa hệ thống đang hoạt động sang trạng thái dừng có kiểm soát: ngăn công việc mới, cho ứng dụng kết thúc, dừng service, xử lý process, sync/unmount filesystem và yêu cầu kernel poweroff/reboot.

11.2. Luồng shutdown

11.3. SIGTERM và SIGKILL

systemd
   ↓
SIGTERM
   ↓
Application cleanup
   ↓
Exit

Nếu không kết thúc theo timeout/policy:
SIGTERM → Timeout → SIGKILL

SIGTERM có thể được ứng dụng xử lý; SIGKILL không thể bị bắt hoặc bỏ qua theo cách xử lý signal thông thường.

c
#include <signal.h>
#include <unistd.h>

static volatile sig_atomic_t running = 1;

static void handle_term(int sig)
{
    (void)sig;
    running = 0;
}

int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = handle_term;
    sigaction(SIGTERM, &sa, NULL);

    while (running) {
        /* Do work */
        sleep(1);
    }

    /* Perform cleanup outside signal handler */
    return 0;
}

Production cần xử lý lỗi system call, race condition và cơ chế wake-up phù hợp; signal handler nên làm việc tối thiểu.

11.4. Vì sao phải sync?

c
write(fd, buffer, size);
fsync(fd);

write() thành công không đồng nghĩa dữ liệu đã bền vững trên storage: có thể còn trong page cache. fsync() yêu cầu đồng bộ file. Khi tạo file tạm rồi rename, có thể phải sync cả file và directory. Durability vẫn phụ thuộc filesystem, driver và thiết bị.

11.5. Journaling có cứu mọi dữ liệu?

Transfer 1,000,000 VND
Account A → Account B
      ↓
Power loss before commit?

Không. Journaling hỗ trợ tính nhất quán filesystem, không đảm bảo mọi transaction ứng dụng chưa commit. Database cần transaction log/recovery riêng. Thiết bị nhúng đặc biệt cần tính đến power loss, nguồn không ổn định, UPS và storage.

-b chọn boot hiện tại, -k chọn kernel, --no-pager không mở pager, head lấy 60 dòng. Trong shell có pipefail, head đóng pipe sớm có thể gây SIGPIPE cho producer. Warning không luôn là lỗi gây boot failure.

  • Boot theo hướng dẫn GRUB, quan sát log, reboot để trở về mặc định.

Kiểm tra root=, thời điểm root device xuất hiện, driver storage, hỗ trợ filesystem, initramfs và boot image. Nếu kernel đã chạy, cài lại GRUB không phải bước đầu tiên hợp lý.

fstab

Mount bắt buộc trong fstab sai UUID có thể ảnh hưởng boot. nofail đôi khi phù hợp cho mount không quan trọng, nhưng không nên dùng để che lỗi storage.

Có thể do binary mất, ExecStart sai, thiếu thư viện, permission, /dev chưa sẵn sàng, dependency lỗi hoặc app crash. Đây là tầng service/application, không nên cài lại GRUB.

14. Mô phỏng tương tác: Boot dừng ở đâu?

Chọn giai đoạn gặp lỗi để xem triệu chứng, kiểm tra và lý do ưu tiên điều tra.

15. Câu hỏi phản biện thường gặp

Linux có chạy không GRUB?

Có. Kernel có thể được nạp qua U-Boot, EFI stub, UKI hoặc boot mechanism khác.

Linux có chạy không initramfs?

Có, nếu kernel và đường root có đủ driver và hỗ trợ cần thiết.

Linux có chạy không systemd?

Có. Có thể dùng SysV init, OpenRC hoặc BusyBox init.

/boot có phải root filesystem?

Không. /boot là thư mục chứa boot files, có thể nằm trong root hoặc partition riêng.

Kernel có phải PID 1?

Không. PID 1 là userspace init trong PID namespace ban đầu.

blame xác định chính xác thủ phạm boot chậm?

Không. Cần xem critical chain, dependency và readiness.

Secure Boot mã hóa ổ đĩa?

Không. Nó xác minh chuỗi tin cậy; mã hóa ổ đĩa như LUKS là cơ chế khác.

Kernel panic luôn là kernel bug?

Không. Có thể do config, root device, driver, phần cứng hoặc lỗi nghiêm trọng khác.

18. Tổng kết theo tư duy hệ thống

Ba câu hỏi quan trọng: (1) Ai đang điều khiển: Boot ROM, firmware, bootloader, kernel, initramfs hay PID 1? (2) Giai đoạn này chuẩn bị gì cho giai đoạn sau? (3) Bằng chứng nào cho thấy nó thành công hay thất bại?

Hardware → Firmware → Bootloader → Kernel
        → Root filesystem → Init → Services → Application

Boot là chuỗi chuyển giao trách nhiệm. Mỗi giai đoạn nhận môi trường chưa hoàn chỉnh, bổ sung khả năng mới và chuyển quyền cho giai đoạn sau.

Tài liệu đọc tiếp

  • man bootup — các giai đoạn boot trong hệ thống systemd.
  • man kernel-command-line — tham số kernel và userspace.
  • man systemd-analyze — phân tích startup.
  • Linux Kernel: ramfs, rootfs và initramfs.
  • systemd bootup documentation.
Điểm cốt lõi: Khi Linux không boot, đừng hỏi “phải cài lại cái gì?”. Hãy hỏi “Giai đoạn cuối cùng đã hoạt động thành công là giai đoạn nào?” — từ đó chọn debug firmware, bootloader, kernel, root filesystem hay service.
