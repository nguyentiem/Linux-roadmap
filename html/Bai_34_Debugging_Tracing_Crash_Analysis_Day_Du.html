1. Đặt vấn đề: Debugging trên Embedded Linux

Một thiết bị Linux nhận dữ liệu CAN, xử lý cảm biến, ghi log và gửi TCP. Sau năm giờ, dữ liệu ngừng gửi, đôi lúc ứng dụng crash hoặc CPU tăng 100%. Khởi động lại tạm thời giải quyết được triệu chứng nhưng chưa tìm được nguyên nhân.

CPU cao không luôn đồng nghĩa có lỗi; CPU thấp cũng không chứng minh ứng dụng hoạt động đúng. Một thread có thể bị deadlock hoặc chờ I/O mà gần như không sử dụng CPU.

Tư duy senior: mô tả triệu chứng → đưa ra giả thuyết → thu thập bằng chứng → kiểm chứng nguyên nhân → sửa lỗi và kiểm thử hồi quy.

2. Debugging, tracing, profiling và monitoring

Debugging kiểm tra trạng thái và nguyên nhân chương trình sai. Tracing ghi nhận chuỗi sự kiện theo thời gian. Profiling lấy mẫu hoặc đo để tìm nơi tiêu tốn tài nguyên. Monitoring theo dõi tình trạng hệ thống trong thời gian dài.

Ví dụ nhà hàng: debugging xem đơn hàng bị kẹt tại bước nào; tracing ghi lại lúc nhận đơn, nấu và giao; profiling tìm công đoạn chiếm nhiều công sức; monitoring theo dõi số đơn tồn và thời gian phục vụ.

Flame graph rộng có nghĩa có nhiều mẫu thuộc stack đó theo cách đo; không chứng minh một lần gọi hàm luôn chậm.

MonitoringTheo dõi latency và error rate

3. Từ source code đến CPU

Source C được compiler và linker chuyển thành ELF chứa machine code. Loader tạo process với virtual memory, threads, register và file descriptors. Debugger cần ánh xạ instruction address về function và source.

Symbol nhận diện các thực thể như function; DWARF debug information có thể chứa dòng source, kiểu dữ liệu, vị trí biến và thông tin unwind. Debug symbols phải khớp chính xác với bản build thực tế.

C 
int calculate(int x) { int y=x*2; return y; }
int main(void) { return calculate(10); }
bash 
gcc -Wall -Wextra -g -O0 main.c -o app
gcc -O2 -g -fno-omit-frame-pointer main.c -o app-release

4. Compiler optimization và debugging

-g bổ sung debug information; -O0 hạn chế tối ưu hóa để dễ theo dõi. Khi -O2, compiler có thể inline function, loại biến trung gian hoặc thay đổi stack shape. GDB có thể hiển thị <optimized out>.

Không nên dùng -O0 thay cho production build khi điều tra race hoặc timing. Cần giữ binary và symbols cùng build ID với chương trình gặp sự cố.

bash 
readelf -n ./app | grep -A2 "Build ID"
file ./app
objdump -d ./app | head

6. Lab GDB: SIGABRT có chủ đích

abort() phát SIGABRT. Đây là user-space process crash, không phải kernel panic. Backtrace có thể bắt đầu ở runtime/libc; phải tìm frame ứng dụng kích hoạt abort.

GDB frame numbering phụ thuộc phiên bản libc, kiến trúc và môi trường. Chọn frame có process_request thay vì mặc định frame #3.

C 
#include <stdlib.h>
static void process_request(int request_id) {
    if (request_id == 42) abort();
}
int main(void) { process_request(42); return 0; }
bash 
gcc -Wall -Wextra -g -O0 crash.c -o crash-lab
gdb -q ./crash-lab
gdb 
run
bt
frame 3
info args
info locals
print request_id
list
quit
Câu hỏi: tại sao frame #0 không nhất thiết là nguyên nhân gốc? Vì nó có thể chỉ là nơi signal được phát hoặc lỗi được phát hiện.

7. Breakpoint, step, next và finish

step đi vào function được gọi; next chạy qua function rồi dừng ở dòng tiếp theo; finish chạy đến khi frame hiện tại trả về. Ở code tối ưu hóa, ranh giới dòng source không luôn khớp instruction.

8. Stack, heap và kiểm tra memory

Stack chứa call frames và thường chứa dữ liệu local tùy compiler; heap quản lý cấp phát động; mappings còn có shared libraries và vùng mmap. ASLR làm địa chỉ thay đổi.

Sau free, pointer không còn quyền truy cập đối tượng. Use-after-free là undefined behavior, có thể chưa crash ngay. GDB hỗ trợ quan sát; AddressSanitizer hỗ trợ phát hiện truy cập sai khi xảy ra.

C 
#include <stdlib.h>
int main(void) { int *p=malloc(sizeof(int)); if(!p)return 1; *p=100; free(p); return *p; }
bash 
gcc -g -O1 -fsanitize=address -fno-omit-frame-pointer uaf.c -o uaf
./uaf
gdb 
print ptr
print *ptr
print &value
x/16xb ptr

fopen là API thư viện; glibc có thể gọi openat để yêu cầu kernel mở file. strace cho biết syscall và kết quả. EACCES có thể đến từ quyền Unix, ACL hoặc MAC policy; ENOENT gợi ý đường dẫn không tồn tại; EMFILE gợi ý process đạt giới hạn FD.

10. Lab strace: mở file không tồn tại

strace thường hiển thị cả syscall từ loader và runtime, không chỉ code bạn viết. Một lời gọi API cấp cao không nhất thiết tương ứng đúng một syscall.

C

#include <errno.h>
#include <string.h>
int main(void){ FILE *fp=fopen("/tmp/debug-lab/missing.txt","r"); if(!fp){fprintf(stderr,"fopen failed: %s\n",strerror(errno));return 1;} fclose(fp);return 0;}
bash 
gcc -Wall -Wextra -g file_debug.c -o file-debug

11. Attach strace và tìm thread chờ

-f theo dõi task liên quan, -tt ghi timestamp, -T ghi thời lượng syscall, -o ghi file. Một futex chờ lâu chưa chứng minh deadlock; có thể là condition variable chờ hợp lệ.

futex hỗ trợ cơ chế ngủ/đánh thức khi đồng bộ hóa cần đến kernel; trường hợp không tranh chấp, mutex có thể hoàn tất hoàn toàn ở user space.

bash 
sudo strace -p 1245
sudo strace -f -tt -T -o /tmp/service.strace -p 1245
ps -T -p 1245 -o pid,tid,stat,wchan:32,comm

12. perf stat: đo sự kiện CPU

perf stat có thể đếm task-clock, context switches, page faults, cycles, instructions và các hardware events tùy quyền/CPU. IPC = instructions / cycles; IPC thấp không đủ để kết luận code kém, vì còn memory stalls, dependencies, branch behavior và kiến trúc CPU.

bash 
perf stat -- timeout 3s python3 -c 'while True: pass'
text

13. perf record: CPU sampling

Sampling lấy mẫu vị trí CPU đang thực thi. Số mẫu tại một function giúp ước lượng phân bố CPU work, không phải thời lượng mỗi lần gọi. Python có thể cần công cụ bổ sung để nhìn đầy đủ call stack ở mức ngôn ngữ.

bash 
perf record -g -- timeout 3s python3 -c 'while True: pass'

14. On-CPU và Off-CPU

Một request có thể mất 1000ms nhưng chỉ dùng 300ms CPU, còn 700ms chờ I/O. CPU profiler không phản ánh đầy đủ off-CPU time. Off-CPU có thể bao gồm sleeping hoặc runnable nhưng chưa được CPU chọn.

Khi latency cao mà CPU thấp, hãy điều tra I/O, lock contention và scheduler latency trước khi tối ưu thuật toán.

15. ftrace, tracepoint và kernel tracing

ftrace là hạ tầng tracing trong kernel, hỗ trợ function tracing, function graph và các tracepoints tùy cấu hình. sched_switch ghi context switch; sched_wakeup ghi sự kiện đánh thức. Task được đánh thức chưa chắc đã chạy ngay.

Tracing có overhead, có thể làm thay đổi timing và che giấu race condition (Heisenbug). Đặc biệt cẩn trọng với production và real-time workloads.

bash 
findmnt -t tracefs
sudo ls /sys/kernel/tracing/events/sched
sudo cat /sys/kernel/tracing/available_events | grep sched_switch

16. Lab ftrace cơ bản

Chỉ thay đổi cấu hình tracing trên VM hoặc board lab riêng. Trước khi thao tác, kiểm tra trạng thái hiện tại vì tracing có thể được dùng chung. Trên một số hệ thống tracefs nằm tại /sys/kernel/debug/tracing.

bash 
sudo -i
cd /sys/kernel/tracing
cat current_tracer
cat tracing_on
cat events/sched/sched_switch/enable
echo 0 > tracing_on
echo nop > current_tracer
echo 0 > events/sched/sched_switch/enable
echo > trace
echo 1 > events/sched/sched_switch/enable
echo 1 > tracing_on
sleep 2
echo 0 > tracing_on
head -n 30 trace

17. eBPF và bpftrace

eBPF cho phép chạy logic được kernel kiểm soát tại những hook được hỗ trợ. Có thể lọc, đếm và tổng hợp sự kiện gần nguồn phát sinh thay vì xuất mọi dòng trace. Vẫn phải kiểm tra kernel version, permissions, verifier và overhead.

Ví dụ bpftrace sau đếm syscall openat theo comm và in mỗi 5 giây. comm không phải định danh duy nhất của process; dùng pid nếu cần phân biệt process.

bash 
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }
interval:s:5 { print(@); clear(@); }
'

18. Core dump và post-mortem debugging

Core dump ghi lại một phần trạng thái process tại thời điểm dump: register, stack, memory mappings và thông tin khác tùy chính sách. Không phải nhật ký đầy đủ lịch sử trước crash.

ulimit -c unlimited không bảo đảm file core xuất hiện ở thư mục hiện tại; còn phụ thuộc core_pattern, systemd-coredump, quyền và chính sách hệ thống. Core dump có thể chứa secrets và dữ liệu người dùng.

19. SIGSEGV và NULL pointer

Một dereference NULL pointer thường gây SIGSEGV trên Linux thông thường. Nhưng câu hỏi gốc không chỉ là dòng nào dereference, mà là vì sao pointer NULL. Kiểm tra hợp đồng API, khởi tạo, allocation failure và error handling.

int main(void){ struct Sensor *sensor=NULL; update_sensor(sensor); return 0; }

20. Stack corruption và lỗi bộ nhớ khó tìm

strcpy vào buffer quá nhỏ có thể ghi tràn stack. Backtrace có thể bị hỏng, và crash xuất hiện tại một function khác với nơi ghi sai. ASan hỗ trợ phát hiện; stack protector chỉ giúp phát hiện một số dạng corruption, không thay thế kiểm thử.

C 
#include <string.h>
void unsafe_copy(const char *src){char buffer[16];strcpy(buffer,src);}
bash 
gcc -g -O1 -fsanitize=address -fno-omit-frame-pointer overflow.c -o overflow

21. Kernel Oops, Panic và kdump

User-space SIGSEGV thường chỉ làm process kết thúc. Kernel Oops là báo cáo lỗi nghiêm trọng trong kernel, hệ thống có thể tiếp tục nhưng trạng thái có thể không còn tin cậy. Kernel panic thường khiến kernel dừng hoạt động bình thường.

Kdump chuẩn bị capture kernel và reserved memory để thu vmcore sau panic. Không thử gây panic trên host đang làm việc hoặc thiết bị điều khiển phần cứng thật.

22. Production case: CAN gateway treo

Gateway có ba thread: CAN reader, parser và TCP sender. CPU chỉ 2%, RAM 35%, process vẫn sống, interface CAN UP và TCP established. Điều này chưa chứng minh network khỏe hoặc ứng dụng đang xử lý dữ liệu.

Kiểm tra ps -T và all-thread backtrace có thể cho thấy CAN reader ở poll, parser ở condition wait và TCP worker chờ mutex. Cần tìm lock owner, các thao tác blocking và điều kiện đánh thức trước khi kết luận deadlock.

bash 
ps -eo pid,ppid,stat,etime,comm | grep gateway
ps -T -p 1245 -o pid,tid,stat,pcpu,wchan:32,comm
sudo gdb -q -p 1245
gdb 
set pagination off
info threads
thread apply all bt

23. Lock contention do blocking send()

Nếu một thread giữ queue_mutex rồi gọi blocking send(), các thread khác cần mutex phải chờ trong khi socket chưa sẵn sàng. Đây có thể là lock contention kéo dài, không nhất thiết deadlock vĩnh viễn.

Giải pháp kiến trúc: lấy hoặc sao chép dữ liệu dưới lock trong thời gian ngắn, unlock, rồi thực hiện I/O ngoài critical section. Cần xử lý partial writes, EINTR, EAGAIN và timeout.

C 
pthread_mutex_lock(&queue_mutex);
/* pop queue */
send(socket_fd, buffer, length, 0); /* có thể block */
pthread_mutex_unlock(&queue_mutex);
C 
void send_data(int fd) {
    struct Message msg;
    pthread_mutex_lock(&queue_mutex);
    bool ok = queue_pop_locked(&msg);
    pthread_mutex_unlock(&queue_mutex);
    if (ok) send_message_with_timeout(fd, &msg);
}

24. Race condition và Heisenbug

Hai thread cùng tăng counter++ không đồng bộ có thể tạo data race và undefined behavior trong C. Khi đặt breakpoint, timing thay đổi nên race có thể biến mất. ThreadSanitizer hỗ trợ phát hiện một số data races nhưng có overhead và giới hạn tương thích.

C 
int counter=0;
void *worker(void *arg){
    for(int i=0;i<100000;i++) counter++;
    return NULL;
}
bash 
gcc -g -O1 -fsanitize=thread -pthread race.c -o race

27. Tracing overhead và bảo mật

GDB dừng process; strace có thể làm syscall path chậm hơn; sanitizer thay đổi timing và memory layout; tracepoint tần suất cao tạo overhead. So sánh baseline, thu thập trong khoảng ngắn, lọc đúng event và không kết luận chỉ từ một mẫu.

Core/vmcore có thể chứa password, token, private key và payload. Cần giới hạn quyền, mã hóa, retention và kiểm soát nơi upload.

29. Câu hỏi phản biện và kiến thức mở rộng

Crash tại malloc chưa chắc malloc lỗi: heap có thể bị hỏng trước. CPU thấp nhưng latency cao cần xem off-CPU. futex wait không chứng minh deadlock. Core dump không ghi lại toàn bộ lịch sử. Debug symbols phải khớp build.

Công cụ học tiếp: gdbserver, addr2line, readelf, objdump, elfutils, perf sched, bpftrace/BCC, trace-cmd, KernelShark, ASan, TSan, Valgrind và crash utility.

Kiểm tra kiến thức

30. Checklist và kết nối Bài 35

Hãy thực hành được: đọc backtrace, xem frame và biến; phân biệt SIGABRT/SIGSEGV/kernel panic; dùng strace tìm errno; chạy perf hoặc giải thích giới hạn quyền; phân biệt On-CPU và Off-CPU; hiểu ftrace/eBPF, core/vmcore; phân tích một case lock/I/O.

Bài 35 tiếp tục với mutex, condition variable, deadlock, race condition và synchronization. Hai thread giữ hai lock theo thứ tự ngược nhau có thể tạo vòng chờ không thể tiến triển.
