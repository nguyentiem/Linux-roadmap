Bài 12 — Process, Thread và Signal trong Linux

Linux Internals · Operating System · Embedded Linux · Từ nền tảng đến tư duy Senior Engineer

Trong bài 11, chúng ta đã tìm hiểu cách Linux cài đặt chương trình, quản lý package và thư viện. Nhưng có một câu hỏi quan trọng: Một chương trình nằm trên ổ đĩa làm thế nào để trở thành thứ đang thực sự chạy trên CPU?

Process là môi trường thực thi được kernel quản lý, bao gồm không gian địa chỉ, tài nguyên và trạng thái thực thi của chương trình. Kernel theo dõi virtual memory, file descriptors, UID/GID, trạng thái thực thi, signal và quan hệ cha-con.

2.1. PID là gì?

PID (Process Identifier) là số định danh process tại một thời điểm. Trong Bash, $$ thường in PID shell; $BASHPID hữu ích khi cần PID Bash process thực thi trong một số trường hợp subshell.

echo $$
ps -ef
UID    PID   PPID CMD
root     1      0 /sbin/init
user  2100      1 sshd
user  2200   2100 bash
user  2300   2200 sleep 300

PID 2300 là sleep, PPID 2200 là Bash. PID 1 thường là init/systemd trên Linux thông thường.

2.2. Process cha và process con

Quan hệ cha-con cho phép parent tạo child để xử lý công việc và nhận thông tin kết thúc của child. Đây là nền tảng của fork(), execve(), wait().

3. Process và Thread — Vì sao cần hai khái niệm?

Robot Embedded Linux có thể đồng thời nhận cảm biến, tính toán điều khiển, gửi lệnh xuống MCU, ghi log và giao tiếp mạng. Nếu làm tuần tự, một tác vụ chậm có thể chặn các tác vụ khác.

3.1. Thread là gì?

Thread là luồng thực thi bên trong process, có trạng thái CPU và stack riêng nhưng chia sẻ nhiều tài nguyên với thread cùng process.

3.3. Race condition — Vấn đề nguy hiểm

counter++;

Phép tăng không nhất thiết nguyên tử: đọc giá trị, cộng 1, rồi ghi lại. Hai thread có thể cùng đọc 0 rồi cùng ghi 1, khiến mất một lần tăng.

BướcThread AThread B

2—Đọc 0

Kết quả = 1 thay vì 2. Trong C/C++, truy cập đồng thời không đồng bộ vào biến thường với ít nhất một thao tác ghi còn có thể là data race và undefined behavior. Giải pháp: mutex, atomic operations và cơ chế đồng bộ.

Phản biện: Tại sao không dùng process cho mọi thứ? Process cô lập tốt nhưng trao đổi dữ liệu thường cần IPC như pipe, socket, shared memory. Thread thuận tiện cho chia sẻ dữ liệu. Event loop/async I/O cũng là lựa chọn khi xử lý nhiều kết nối.

4. Scheduler thực sự lập lịch cái gì?

Linux scheduler lập lịch các task biểu diễn bằng task_struct. Nhiều thread trong một process có thể được chạy trên các CPU core khác nhau.

Mô phỏng scheduler: 4 thread trên 2 CPU core
CPU Core 0: Thread 1
CPU Core 1: Thread 2

Mô phỏng minh họa, không phải thuật toán scheduler thực tế.

Concurrency: nhiều công việc tiến triển xen kẽ. Parallelism: nhiều công việc thực thi thực sự cùng lúc trên các đơn vị xử lý khác nhau. Một CPU một core có thể quản lý 100 thread nhưng không thực thi 100 thread cùng một lúc trên core đó.

Context switch

Khi CPU chuyển task A sang B, kernel lưu/khôi phục trạng thái như registers, program counter, stack pointer, scheduling state và thông tin memory mapping khi cần. Context switch có chi phí CPU/cache/TLB; nhiều thread không mặc nhiên nhanh hơn.

5. fork() — Process được sinh ra như thế nào?

ls -l

Một mô hình Unix truyền thống: Bash gọi fork() tạo child, child gọi execve() để thay bằng chương trình ls, còn Bash vẫn tồn tại. Một số shell cũng có thể dùng posix_spawn().

5.1. fork() là gì?

fork() tạo process con. Cả cha và con tiếp tục từ sau lời gọi; parent nhận PID con, child nhận 0, lỗi trả -1 ở parent.

Nơi thực thiGiá trị fork()
ParentPID của child
Child0
Lỗi-1 trong parent
#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>

int main(void)
{
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }
    if (pid == 0) {
        printf("Child: PID=%ld\n", (long)getpid());
    } else {
        printf("Parent: PID=%ld, Child=%ld\n", (long)getpid(), (long)pid);
    }
    return 0;
}
gcc fork_demo.c -o fork_demo
./fork_demo
# Parent: PID=4000, Child=4001
# Child: PID=4001

Thứ tự output không đảm bảo vì scheduler có thể chọn parent hoặc child trước.

5.2. Copy-on-Write (COW)

fork() thường không sao chép ngay toàn bộ RAM. Nhiều trang vật lý được chia sẻ tạm thời theo Copy-on-Write. Khi một bên ghi vào trang cần tách riêng, kernel xử lý page fault và tạo bản sao phù hợp.

Copy-on-Write — tương tác

Hai ánh xạ có thể dùng chung trang vật lý.

COW tối ưu bộ nhớ nhưng không biến hai process thành shared-memory process theo nghĩa thông thường.

6. execve() — Thay chương trình mà không tạo PID mới

fork() tạo process mới; execve() thay image chương trình trong process hiện tại. Nếu thành công, mã phía sau execve() không chạy.

#include <unistd.h>
#include <stdio.h>
extern char **environ;
int main(void)
{
    char *argv[] = {"ls", "-l", NULL};
    execve("/bin/ls", argv, environ);
    perror("execve failed");
    return 1;
}
PID không đổi sau execve()

Không phải mọi tài nguyên đều mất đi: file descriptor không đánh dấu close-on-exec thường vẫn tồn tại. Vì vậy FD_CLOEXEC rất quan trọng.

7. wait() — Vì sao cha phải chờ con?

Khi child kết thúc, kernel giữ một ít thông tin để parent lấy exit status và nguyên nhân kết thúc bằng wait()/waitpid(). Giá trị raw status phải giải mã bằng WIFEXITED, WEXITSTATUS, WIFSIGNALED, WTERMSIG.

#include <sys/wait.h>
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>
int main(void)
{
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }
    if (pid == 0) _exit(42);
    int status;
    if (waitpid(pid, &status, 0) == -1) { perror("waitpid"); return 1; }
    if (WIFEXITED(status)) printf("Exit code = %d\n", WEXITSTATUS(status));
    return 0;
}
Exit code = 42

8. Zombie và Orphan — Hai khái niệm dễ nhầm nhất

8.1. Zombie process

Zombie đã kết thúc thực thi nhưng parent chưa thu nhận trạng thái. Giống nhân viên đã nghỉ nhưng hồ sơ bàn giao còn chờ xử lý.

Running → Exited (Zombie) → Reaped

Tại sao SIGKILL không giết zombie? Vì nó đã chết. Cần parent gọi wait()/waitpid(), hoặc một reaper phù hợp sau reparent.

8.2. Orphan process

Orphan là process vẫn tồn tại sau khi parent ban đầu kết thúc. Nó có thể vẫn chạy và được reparent tới subreaper phù hợp hoặc init của PID namespace.

ZombieOrphan
Đã kết thúc thực thiCó thể vẫn đang chạy
Chờ thu exit statusMất parent ban đầu
Thường trạng thái ZKhông có trạng thái orphan riêng
Không sửa bằng SIGKILLĐược reparent theo cơ chế kernel

Câu hỏi phỏng vấn: Có thể vừa orphan vừa zombie? Có thể có tình huống child đã kết thúc chưa được reap, trong khi parent ban đầu biến mất; child được reparent để reaper thu trạng thái.

9. Vòng đời và các trạng thái process

Process có thể đang chạy, chờ CPU, timer, I/O, sự kiện hoặc đã kết thúc.

Chọn trạng thái để xem ý nghĩa

R: đang chạy hoặc sẵn sàng chạy.

9.1. R — Running hoặc Runnable

R không đảm bảo task đang chiếm CPU ngay tại thời điểm quan sát; nó cũng có thể đang chờ scheduler chọn.

9.2. S — Interruptible sleep

sleep 300

sleep chủ yếu chờ timer, không tính toán liên tục trong 300 giây.

9.3. D — Uninterruptible sleep

D thường là đường chờ liên quan I/O hoặc tài nguyên kernel. Không kết luận cứ có D là đĩa hỏng. Kiểm tra wait channel và stack khi được phép.

ps -eo pid,stat,wchan:32,comm
cat /proc/<PID>/wchan
cat /proc/<PID>/stack

9.4. T — Stopped

Task bị dừng, ví dụ bởi SIGSTOP.

9.5. Z — Zombie

Task đã kết thúc nhưng chưa được thu hồi trạng thái.

10. Signal — Cơ chế gửi thông báo đến process

Signal là cơ chế thông báo bất đồng bộ của hệ điều hành; không phải callback thông thường hay kênh truyền dữ liệu tổng quát thay cho socket/pipe.

SIGSEGV11Lỗi truy cập bộ nhớ

Số signal có thể khác kiến trúc; dùng tên hằng thay vì hardcode.

10.1. SIGTERM và SIGKILL khác nhau thế nào?

SIGTERM

Yêu cầu dừng → handler có thể chạy → cleanup → exit

SIGKILL

Buộc kết thúc → không handler → không cleanup user space

SIGKILL không thể bị bắt/chặn/bỏ qua; tác động có thể chưa tức thì nếu task đang mắc trong đường chờ kernel không ngắt được. Không dùng SIGKILL tùy tiện cho shutdown: ứng dụng có thể đang ghi file, hoàn tất transaction, đồng bộ dữ liệu, đóng socket hoặc đưa phần cứng về trạng thái an toàn.

11. Lab 1 — Điều khiển process bằng signal

sleep 300 &
lab_pid=$!
ps -p "$lab_pid" -o pid,ppid,stat,etime,args
kill -STOP "$lab_pid"
ps -p "$lab_pid" -o pid,stat,args
kill -CONT "$lab_pid"
kill -TERM "$lab_pid"
wait "$lab_pid"
printf 'status=%s\n' "$?"

Bước 1: Chạy nền

sleep 300 &

Dấu & cho shell chạy background job, tiếp tục nhận lệnh.

Bước 2: Lưu PID

lab_pid=$!

$! là PID liên quan đến job bất đồng bộ gần nhất; với sleep đơn, đây là PID cần theo dõi.

Bước 3: Kiểm tra trạng thái

ps -p "$lab_pid" -o pid,ppid,stat,etime,args

PID là process ID; PPID là parent PID; STAT là trạng thái; ETIME là thời gian từ khi tạo; ARGS là command line.

Bước 4: Dừng process

kill -STOP "$lab_pid"

kill dùng gửi signal, không chỉ để giết. STOP thường đưa task sang trạng thái T.

Bước 5: Tiếp tục

kill -CONT "$lab_pid"

Task có thể tiếp tục được scheduler lập lịch.

Bước 6: Yêu cầu kết thúc

kill -TERM "$lab_pid"

sleep thường dùng hành động mặc định của SIGTERM là kết thúc.

Bước 7: Thu nhận trạng thái

wait "$lab_pid"
printf 'status=%s\n' "$?"

Trong Bash, kết thúc bởi signal thường trả 128 + số signal; SIGTERM=15 nên status thường là 143. Đây là quy ước shell, không phải raw wait status.

12. Lab 2 — Ứng dụng Python xử lý SIGTERM

mkdir -p ~/linux-lab
nano ~/linux-lab/signals.py
import signal
import time

running = True

def stop(signum, frame):
    global running
    running = False

signal.signal(signal.SIGTERM, stop)
print("ready", flush=True)
try:
    while running:
        time.sleep(0.2)
finally:
    print("cleanup complete", flush=True)

running là cờ điều khiển. Handler SIGTERM đổi running=False, vòng lặp kết thúc và finally in cleanup complete. Trong CPython, Python-level handler được thực thi tại các điểm interpreter phù hợp, thường trên main thread, không nhất thiết ngay thời điểm kernel gửi signal.

python3 ~/linux-lab/signals.py &
pid=$!
# Đợi ready
kill -TERM "$pid"
wait "$pid"
ready
cleanup complete

Nếu handler chỉ đổi cờ và chương trình thoát bình thường, exit code có thể là 0.

python3 ~/linux-lab/signals.py &
pid=$!
# Đợi ready
kill -KILL "$pid"
wait "$pid"

Lần này không kỳ vọng thấy cleanup complete. finally không phải bảo đảm tuyệt đối: SIGKILL, mất điện, crash nghiêm trọng hoặc os._exit() có thể khiến nó không chạy.

13. Quan sát thread trong Linux

top -H
ps -L -p <PID> -o pid,tid,stat,psr,comm
PID   TID  STAT PSR COMMAND
4000  4000 S      0 app
4000  4001 R      1 app
4000  4002 S      2 app

PID thường là thread group ID; TID là thread/task ID; STAT là trạng thái; PSR là CPU logic gần nhất ghi nhận; COMM là tên task. 20 thread không mặc nhiên nhanh hơn một thread: có thể đang chờ lock/I/O hoặc tăng contention/context switch.

14. Signal trong chương trình đa luồng

Process-directed signal được gửi tới process và kernel chọn thread đủ điều kiện; thread-directed signal nhắm vào thread cụ thể. Mỗi thread có signal mask riêng, trong khi nhiều signal dispositions được chia sẻ mức process. SIGSEGV do lỗi thực thi thường hướng tới thread gây lỗi.

Thread A: Network
Thread B: Control
Thread C: Logging

Gửi SIGTERM tới process không đồng nghĩa cả ba thread chạy độc lập cùng một handler. Thiết kế C/C++ thường chặn signal ở worker threads, dùng thread chuyên trách sigwait() và phối hợp shutdown.

Quy tắc C: không tùy tiện gọi printf(), malloc() hoặc khóa mutex trong asynchronous signal handler. Chỉ các hàm async-signal-safe mới an toàn trong ngữ cảnh đó.

15. Từ Signal đến shutdown service bằng systemd

sudo systemctl stop myservice

systemd quản lý vòng đời service theo unit. Thông thường nó có thể gửi SIGTERM trước, chờ timeout rồi áp dụng biện pháp mạnh hơn theo cấu hình.

[Service]
ExecStart=/usr/bin/python3 /opt/app/main.py
KillSignal=SIGTERM
TimeoutStopSec=10s

Quy trình: yêu cầu dừng → cho cleanup → quá timeout có thể kết thúc cưỡng bức. Chi tiết phụ thuộc KillMode, SendSIGKILL, ExecStop và cấu hình khác.

Shutdown ứng dụng điều khiển BLDC qua CAN

Phản biện: Nếu mất điện hoặc SIGKILL, ai đảm bảo động cơ dừng? Không thể chỉ dựa vào Linux signal handler. Hệ thống điều khiển cần fail-safe ở MCU/driver: watchdog, timeout lệnh, giới hạn dòng, ngắt công suất hoặc safe state phù hợp.

16. Những lỗi thực tế Senior Engineer thường gặp

Lỗi 1: Dùng kill -9 ngay khi service không phản hồi

Hãy quan sát trạng thái, gửi TERM, chờ hợp lý, kiểm tra lại và chỉ dùng KILL khi cần.

Lỗi 2: Nghĩ PID tồn tại vĩnh viễn

PID có thể tái sử dụng. Script lưu PID cũ có thể gửi nhầm signal. pidfd trên Linux hiện đại giúp tránh một số race condition liên quan PID reuse.

Lỗi 3: Nhầm D với zombie

D là trạng thái chờ; Z là đã kết thúc nhưng chưa được reap. Nguyên nhân và hướng xử lý khác nhau.

Lỗi 4: Tạo thread không thiết kế đồng bộ

Shared state thiếu mutex/atomic/ownership rõ ràng có thể gây race condition, deadlock và lỗi khó tái hiện.

Lỗi 5: Parent không wait child

Child kết thúc mà parent không thu trạng thái có thể tích lũy zombie.

• Process là môi trường tài nguyên; thread là luồng thực thi; scheduler lập lịch task.

• An toàn hệ thống nhúng cần watchdog, timeout và fail-safe ở tầng thích hợp.
