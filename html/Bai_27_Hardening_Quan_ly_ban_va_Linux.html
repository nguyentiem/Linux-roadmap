MỤC 01 / 43

Tư duy nền tảng về Hardening

Một server có thể hoạt động tốt nhưng vẫn không an toàn. Ví dụ một máy chạy Nginx, API, PostgreSQL và SSH: website vẫn trả lời HTTP 200 nhưng SSH cho phép root password, database lắng nghe công khai và các service thử nghiệm chưa được tắt.

Hardening là giảm các khả năng không cần thiết mà kẻ tấn công có thể lợi dụng, đồng thời duy trì chức năng, khả năng quản trị và khả năng khôi phục.

Ví dụ đời sống: Một ngôi nhà có mười cửa nhưng chỉ cần hai cửa. Khóa tám cửa không dùng, kiểm soát chìa khóa hai cửa còn lại và có phương án thoát hiểm. Nếu khóa cả lối thoát hiểm, biện pháp an ninh lại gây nguy hiểm.

Câu hỏi phản biện: Tắt hết dịch vụ có an toàn hơn không? Không, nếu nó khiến hệ thống không thể vận hành hoặc khôi phục.

MỤC 02 / 43

Attack Surface — Bề mặt tấn công

Attack surface không chỉ là port mở mà còn gồm API, user, sudo, package, kernel, dependency, secrets, CI/CD và giao diện quản trị.

sudo ss -lntup

Ví dụ output:

tcp LISTEN 0 128 0.0.0.0:22
tcp LISTEN 0 511 0.0.0.0:80
tcp LISTEN 0 511 0.0.0.0:443
tcp LISTEN 0 128 0.0.0.0:3306

Nếu MySQL chỉ phục vụ ứng dụng trên cùng host, cân nhắc bind-address = 127.0.0.1 hoặc Unix socket. Tuy nhiên, bind localhost không ngăn ứng dụng web bị chiếm quyền truy cập database từ chính host.

Tại sao? Bảo vệ mạng không thay thế phân quyền ứng dụng và database.

MỤC 03 / 43

Defense in Depth — Phòng thủ nhiều lớp

Firewall hạn chế đường truy cập; SSH xác thực quản trị viên; sudo giới hạn đặc quyền; SELinux/AppArmor giới hạn thao tác; logging/audit giúp phát hiện; backup giúp khôi phục.

Nếu firewall bị vượt qua, attacker vẫn phải đối mặt với xác thực, phân quyền và MAC. Không lớp nào là tuyệt đối.

Câu hỏi: Có firewall rồi thì có cần quyền database không? Có, vì firewall chỉ giải quyết một phần luồng mạng.

MỤC 04 / 43

Baseline theo vai trò

Security baseline là tập yêu cầu cấu hình và kiểm chứng tối thiểu cho từng vai trò máy chủ. Web server, database server và build server không nên có cùng phần mềm, port và quyền.

Hạng mục Web Database Build
HTTP/HTTPS Có Không Tùy
Database listener Không Mạng riêng Không
Compiler Thường không Thường không Cần
SSH Hạn chế Hạn chế Hạn chế

Baseline cần người sở hữu, lý do, bằng chứng kiểm tra, ngoại lệ và ngày đánh giá lại.

MỤC 06 / 43

Kiểm kê port và listener

sudo ss -lntup

-l liệt kê listening socket phù hợp; -n giữ dạng số; -t TCP; -u UDP; -p process. UDP không có trạng thái LISTEN giống TCP.

0.0.0.0:22 nghĩa là bind mọi IPv4 interface, không chứng minh port có thể truy cập từ Internet: firewall, routing và NAT vẫn ảnh hưởng.

MỤC 07 / 43

Kiểm kê service và dependency

systemctl list-unit-files --state=enabled
systemctl --type=service --state=running
systemctl list-sockets
systemctl list-timers --all

enabled không đồng nghĩa active. Service có thể chạy vì socket activation hoặc dependency.

sudo systemctl disable example.service
sudo systemctl mask example.service

disable bỏ enablement, không nhất thiết dừng tiến trình; mask ngăn nhiều cơ chế kích hoạt nhưng có thể phá dependency. Đừng mask mù quáng.

MỤC 08 / 43

Kiểm kê tài khoản

getent passwd
getent group sudo
sudo -l

Dòng passwd có dạng username:password:UID:GID:GECOS:home:shell. Ký tự x thường chỉ password hash được quản lý riêng. Shell /usr/sbin/nologin không phải sandbox tuyệt đối. Không xóa tài khoản hệ thống chỉ vì tên lạ.

MỤC 09 / 43

SSH Host Key và User Key

Host key cho client biết danh tính server; user key giúp server xác thực người đăng nhập. Ví dụ đời sống: bạn phải biết mình đến đúng ngân hàng trước khi ngân hàng kiểm tra giấy tờ của bạn.

ssh admin@192.168.1.50
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Fingerprint cần đối chiếu qua kênh đáng tin cậy. Host key thay đổi có thể do rebuild hợp lệ hoặc máy giả mạo; không xóa toàn bộ known_hosts để né cảnh báo.

MỤC 10 / 43

SSH public key và tạo khóa

Private key được giữ ở client; public key được server cho phép. Client chứng minh sở hữu private key bằng mật mã mà không gửi private key cho server.

ssh-keygen -t ed25519 -a 100 -C "admin-laptop"
ssh-copy-id admin@192.168.1.50
ssh -o PreferredAuthentications=publickey \
    -o PasswordAuthentication=no admin@192.168.1.50

-a 100 điều chỉnh KDF khi bảo vệ private key OpenSSH, không phải số vòng chữ ký Ed25519.

MỤC 11 / 43

Quy trình SSH Hardening an toàn

Trước khi tắt password login: giữ phiên hiện tại, bảo đảm console dự phòng, thử key login trong phiên mới, kiểm tra sudo và sao lưu cấu hình.

PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no

Đánh giá MFA/PAM trước khi tắt keyboard-interactive.

sudo sshd -t
sudo sshd -T
sudo sshd -T -C user=admin,host=client.example,addr=192.0.2.10
sudo systemctl reload ssh

Tên service có thể là ssh hoặc sshd. Match block làm thay đổi cấu hình hiệu lực theo ngữ cảnh. Phiên SSH cũ vẫn sống không chứng minh login mới sẽ thành công.

MỤC 12 / 43

Least Privilege

Mỗi người dùng và service chỉ nên có quyền cần thiết. Ví dụ người giao hàng chỉ cần vào khu nhận hàng, không cần chìa khóa phòng tài chính.

Một API đọc dữ liệu không nên chạy root nếu không cần. Hạn chế quyền giúp giảm thiệt hại nếu ứng dụng bị khai thác.

MỤC 13 / 43

Sudo và lệnh nguy hiểm

operator ALL=(root) NOPASSWD: /usr/bin/vim

Rule trên nguy hiểm vì editor có thể thực thi shell. Interpreter, shell, package manager và công cụ gọi subprocess cũng cần đánh giá tương tự.

operator ALL=(root) /usr/bin/systemctl restart myapp.service

Ngay cả rule restart cụ thể cũng phải kiểm tra ai có thể sửa unit, binary và file mà service dùng.

MỤC 14 / 43

Chỉnh sudoers và capabilities

sudo visudo
sudo visudo -f /etc/sudoers.d/myapp
sudo visudo -c

Linux capabilities tách một phần quyền root. Ví dụ service cần bind port đặc quyền có thể dùng:

[Service]
User=webapp
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
NoNewPrivileges=yes

Cần xét socket activation và cấu hình hệ thống trước khi cấp capability.

MỤC 15 / 43

Vì sao phần mềm ổn định vẫn cần patch?

Một thư viện có thể trả kết quả đúng trong mọi kiểm thử thông thường nhưng có memory corruption khi nhận input độc hại. Functional correctness khác security assurance.

Patch management là quá trình kiểm kê, đánh giá, kiểm thử, triển khai và xác minh bản sửa lỗi xuyên suốt vòng đời hệ thống.

MỤC 16 / 43

Exploit Cách/mã khai thác điểm yếu

Không quyết định chỉ bằng CVSS: cần xét tài sản, khả năng tiếp cận, exploit đang được dùng và biện pháp bù trừ.

MỤC 17 / 43

Backport Security Fix

Distro có thể lấy bản sửa từ upstream mới và áp dụng vào nhánh cũ. Vì vậy phiên bản upstream nhìn vẫn cũ nhưng package distro đã được vá.

dpkg-query -W openssh-server
apt-cache policy openssh-server
uname -r
dpkg -l 'linux-image*'

Cần đọc advisory của đúng distro và đúng package build.

MỤC 18 / 43

Patch Workflow: Inventory và Assess

Bước 1: kiểm kê OS, kernel, package, service, container, virtual environment và static binaries.

cat /etc/os-release
uname -r
dpkg-query -W
systemctl --type=service --state=running

Bước 2: đánh giá CVE có ảnh hưởng tới cấu hình thực tế không, mức độ exposed, mức độ quan trọng của tài sản và tình trạng khai thác ngoài thực tế.

MỤC 19 / 43

Patch Workflow: Test, Prepare, Deploy

Bước 3: kiểm thử trên clone/staging với workload đại diện.

curl -fsS http://127.0.0.1:8080/health

HTTP 200 chưa đủ: cần thử xác thực, đọc/ghi dữ liệu và dependency.

Bước 4: chuẩn bị backup, restore test, rollback, maintenance window, tiêu chí dừng.

Bước 5: triển khai theo chính sách:

sudo apt update
sudo apt upgrade

Production có thể cần pin package, staged rollout và change approval.

MỤC 20 / 43

Patch Workflow: Verify runtime

Installed version ≠ Running version. Tiến trình có thể giữ thư viện cũ trong RAM sau khi package trên disk được cập nhật.

sudo lsof +L1
uname -r
systemctl status myapp.service
journalctl -u myapp.service -b --no-pager

lsof +L1 không phải công cụ xác minh bản vá đầy đủ. needrestart có thể giúp trên hệ thống hỗ trợ.

MỤC 21 / 43

Rollback package khác rollback dữ liệu

Giả sử App v2 thay đổi schema database. Quay lại binary App v1 không đồng nghĩa schema tự quay lại v1.

CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT);
ALTER TABLE users ADD COLUMN email TEXT;

Cần phân biệt rollback binary, cấu hình, schema, restore dữ liệu và toàn bộ hệ thống. Migration phá hủy dữ liệu có thể không đảo ngược được. Xem thêm expand-and-contract, blue-green và canary.

MỤC 22 / 43

Secrets và credential

Secret gồm API token, database password, SSH private key, TLS private key và signing key.

myapp --password "SuperSecret123"

Argument có thể lộ qua process listing, shell history hoặc log. Environment variable cũng không phải kho bí mật tuyệt đối. Dùng secret manager hoặc cơ chế phù hợp, quyền file hẹp và rotation.

MỤC 23 / 43

Vì sao không lưu secret trong Git?

API_TOKEN = "secret-value"

Xóa secret ở commit mới không xóa nó khỏi lịch sử, clone hoặc CI log. Nếu lộ: thu hồi/rotate, điều tra phạm vi ảnh hưởng, kiểm tra log, xử lý lịch sử khi cần và bổ sung secret scanning. Xóa Git history không thay thế rotation.

MỤC 24 / 43

Audit, logging và time synchronization

Application log ghi hành vi ứng dụng; audit tập trung vào sự kiện cần truy vết. Log local có thể bị sửa nếu host bị chiếm quyền cao, nên cân nhắc hệ thống log tập trung.

sudo systemctl status auditd
sudo auditctl -s
timedatectl status
chronyc tracking
chronyc sources -v

NTP service active không chứng minh đồng hồ đã synchronized. Thời gian sai gây khó điều tra incident, kiểm tra certificate và token.

MỤC 25 / 43

Lab kiểm kê và thay đổi nhỏ

mkdir -p ~/hardening-lab
cd ~/hardening-lab
cat /etc/os-release > os-before.txt
uname -a > kernel-before.txt
sudo ss -lntup > ports-before.txt
systemctl list-unit-files --state=enabled > services-before.txt
getent passwd > users-before.txt
timedatectl status > time-before.txt

Trên VM clone, chọn service thử nghiệm đã xác nhận không cần, kiểm tra reverse dependencies rồi mới đổi:

systemctl status lab-demo.service
systemctl list-dependencies --reverse lab-demo.service
sudo systemctl disable --now lab-demo.service
systemctl is-active lab-demo.service
systemctl is-enabled lab-demo.service
curl -fsS http://127.0.0.1:8080/health

Rollback phải khôi phục đúng trạng thái trước thay đổi. enable --now không đúng nếu service trước đó active nhưng disabled.

MỤC 26 / 43

Câu hỏi phản biện tổng hợp

  • Tắt tất cả port có an toàn tuyệt đối? Không: còn local exploit, supply chain, credential và rủi ro phục hồi.
  • Có SSH key thì còn cần firewall? Có: xác thực khác network access control.
  • Package đã update có cần reboot? Tùy kernel, thư viện và tiến trình.
  • Vì sao không tắt log để tiết kiệm disk? Vì mất điều tra; nên rotation, retention và compression.
  • SELinux enforcing có thay thế patch? Không.
  • Snapshot có đồng nghĩa backup? Không.
  • Phiên SSH cũ còn sống có chứng minh cấu hình mới? Không.
MỤC 27 / 43

Systemd Sandboxing

Systemd hỗ trợ giới hạn môi trường thực thi service, nhưng không thay thế SELinux/AppArmor và không tạo sandbox tuyệt đối.

[Service]
User=myapp
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6
StateDirectory=myapp
Directive Ý nghĩa
User= Chạy bằng user cụ thể
NoNewPrivileges= Giảm khả năng tăng đặc quyền khi exec
PrivateTmp= Namespace thư mục tạm riêng
ProtectSystem=strict Phần lớn cây filesystem chỉ đọc
ProtectHome=yes Hạn chế đường dẫn home
RestrictAddressFamilies= Giới hạn họ socket
StateDirectory= Quản lý vùng dữ liệu ghi được 
systemd-analyze security myapp.service

Điểm số là gợi ý, không phải chứng nhận an toàn.

MỤC 28 / 43

File Integrity Monitoring (FIM)

Đặt vấn đề: hôm qua SSH cấm root login, hôm nay cấu hình bị sửa cho phép root password. Server vẫn chạy; làm sao phát hiện?

FIM theo dõi nội dung, file mới/xóa, ownership, permission và metadata. Ví dụ đời sống: kiểm kê kho mỗi tối và so sánh với hôm trước.

sha256sum /etc/ssh/sshd_config

Hash chỉ so sánh với trạng thái tham chiếu, không tự chứng minh file an toàn. Baseline phải được bảo vệ.

AIDE:

sudo apt update
sudo apt install aide
sudo aide --init
sudo aide --check

Tùy distro cần đặt database vừa tạo vào đúng vị trí. AIDE báo khác biệt không tự chứng minh có attacker: package update và automation cũng có thể thay đổi file.

MỤC 29 / 43

Vulnerability Scanning và Compliance Scanning

Vulnerability scanning: phần mềm có lỗ hổng đã biết không? Compliance scanning: cấu hình có tuân baseline không?

Tiêu chí Vulnerability Compliance
Mục tiêu Tìm lỗ hổng Kiểm tra baseline
Ví dụ Package bị CVE SSH root login
Dữ liệu Advisory, CVE CIS, policy
Kết quả Finding, risk Pass/fail/exception

Scanner có false positive, false negative, thiếu runtime context hoặc không nhận biết backport. Kết quả cần được triage.

MỤC 30 / 43

CIS Benchmark và OpenSCAP

Khi có 200 server, cần benchmark nhất quán thay vì mỗi quản trị viên tự chọn cấu hình. CIS cung cấp khuyến nghị; SCAP là hệ sinh thái chuẩn biểu diễn và đánh giá; OpenSCAP là bộ công cụ.

sudo apt install libopenscap8
oscap --version
oscap info benchmark.xml
sudo oscap xccdf eval \
  --profile PROFILE_ID \
  --results results.xml \
  --report report.html \
  benchmark.xml

Package CLI thay đổi theo distro; PROFILE_ID phải tồn tại trong SCAP content. Không chạy remediation tự động trên production khi chưa review và test.

MỤC 31 / 43

Kernel Hardening

Kernel quản lý memory, process, file, network, driver và syscall. Kernel exploit có thể phá vỡ nhiều lớp bảo vệ.

ASLR làm ngẫu nhiên hóa vị trí vùng nhớ, tăng độ khó của nhiều kỹ thuật memory exploitation, nhưng không sửa memory corruption.

cat /proc/sys/kernel/randomize_va_space
sysctl kernel.randomize_va_space
sysctl net.ipv4.conf.all.rp_filter
sysctl net.ipv4.ip_forward

Giá trị ASLR thường là 0=tắt, 1=một phần, 2=mở rộng. rp_filter có thể ảnh hưởng asymmetric routing. Không copy hàng trăm sysctl từ Internet mà không hiểu network topology.

MỤC 32 / 43

Filesystem Hardening

Quyền chmod/chown chưa đủ; mount option bổ sung rào chắn:

  • nodev: không diễn giải device special files trên mount.
  • nosuid: hạn chế setuid/setgid và file capabilities.
  • noexec: ngăn thực thi trực tiếp file trên mount theo cơ chế tương ứng.
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS

noexec cho /tmp không ngăn interpreter đọc script từ đó và có thể làm hỏng ứng dụng.

sudo chattr +i important.conf
lsattr important.conf
sudo chattr -i important.conf

Immutable attribute không chống được mọi người có đủ quyền và có thể cản package updates.

MỤC 33 / 43

Systemd Hardening nâng cao

Seccomp hạn chế system calls:

[Service]
SystemCallArchitectures=native
SystemCallFilter=@system-service
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6
IPAddressDeny=any
IPAddressAllow=localhost
ProtectSystem=strict
StateDirectory=myapp

Đây là ví dụ các cơ chế, không phải profile phù hợp mọi service. Các filter có thể làm hỏng dependency hoặc workload; phải kiểm thử thực tế.

Một service sandbox chặt vẫn có thể bị SQL injection.

Container Hardening

Container thông thường chia sẻ host kernel; VM có guest kernel riêng. Vì vậy container không tương đương VM về isolation.

FROM python:3.12-slim
RUN groupadd -r app && useradd -r -g app app
WORKDIR /app
COPY --chown=app:app . /app
USER app
CMD ["python", "main.py"]

docker run --read-only myapp:latest
docker run --cap-drop=ALL myapp:latest

Có thể cần tmpfs/volume ghi riêng. Không dùng --privileged như cách mặc định để chữa lỗi permission. USER app không tự loại bỏ mọi capability.

Kernel Patch, Live Patching và Reboot

Package kernel mới trên disk không đồng nghĩa kernel đang chạy đã đổi:

uname -r

Live patching áp dụng một số sửa lỗi lên kernel đang chạy, nhưng không hỗ trợ mọi thay đổi và không thay thế hoàn toàn reboot.

Rolling update với 3 web server: rút A khỏi load balancer → update/reboot → health check → đưa lại → lặp B, C. Cần đủ capacity, session handling và dependency; rolling update không tự bảo đảm zero downtime.

Security Compliance và Configuration Drift

Configuration drift: nhiều server ban đầu cùng baseline, sau sáu tháng khác nhau do manual changes, exception cũ, package lạ.

Drift khiến quyền, firewall, service, log và phiên bản không đồng nhất; bản sửa trên máy A chưa chắc hoạt động trên B.

Giải pháp: version control, configuration management, automated compliance checks, change review và exception tracking. Đây là cầu nối trực tiếp sang Ansible.

Câu hỏi phỏng vấn Senior Linux Security Engineer

  1. Vì sao firewall không thay thế SELinux? Vì một bên giới hạn network, bên kia giới hạn subject-object theo policy.
  2. Vì sao cập nhật OpenSSL chưa chắc có hiệu lực? Process có thể giữ thư viện cũ.
  3. Vì sao sudo Python/root nguy hiểm? Interpreter có thể truy cập file và chạy lệnh tùy ý.
  4. Vì sao scanner có thể báo sai CVE? Distro backport bản vá.
  5. Vì sao hardening có thể gây downtime? Chặn quyền/network/dependency hợp lệ.
  6. Vì sao cần restore test? Backup tồn tại không chứng minh phục hồi được.
  7. Vì sao compliance 100% không đồng nghĩa an toàn? Checklist không bao phủ mọi lỗ hổng.
  8. Vì sao cần configuration management? Để duy trì desired state và chống drift.

Kết nối sang Bài 28 — Ansible

Hardening một máy là vấn đề kỹ thuật; duy trì baseline trên 10, 100, 1.000 máy là vấn đề tự động hóa và vận hành.

Desired state mô tả trạng thái mong muốn thay vì một chuỗi thao tác thủ công.

- name: Harden SSH
  hosts: linux_servers
  become: true
  tasks:
    - name: Ensure root SSH login is disabled
      ansible.builtin.lineinfile:
        path: /etc/ssh/sshd_config
        regexp: '^PermitRootLogin'
        line: 'PermitRootLogin no'
        validate: '/usr/sbin/sshd -t -f %s'

Ví dụ trên chưa xử lý đầy đủ include files, Match blocks, duplicate directives, effective config hoặc safe rollout. Production cần kiểm tra cấu hình hiệu lực, test login mới và rollback.

Kết luận: Hardening không phải làm Linux khó dùng nhất có thể. Hardening là giảm rủi ro có kiểm soát trong khi vẫn giữ khả năng vận hành, cập nhật và khôi phục.
