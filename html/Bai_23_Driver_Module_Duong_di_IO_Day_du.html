Bài 23 — Linux Driver, Kernel Module và đường đi I/O

Giải thích chuyên sâu theo góc nhìn Senior Linux / Embedded Linux Engineer

Bài này kết nối những kiến thức đã học về system call, quản lý bộ nhớ, filesystem, scheduler và phần cứng để trả lời một câu hỏi quan trọng:

Khi chương trình Linux muốn đọc hoặc ghi dữ liệu vào một thiết bị, từ lúc gọi read() hoặc write() cho đến khi phần cứng thực sự hoạt động, chuyện gì xảy ra?

Ví dụ, bạn có một board ODROID XU4 chạy Linux, một ESP32 kết nối qua USB-UART, một ổ eMMC và một card mạng Ethernet. Làm thế nào Linux nhận diện, quản lý và giao tiếp được với tất cả những thiết bị khác nhau này?

Chúng ta sẽ đi từ bức tranh tổng thể đến từng cơ chế bên trong kernel, rồi thực hành quan sát trực tiếp.

1. Đặt vấn đề: Vì sao Linux cần driver?

Hãy tưởng tượng bạn viết chương trình:

#include <stdio.h>
int main(void)
{
    FILE *f = fopen("/tmp/data.txt", "w");
    if (!f) { perror("fopen"); return 1; }
    fprintf(f, "Hello Linux\n");
    if (fclose(f) != 0) { perror("fclose"); return 1; }
    return 0;
}

Chương trình rất đơn giản, nhưng có những câu hỏi thú vị:

  • Làm sao fprintf() biết dữ liệu cần ghi vào ổ SSD, eMMC hay thẻ SD?
  • Ai biết địa chỉ thanh ghi phần cứng của bộ điều khiển lưu trữ?
  • CPU có phải tự chép từng byte xuống thiết bị không?
  • Tại sao chương trình ghi xong nhưng mất điện vẫn có thể mất dữ liệu?
  • Nếu thay SSD SATA bằng NVMe, tại sao chương trình C không phải sửa?

Để trả lời, hãy xem kiến trúc tổng thể.

Đường đi dữ liệu từ ứng dụng đến thiết bị lưu trữ

User Space
Ứng dụng C / Python / Database
fprintf(), fwrite(), read()
↓ System call: write(), read(), fsync()
VFS
Giao diện filesystem thống nhất
↓
Filesystem
ext4, XFS, Btrfs...
↓
Page Cache / Writeback
Cache dữ liệu và đẩy trang bẩn
↓

Tạo, gộp và xếp hàng I/O request
↓

Điều khiển bộ điều khiển phần cứng
↓

Đây là đường đi khái niệm của block I/O thông thường. Một số lớp có thể bị bỏ qua hoặc thay đổi tùy loại I/O, filesystem và thiết bị.

Điều quan trọng đầu tiên: ứng dụng không cần biết phần cứng cụ thể đang được sử dụng.

Ứng dụng chỉ cần sử dụng một giao diện chuẩn. Kernel và driver chịu trách nhiệm chuyển yêu cầu đó thành những thao tác phù hợp với thiết bị.

Đây chính là nguyên lý abstraction (trừu tượng hóa) mà bạn đã gặp trong lập trình hướng đối tượng và kiến trúc hệ điều hành.

2. Driver thực chất là gì?

2.1. Định nghĩa

Device driver là thành phần phần mềm chịu trách nhiệm điều khiển một loại thiết bị, đồng thời kết nối thiết bị đó với các subsystem của hệ điều hành.

Nói đơn giản:

Driver là người phiên dịch giữa yêu cầu của hệ điều hành và cách điều khiển cụ thể của phần cứng.

Ví dụ trong đời sống: Bạn là khách hàng tại nhà hàng, muốn gọi món. Bạn không cần biết bếp sử dụng lò điện, lò gas hay bếp từ.

  • Khách hàng: ứng dụng.
  • Nhân viên nhận đơn: giao diện hệ điều hành.
  • Đầu bếp: driver.
  • Thiết bị nấu: phần cứng.

Cùng một yêu cầu "nấu cơm", đầu bếp phải biết thao tác với từng loại thiết bị.

2.2. Driver làm những công việc nào?

Một driver có thể thực hiện:

  1. Phát hiện và khởi tạo thiết bị.
  2. Cấu hình thanh ghi phần cứng.
  3. Thiết lập clock, interrupt, DMA.
  4. Gửi yêu cầu đọc/ghi dữ liệu.
  5. Nhận thông báo hoàn thành từ phần cứng.
  6. Xử lý lỗi, timeout và reset thiết bị.
  7. Quản lý trạng thái nguồn và suspend/resume.
  8. Cung cấp giao diện cho các lớp kernel khác hoặc user space.

Lấy ví dụ một UART driver trên SoC.

Khi ứng dụng gọi:

write(fd, "ABC", 3);

Kernel có thể chuyển dữ liệu đến UART driver. Driver kiểm tra trạng thái FIFO, cấu hình interrupt hoặc DMA, sau đó yêu cầu UART controller phát các bit ra chân TX.

Không phải driver nào cũng trực tiếp tạo bit tín hiệu. Phần lớn công việc truyền bit thực tế do peripheral phần cứng thực hiện.

2.3. Driver khác ứng dụng bình thường như thế nào?

Đặc điểm Ứng dụng user space Kernel driver
Quyền truy cập Bị giới hạn Có quyền kernel
Truy cập thanh ghi MMIO Thường không trực tiếp Có thể qua API kernel
Lỗi truy cập bộ nhớ Thường làm hỏng process Có thể gây kernel panic
API sử dụng libc, POSIX Linux kernel API
Quản lý bộ nhớ malloc, mmap kmalloc, vmalloc, DMA API...
Khả năng sleep Theo luồng xử lý Phụ thuộc execution context

Câu hỏi phản biện: Driver có bắt buộc chạy trong kernel không?

Không. Linux cũng có những giải pháp điều khiển phần cứng từ user space như UIO, VFIO, libusb và một số mô hình driver chuyên dụng.

Tuy nhiên, các driver truyền thống của block, network, UART, I2C và SPI thường hoạt động trong kernel.

3. Kernel module là gì? Driver và module có phải một?

Đây là hai khái niệm rất dễ nhầm lẫn.

Driver mô tả chức năng. Module mô tả cách đóng gói và nạp mã vào kernel.

Một driver có thể được biên dịch trực tiếp vào kernel hoặc biên dịch thành một module nạp động.

3.1. Hai hình thức driver phổ biến

Built-in driver

Mã driver nằm trong kernel image và có mặt khi kernel khởi động.

CONFIG_XXX=y
Loadable module

Mã được đóng gói thành file .ko, có thể nạp vào kernel khi cần.

CONFIG_XXX=m

Trong cấu hình build kernel:

CONFIG_FOO=y   # Built-in
CONFIG_FOO=m   # Module
# CONFIG_FOO is not set

Giả sử driver USB-UART được biên dịch thành module cp210x.ko.

Khi cắm một USB-UART CP210x tương thích, Linux có thể tự nạp module và gắn driver với thiết bị.

Các lệnh thường dùng:

lsmod
modinfo cp210x
sudo modprobe cp210x

lsmod liệt kê module đang nạp. modinfo hiển thị metadata của module. modprobe yêu cầu nạp module và xử lý các dependency liên quan theo cấu hình hệ thống.

3.2. Vì sao lsmod không thấy driver nhưng thiết bị vẫn hoạt động?

Vì driver có thể là built-in.

Ví dụ, trên một board nhúng, driver phục vụ root filesystem thường phải sẵn sàng đủ sớm trong quá trình boot.

Nếu driver lưu trữ chỉ tồn tại trên chính filesystem cần driver đó để đọc, ta gặp vấn đề "con gà và quả trứng".

Giải pháp thường là tích hợp driver cần thiết vào kernel hoặc cung cấp module và dependency trong initramfs.

3.3. Module được nạp như thế nào?

Luồng nạp module tự động — ví dụ USB-UART

① Cắm USB-UART vào cổng USB
↓
② USB core phát hiện thiết bị và đọc descriptor
↓
③ Kernel tạo thông tin thiết bị và phát uevent
↓
④ Cơ chế userspace/kmod hỗ trợ tìm và nạp module phù hợp
↓
⑤ Driver đăng ký, được match và chạy probe()
↓
⑥ Thiết bị sẵn sàng, ví dụ /dev/ttyUSB0

Ở đây xuất hiện một khái niệm mới: probe().

Probe là callback mà bus/driver core sử dụng khi một thiết bị được ghép với driver phù hợp. Trong quá trình này driver có thể cấp phát tài nguyên, ánh xạ thanh ghi, đăng ký interrupt và khởi tạo thiết bị.

Probe không phải lúc nào cũng chạy thành công. Driver có thể báo lỗi hoặc hoãn probe nếu tài nguyên phụ thuộc chưa sẵn sàng.

4. Firmware khác driver như thế nào?

Hãy lấy một card Wi-Fi làm ví dụ.

Driver Linux biết cách giao tiếp với card Wi-Fi. Nhưng bản thân chip Wi-Fi có thể cần một chương trình riêng chạy trên bộ xử lý bên trong chip.

Chương trình đó là firmware.

Ứng dụng Linux
Yêu cầu gửi dữ liệu qua Wi-Fi
↓
Wi-Fi Driver — chạy trên CPU Linux
Gửi lệnh, quản lý buffer, nhận sự kiện
↓
Wi-Fi Firmware — chạy trên chip Wi-Fi
Thực hiện chức năng điều khiển nội bộ của thiết bị
↓
Radio / MAC / PHY Hardware

Firmware có thể được lưu sẵn trong ROM/flash của thiết bị hoặc được driver tải xuống trong quá trình khởi tạo.

Một đường dẫn thường gặp:

ls /lib/firmware

Để tìm lỗi firmware:

sudo dmesg | grep -i firmware

Cần phân biệt thêm:

  • Bootloader khởi động hệ thống.
  • Kernel quản lý tài nguyên hệ điều hành.
  • Driver điều khiển và tích hợp thiết bị.
  • Firmware cung cấp mã hoặc dữ liệu mà phần cứng/nền tảng cần.

Câu hỏi: Đã nạp đúng driver mà Wi-Fi vẫn không hoạt động, có chắc driver lỗi không?

Không. Có thể thiếu firmware, firmware không tương thích, thiết bị chưa được cấp nguồn, sai Device Tree, lỗi clock hoặc reset.

Đó là lý do kỹ sư nhúng không chỉ nhìn lsmod khi debug.

5. Linux Device Model — Kernel biết thiết bị nào dùng driver nào?

Trước khi bàn về interrupt và DMA, cần hiểu kernel tổ chức các thiết bị như thế nào.

Linux có một device model mô tả quan hệ giữa thiết bị, bus, driver và các lớp thiết bị.

Ví dụ một thiết bị USB-UART:

USB Host Controller
    |
    +-- USB Bus
         |
         +-- USB Device
              |
              +-- USB Interface
                   |
                   +-- cp210x Driver
                        |
                        +-- tty subsystem
                             |
                             +-- /dev/ttyUSB0

Lưu ý rằng trong USB, driver thường được ghép với USB interface, không nhất thiết với toàn bộ USB device.

5.1. Device, bus, driver và class

Thành phần Vai trò Ví dụ
Device Đối tượng thiết bị Một USB interface
Bus Cơ chế kết nối/match USB, PCI, platform
Driver Mã điều khiển cp210x, nvme
Class Nhóm chức năng tty, net, block
Device node Điểm truy cập user space /dev/ttyUSB0

Một điểm cần chú ý: /dev/ttyUSB0 không phải là driver.

Đó là một device node giúp ứng dụng truy cập chức năng thiết bị thông qua kernel.

5.2. sysfs là gì?

sysfs là một filesystem ảo, thường được mount tại:

/sys

Nó cung cấp cái nhìn có cấu trúc về các đối tượng và thuộc tính mà kernel xuất ra user space.

Một số thư mục quan trọng:

/sys/
├── bus/
├── class/
├── devices/
├── block/
├── module/
└── firmware/

Bạn có thể quan sát:

ls /sys/class/net
ls /sys/class/block
ls /sys/bus/usb/devices

/sys/class/net thể hiện các network interface, còn /sys/class/block thể hiện các block device.

Các entry trong /sys/class thường liên kết tới những đối tượng nằm trong cây /sys/devices.

Ví dụ: lần theo driver của card mạng

ls -l /sys/class/net

Giả sử hệ thống có eth0:

readlink -f /sys/class/net/eth0/device

Tiếp theo:

readlink -f /sys/class/net/eth0/device/driver

Với một thiết bị mạng vật lý, đường dẫn này có thể trỏ tới driver đang gắn với thiết bị.

Tuy nhiên, không phải mọi interface đều có đường dẫn đó. lo, veth, tun hoặc một số interface ảo không tương ứng trực tiếp với thiết bị phần cứng.

Tư duy debug của senior: Nếu một symlink không tồn tại, đừng vội kết luận thiết bị không có driver. Trước tiên hãy xác định bạn đang quan sát thiết bị vật lý, thiết bị ảo hay một tầng trung gian.

6. udev là gì? Tại sao cắm USB lại xuất hiện /dev/ttyUSB0?

Đây là chỗ liên kết kiến thức kernel với user space.

Kernel phát hiện thiết bị và quản lý đối tượng thiết bị. udev, thường thông qua systemd-udevd, xử lý các sự kiện thiết bị trong user space và áp dụng quy tắc.

Quá trình thiết bị xuất hiện

Kernel phát hiện thiết bị
↓
Kernel device model + uevent
↓
systemd-udevd xử lý rule
Permission, group, symlink, metadata
↓
/dev/ttyUSB0 hoặc symlink ổn định

Một điều chỉnh kỹ thuật quan trọng: trên Linux hiện đại, devtmpfs thường giúp kernel tạo device node cơ bản. udev không nhất thiết là thành phần trực tiếp tạo ra mọi node trong /dev; nó còn quản lý thuộc tính, quyền và các symlink.

6.1. Tại sao không nên chmod thủ công?

Giả sử:

sudo chmod 666 /dev/ttyUSB0

Lệnh có thể cho phép nhiều process truy cập cổng UART, nhưng thay đổi này thường không bền khi thiết bị bị tháo/cắm lại.

Ngoài ra, quyền 666 cho mọi người đọc/ghi có thể không phù hợp về bảo mật.

Giải pháp tốt hơn là sử dụng group và udev rule phù hợp.

Ví dụ:

SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", GROUP="dialout", MODE="0660"

Đây là ví dụ cho một loại thiết bị CP210x với VID/PID tương ứng; không nên áp dụng cho mọi USB-UART nếu chưa kiểm tra descriptor.

Xem thuộc tính:

udevadm info --attribute-walk \
    --name=/dev/ttyUSB0

6.2. Tại sao tên ttyUSB0 không ổn định?

Giả sử bạn cắm hai USB-UART:

USB-UART A → ttyUSB0
USB-UART B → ttyUSB1

Sau reboot hoặc cắm theo thứ tự khác, tên có thể thay đổi.

Vì vậy, trong sản phẩm nhúng, nên cân nhắc symlink theo serial hoặc đường kết nối vật lý.

Kiểm tra:

ls -l /dev/serial/by-id/
ls -l /dev/serial/by-path/

Nếu thiết bị và cấu hình udev hỗ trợ, các đường dẫn này có thể ổn định hơn.

Đây là một vấn đề rất thực tế khi làm robot, hệ thống điều khiển động cơ hoặc nhiều USB-CAN adapter.

7. Interrupt và DMA — CPU giao tiếp với phần cứng như thế nào?

Bây giờ ta đi xuống sâu hơn.

Giả sử ứng dụng muốn đọc 4 KiB dữ liệu từ một thiết bị lưu trữ.

Có hai câu hỏi:

  1. Ai chuyển dữ liệu giữa thiết bị và RAM?
  2. Làm sao CPU biết việc truyền dữ liệu đã hoàn thành?

Đây là lúc DMA và interrupt xuất hiện.

7.1. Polling — CPU liên tục hỏi thiết bị

Ví dụ đơn giản:

while (!(STATUS_REG & DATA_READY)) {
    /* wait */
}
value = DATA_REG;

CPU liên tục đọc thanh ghi trạng thái.

Ví dụ đời sống: bạn đặt đồ ăn và cứ mỗi giây lại hỏi nhà hàng "Xong chưa?".

Ưu điểm là đơn giản và có thể hữu ích khi chờ cực ngắn hoặc trong những ngữ cảnh cần kiểm soát chặt độ trễ.

Nhược điểm là CPU có thể tiêu tốn thời gian để chờ.

7.2. Interrupt — Thiết bị chủ động báo

Thay vì liên tục hỏi, CPU cấu hình thiết bị để phát interrupt khi một sự kiện xảy ra.

Ví dụ đời sống: bạn đặt đồ ăn, nhà hàng gọi điện khi món đã sẵn sàng.

Minh họa đơn giản. Trong thực tế, polling có thể rất hiệu quả với một số workload và thiết bị tốc độ cao; interrupt cũng có overhead.

7.3. Interrupt có làm CPU lập tức chạy handler không?

Không phải lúc nào cũng ngay lập tức.

CPU có thể đang tắt interrupt cục bộ, đang xử lý interrupt ưu tiên khác hoặc đang trong vùng kernel hạn chế preemption.

Độ trễ interrupt phụ thuộc phần cứng, kiến trúc CPU, cấu hình kernel và tải hệ thống.

Đây chính là điểm nối sang bài Real-Time Linux: latency và tính dự đoán được của thời gian phản hồi.

8. DMA — Direct Memory Access

Hãy tưởng tượng bạn cần chuyển 1 MB dữ liệu từ một peripheral vào RAM.

Nếu CPU tự đọc từng đơn vị dữ liệu từ thiết bị rồi ghi vào RAM, CPU phải tham gia vào rất nhiều thao tác chuyển dữ liệu.

DMA cho phép một DMA engine hoặc thiết bị bus-master chuyển dữ liệu trực tiếp tới hoặc từ bộ nhớ theo cấu hình được thiết lập.

8.1. Không dùng DMA

CPU-mediated transfer — mô hình đơn giản

→
🖥 CPU
→
▤ RAM

CPU thực hiện thao tác chuyển dữ liệu, làm tăng công việc phải xử lý.

8.2. Sử dụng DMA

⇄

CPU cấu hình transfer và xử lý completion, không phải tự chép từng byte.

8.3. DMA có nghĩa CPU hoàn toàn không tham gia?

Không. CPU/driver vẫn thường phải:

  • Chuẩn bị buffer và descriptor.
  • Thiết lập mapping DMA.
  • Cấu hình hoặc submit transfer.
  • Đảm bảo thứ tự truy cập bộ nhớ thích hợp.
  • Nhận completion.
  • Thu hồi hoặc tái sử dụng tài nguyên.

DMA giảm công việc chuyển dữ liệu của CPU, nhưng không loại bỏ vai trò điều phối của CPU.

8.4. Descriptor là gì?

Descriptor là cấu trúc mô tả công việc mà thiết bị hoặc DMA engine cần thực hiện.

Một ví dụ khái niệm:

struct dma_descriptor {
    uint64_t dma_address;
    uint32_t length;
    uint32_t flags;
};

Lưu ý đây không phải cấu trúc DMA API chung của Linux, mà chỉ dùng để minh họa.

Descriptor có thể cho biết địa chỉ DMA, độ dài dữ liệu và cờ điều khiển.

Đây là kiến thức rất gần với descriptor ring trong Ethernet controller, USB controller và nhiều bộ điều khiển lưu trữ.

9. DMA và Cache Coherency — Một lỗi rất khó debug

Đây là phần phân biệt giữa người mới học driver và người đã làm việc thực tế với phần cứng.

Giả sử CPU có cache.

CPU đọc một vùng RAM, sau đó thiết bị DMA ghi dữ liệu mới vào vùng RAM đó.

Nếu hệ thống không bảo đảm cache coherence, CPU có thể vẫn nhìn thấy bản dữ liệu cũ trong cache.

Ngược lại, CPU có thể đã sửa dữ liệu trong cache nhưng chưa làm cho thiết bị DMA nhìn thấy nội dung mới.

▶ Minh họa nguy cơ dữ liệu không nhất quán

CPU Cache
0xAA
Có thể đang giữ dữ liệu cũ
RAM
0xBB
DMA vừa ghi dữ liệu mới

Đây là mô hình của hệ thống không tự bảo đảm coherence. Trên hệ thống cache-coherent, phần cứng có thể duy trì tính nhất quán mà không cần thao tác thủ công tương đương.

Trong Linux kernel, driver nên sử dụng DMA API đúng cách thay vì tự đoán thao tác flush/invalidate cache.

Ví dụ các API thường gặp:

dma_alloc_coherent(...)
dma_map_single(...)
dma_unmap_single(...)
dma_sync_single_for_cpu(...)
dma_sync_single_for_device(...)

Việc chọn API phụ thuộc kiểu buffer, hướng truyền, ownership và khả năng coherence của nền tảng.

Câu hỏi: Nếu DMA đã ghi xong vào RAM thì có chắc CPU đọc được dữ liệu mới ngay không?

Không thể kết luận như vậy trên mọi kiến trúc nếu chưa xét cache coherence, memory ordering và các quy tắc của DMA API.

10. Buffer ownership — Ai được phép sử dụng buffer?

Giả sử driver đang sử dụng một buffer để DMA truyền dữ liệu.

CPU sửa buffer trong khi DMA đang đọc nó.

Điều gì xảy ra?

Thiết bị có thể nhận dữ liệu không nhất quán, tùy cách truy cập và đồng bộ.

Vì vậy driver phải quản lý ownership: tại một thời điểm, bên nào được quyền truy cập hoặc sửa buffer theo hợp đồng DMA.

Vòng đời buffer DMA đơn giản

① CPU owns buffer
CPU chuẩn bị nội dung và metadata
↓
② DMA mapping / sync
Thiết lập khả năng truy cập cho thiết bị
↓
③ Device owns buffer
Thiết bị thực hiện truyền dữ liệu
↓
④ Completion
Driver nhận biết transfer hoàn thành
↓
⑤ CPU owns buffer again
Đồng bộ/thu hồi mapping khi cần, rồi CPU xử lý

Một lỗi thường gặp là dùng lại buffer quá sớm hoặc giải phóng buffer trong khi thiết bị vẫn còn truy cập.

Trong kernel, lỗi kiểu này có thể dẫn đến memory corruption rất khó tái hiện.

11. I/O Scheduler khác CPU Scheduler như thế nào?

Bạn đã học CPU scheduling ở các bài trước.

CPU scheduler quyết định task nào được chạy trên CPU.

I/O scheduler quyết định các yêu cầu I/O ở block layer được tổ chức và phân phối như thế nào.

Ví dụ có ba tiến trình cùng yêu cầu đọc dữ liệu:

Process A → Read block 100
Process B → Read block 900
Process C → Read block 101

Với ổ cứng HDD, việc đọc các block gần nhau có thể giảm chi phí seek.

Với SSD hoặc NVMe, không có cơ chế seek cơ học như HDD, nhưng queueing, fairness, latency và parallelism vẫn quan trọng.

11.1. Các scheduler thường gặp

Scheduler Ý tưởng chính Tình huống cân nhắc
mq-deadline Điều phối request với cơ chế deadline Kiểm soát độ trễ chờ
bfq Phân phối dịch vụ theo budget Fairness, workload tương tác
none Không thêm lớp I/O scheduling tại vị trí này Thiết bị/stack có khả năng queueing tốt

Không có scheduler tốt nhất cho mọi workload.

11.2. Quan sát scheduler đang dùng

Ví dụ:

cat /sys/block/sda/queue/scheduler

Output giả định:

[mq-deadline] kyber bfq none

Scheduler trong dấu ngoặc vuông là scheduler đang được chọn.

Danh sách thực tế phụ thuộc kernel, thiết bị và các scheduler đã được biên dịch hoặc nạp.

11.3. Thử thay đổi scheduler

Trên thiết bị lab phù hợp, sau khi đánh giá rủi ro:

echo none | sudo tee \
  /sys/block/sdX/queue/scheduler

Chỉ thực hiện khi none xuất hiện trong danh sách khả dụng, thay sdX bằng đúng thiết bị và hiểu ảnh hưởng đến workload.

Không nên thay scheduler trên ổ production chỉ vì thấy một bài benchmark khác có kết quả tốt hơn.

12. NVMe và Multi-Queue — Vì sao một thiết bị có thể xử lý nhiều I/O cùng lúc?

HDD truyền thống bị giới hạn mạnh bởi cơ cấu cơ khí.

NVMe được thiết kế cho lưu trữ flash với nhiều queue và khả năng xử lý song song.

Mô hình đơn giản của NVMe multi-queue

Hình này chỉ mô tả ý tưởng. Số lượng hardware/software queue thực tế không nhất thiết bằng số CPU và phụ thuộc cấu hình driver, controller.

Vì thế, khi quan sát NVMe, không nên diễn giải %util như một tỷ lệ "thiết bị chỉ có thể làm một việc tại một thời điểm".

Để phân tích performance, nên kết hợp throughput, latency, queue depth, IOPS và workload.

13. Buffered I/O — Vì sao write() thành công chưa chắc dữ liệu đã nằm trên ổ?

Đây là một trong những phần quan trọng nhất của bài.

Giả sử bạn viết:

write(fd, buffer, 4096);

Nhiều người nghĩ dữ liệu đã được ghi xuống SSD ngay khi write() trả về thành công.

Điều này không đúng trong trường hợp buffered I/O thông thường.

13.1. Page cache là gì?

Page cache là vùng bộ nhớ mà kernel sử dụng để cache dữ liệu file.

Nó giúp giảm số lần truy cập storage, đặc biệt khi nhiều lần đọc/ghi cùng dữ liệu.

Đối với buffered write, dữ liệu có thể được chép vào page cache, đánh dấu dirty, rồi write() trả về.

Sau đó kernel thực hiện writeback để đưa dữ liệu xuống tầng lưu trữ.

▶ Mô phỏng vòng đời buffered write

Application
Gọi write() để ghi dữ liệu
↓
Page Cache
Dữ liệu được cache, có thể ở trạng thái dirty
↓
Writeback / Filesystem
Kernel gửi dữ liệu và metadata liên quan xuống storage
↓
Storage Device
Thiết bị xử lý và lưu dữ liệu theo cơ chế riêng

Đây là luồng khái niệm. Thời điểm writeback có thể khác, và ngay cả khi thiết bị đã nhận lệnh ghi, bảo đảm chống mất điện còn phụ thuộc vào cơ chế flush và tính đúng đắn của thiết bị.

13.2. Dirty page là gì?

Một dirty page là trang cache chứa dữ liệu đã được sửa nhưng chưa được đồng bộ hoàn toàn tới backing storage tương ứng.

Ví dụ:

RAM Page Cache:
[ Hello Linux ]  ← Dirty

SSD:
[ Old Content ]

Kernel có thể thực hiện writeback theo chính sách của hệ thống hoặc do ứng dụng yêu cầu đồng bộ.

Bạn có thể quan sát tổng quan:

grep -E 'Dirty|Writeback' /proc/meminfo

Lưu ý các giá trị này phản ánh trạng thái bộ nhớ toàn hệ thống, không phải riêng file đang nghiên cứu.

14. flush(), fsync() và sync() khác nhau thế nào?

Ba khái niệm này rất hay bị đánh đồng.

14.1. flush() của Python

Ví dụ:

f = open("data.txt", "w")
f.write("Hello")
f.flush()

Python có buffering riêng trong user space.

flush() đẩy dữ liệu từ buffer Python xuống tầng file descriptor/kernel.

Nó không tự bảo đảm dữ liệu đã được lưu bền trên thiết bị.

14.2. fsync()

Ví dụ:

import os
with open("data.txt", "w") as f:
    f.write("Hello")
    f.flush()
    os.fsync(f.fileno())

fsync() yêu cầu kernel đồng bộ dữ liệu và metadata cần thiết của file theo hợp đồng của syscall, filesystem và thiết bị.

Trong stack lưu trữ bình thường, điều này có thể dẫn đến các thao tác flush/cache-control phù hợp ở tầng thấp hơn.

Tuy nhiên, không thể dùng một lần fsync() thành công để chứng minh toàn bộ hệ thống phần cứng có khả năng chống mất điện tuyệt đối.

14.3. sync()

sync() yêu cầu đồng bộ các dữ liệu filesystem đang chờ trên phạm vi hệ thống.

Nó không phải là phương án thay thế tốt cho một giao thức transaction được thiết kế đúng trong ứng dụng.

Bảng so sánh

Thao tác Ý nghĩa chính
Python flush() Đẩy buffer user space xuống OS
write() Gửi dữ liệu tới kernel
fsync(fd) Đồng bộ file theo bảo đảm filesystem
fdatasync(fd) Đồng bộ dữ liệu và metadata cần thiết để đọc dữ liệu
sync() Đồng bộ dữ liệu filesystem trên phạm vi hệ thống
O_DIRECT Điều khiển đường đi cache của file I/O
O_SYNC Yêu cầu ngữ nghĩa ghi đồng bộ

Một câu hỏi quan trọng: O_DIRECT có làm dữ liệu an toàn khi mất điện không?

Không. Direct I/O và durability là hai vấn đề khác nhau.

15. Direct I/O và Buffered I/O

Buffered I/O thường sử dụng page cache.

Direct I/O thường giảm hoặc bỏ qua page cache cho phần dữ liệu file, tùy filesystem, loại I/O và các ràng buộc cụ thể.

Buffered I/O

Application
↓
Page Cache
↓
Storage

Direct I/O

Application
↓
Filesystem / Block Layer
↓
Storage

Vậy tại sao không sử dụng O_DIRECT cho mọi ứng dụng?

Vì page cache rất hữu ích. Nó giúp tăng hiệu năng khi dữ liệu được tái sử dụng và giảm I/O vật lý.

Direct I/O còn có những yêu cầu về alignment, kích thước, filesystem và xử lý đồng bộ với các hoạt động I/O khác.

Một số database sử dụng direct I/O vì muốn tự quản lý cache hoặc tránh cache trùng lặp, nhưng điều này không có nghĩa direct I/O luôn nhanh hơn.

16. Crash Consistency — Vì sao ghi file xong vẫn có thể mất tên file?

Đây là tình huống thực tế rất quan trọng.

Giả sử chương trình tạo một file mới:

/config/settings.json

Chương trình ghi nội dung và gọi:

fsync(fd);

Có thể dữ liệu file đã được đồng bộ, nhưng thay đổi directory entry liên quan tới tên file mới chưa được đồng bộ bền vững theo quy trình cần thiết.

Để bảo đảm một cập nhật file bằng phương pháp ghi file tạm rồi rename, ứng dụng thường cần một giao thức phù hợp:

  1. Tạo file tạm trong cùng directory.
  2. Ghi đầy đủ nội dung.
  3. Gọi fsync() trên file tạm.
  4. rename() file tạm thành tên chính thức.
  5. Gọi fsync() trên directory.

Ví dụ Python:

import os
import tempfile

directory = "/tmp"
target = os.path.join(directory, "settings.json")

fd, temp_path = tempfile.mkstemp(
    dir=directory,
    prefix=".settings-"
)

try:
    with os.fdopen(fd, "w") as f:
        f.write('{"mode": "safe"}\n')
        f.flush()
        os.fsync(f.fileno())

    os.replace(temp_path, target)

    dir_fd = os.open(
        directory,
        os.O_RDONLY | os.O_DIRECTORY
    )

    try:
        os.fsync(dir_fd)
    finally:
        os.close(dir_fd)

finally:
    if os.path.exists(temp_path):
        os.unlink(temp_path)

Đây là mẫu cơ bản cho local filesystem hỗ trợ các thao tác cần thiết. Các chi tiết về metadata, quyền, lỗi I/O, filesystem và thiết bị vẫn phải được xem xét khi dùng trong production.

Vì sao rename có ích?

Trên cùng filesystem, rename() có ngữ nghĩa atomic về việc thay đổi tên nhìn thấy bởi các process khác trong những điều kiện thích hợp.

Điều này giúp tránh việc ứng dụng khác nhìn thấy file đích mới đang được ghi dở.

Nhưng atomic visibility không đồng nghĩa với crash durability.

Đó là lý do cần phân biệt rõ rename() và fsync().

19. Liên hệ thực tế với Embedded Linux

Với board như ODROID XU4, Raspberry Pi hoặc các hệ thống Linux SoC, có thêm một vấn đề quan trọng: Device Tree.

Trên PC, nhiều thiết bị PCI/USB có cơ chế enumeration tự động.

Nhưng nhiều peripheral tích hợp trong SoC không thể tự mô tả đầy đủ bằng cơ chế như PCI.

Kernel cần biết địa chỉ thanh ghi, interrupt, clock và những thông tin phần cứng khác.

Device Tree cung cấp mô tả phần cứng để kernel có thể khởi tạo và ghép driver.

Ví dụ minh họa:

uart0: serial@12340000 {
    compatible = "vendor,soc-uart";
    reg = <0x12340000 0x1000>;
    interrupts = <42>;
    status = "okay";
};

Các giá trị này chỉ là giả định, không phải cấu hình thật của ODROID XU4.

Ý nghĩa:

  • compatible: giúp xác định loại phần cứng để match driver.
  • reg: mô tả vùng tài nguyên thanh ghi.
  • interrupts: mô tả tài nguyên interrupt theo binding.
  • status: cho biết node có được bật hay không.

Trong driver platform, thông tin Device Tree có thể được sử dụng để lấy resource, ánh xạ MMIO và đăng ký interrupt.

Một lỗi thường gặp khi làm board bring-up là:

Driver đã được build
        ↓
Module có thể đã nạp
        ↓
Nhưng không có thiết bị được match
        ↓
probe() không chạy

Nguyên nhân có thể nằm ở Device Tree, compatible, trạng thái node, bus hoặc cơ chế tạo platform device, chứ không nhất thiết ở mã driver.

21. Những câu hỏi phỏng vấn và tình huống thực tế

❓ Tự kiểm tra kiến thức

0/7 đáp án đã mở

Tại sao lsmod không hiển thị driver nhưng thiết bị vẫn hoạt động?

Vì driver có thể được build trực tiếp vào kernel. Ngoài ra, thiết bị có thể được phục vụ qua một hoặc nhiều tầng driver khác, nên tên module bạn kỳ vọng không nhất thiết xuất hiện.

Driver và firmware khác nhau thế nào?

Driver là mã phía hệ điều hành để tích hợp và điều khiển thiết bị. Firmware là mã hoặc dữ liệu phục vụ hoạt động của thiết bị/nền tảng, đôi khi chạy trên bộ xử lý riêng bên trong thiết bị.

DMA có phải luôn nhanh hơn CPU copy không?

Không. DMA có chi phí setup, mapping, synchronization và completion. Với transfer nhỏ, CPU copy có thể hiệu quả hơn tùy nền tảng.

Interrupt luôn tốt hơn polling?

Không. Polling có thể giảm overhead và độ trễ trong những tình huống phù hợp, đặc biệt khi công việc đến liên tục. Interrupt thường có lợi khi không muốn CPU bận chờ.

O_DIRECT có bảo đảm dữ liệu không mất khi mất điện?

Không. O_DIRECT chủ yếu ảnh hưởng đường đi cache của dữ liệu. Durability là vấn đề riêng liên quan đến đồng bộ, filesystem và bảo đảm thiết bị.

Tại sao fsync(file) đôi khi chưa đủ để bảo vệ một file mới tạo?

Vì directory entry hoặc thao tác rename có thể cần được đồng bộ riêng. Quy trình crash-safe thường phải xem xét fsync directory.

Tại sao /dev/ttyUSB0 thay đổi sau reboot?

Tên được cấp theo cơ chế phát hiện và đăng ký thiết bị, nên thứ tự có thể thay đổi. Có thể dùng udev symlink theo serial hoặc physical path để có tên ổn định hơn.

22. Tổng kết — Ghép toàn bộ kiến thức thành một bức tranh

Sau bài này, hãy nhớ ba đường đi quan trọng.

Đường điều khiển thiết bị:

Device
   ↓
Bus / Device Model
   ↓
Driver Matching
   ↓
probe()
   ↓
Device Ready
   ↓
User-space Interface

Đường truyền dữ liệu:

Application
   ↓
System Call
   ↓
Kernel Subsystem
   ↓
Driver
   ↓
Descriptor / DMA
   ↓
Hardware
   ↓
Interrupt / Completion

Đường bảo đảm dữ liệu lưu trữ:

Application Buffer
   ↓ flush()
Kernel Page Cache
   ↓ writeback / fsync()
Filesystem + Block Layer
   ↓
Storage Controller
   ↓
Persistent Media

Ba luồng này liên quan chặt chẽ nhưng giải quyết ba vấn đề khác nhau: thiết bị được nhận diện như thế nào, dữ liệu được truyền như thế nào và dữ liệu được lưu bền như thế nào.
