Tài liệu học tập độc lập, có code, bảng, sơ đồ và mô phỏng tương tác bằng JavaScript.

Mục lục — 45 chủ đề

Phần I — Tại sao Linux cần Package Manager?

1. Hãy tưởng tượng một máy Linux hoàn toàn mới

Bạn vừa cài Ubuntu Server và muốn gọi API bằng curl. Nhưng shell báo không tìm thấy lệnh.

curl https://example.com
# curl: command not found

Câu hỏi quan trọng không chỉ là “cài curl thế nào?” mà là: ai đưa chương trình vào máy, ai theo dõi phiên bản, ai quản lý thư viện phụ thuộc, và ai biết phải xóa file nào khi gỡ?

2. Nếu không có Package Manager thì sao?

Bạn tải source và tự biên dịch:

./configure
make
sudo make install
# error: OpenSSL headers not found

Ứng dụng có thể phụ thuộc OpenSSL, zlib và các thư viện khác. Giống một quán cà phê cần điện, nước, máy pha và nguyên liệu, ứng dụng cần một hệ sinh thái phụ thuộc.

Ứng dụng curl
↙ ↓ ↘
OpenSSL
zlib / libnghttp2
↓
Các thư viện nền khác

Minh họa quan hệ phụ thuộc; cấu hình build thực tế có thể khác.

3. Package là gì?

Package là đơn vị phân phối phần mềm chứa executable, thư viện, metadata, dependency, thông tin file và đôi khi maintainer scripts. Ví dụ tên file:

curl_8.5.0-2ubuntu10_amd64.deb
Thành phầnÝ nghĩa
curlTên package
8.5.0Phiên bản upstream
2ubuntu10Revision đóng gói
amd64Kiến trúc đích
.debĐịnh dạng Debian
Phản biện: Package có phải chỉ là file nén? Không. Metadata và scripts cho phép quản lý vòng đời, đồng thời làm package không tin cậy trở thành rủi ro bảo mật.

Phần II — Repository, APT và dpkg

4. Repository là gì?

Repository là kho package và metadata. APT giống người điều phối lựa chọn hàng, dpkg giống bộ phận quản lý lắp đặt tại máy.

6. apt update có cập nhật phần mềm không?

apt update cập nhật metadata, không tự nâng cấp executable. apt upgrade mới thực hiện nâng cấp theo các quy tắc dependency phù hợp; apt full-upgrade có thể gỡ package.

sudo apt update
sudo apt upgrade
Mô phỏng APT update / upgrade
APT biết phiên bản: 8.4
Đã cài: 8.4

Mô phỏng, không thực thi lệnh. Phiên bản chỉ minh họa.

Phần III — Dependency và Dependency Hell

7. Dependency là gì?

Application A
 ├── libnetwork >= 2.0
 ├── libcrypto >= 3.0
 └── libc >= 2.35

Dependency là ràng buộc một thành phần cần thành phần khác để cài đặt hoặc hoạt động. Thiếu version phù hợp có thể khiến resolver từ chối cài.

8. Dependency Hell

Application A → libfoo 1.x
Application B → libfoo 2.x

Hai SONAME khác nhau có thể cùng tồn tại, nhưng conflict file, version constraint, hoặc ABI không tương thích vẫn có thể khiến hệ thống khó quản lý.

9. Tại sao không nên trộn repository?

Trộn release có thể kéo theo nâng cấp thư viện nền ngoài ý muốn. Hãy xem policy và mô phỏng transaction trước khi xác nhận.

apt-cache policy curl
apt-cache depends curl
sudo apt -s install curl
Nếu APT muốn gỡ hàng chục package để cài một công cụ nhỏ, hãy dừng và tìm nguyên nhân, không nhấn Y theo thói quen.

Phần IV — Trust và chữ ký Repository

10. Cài package từ Internet có đáng tin không?

Chữ ký xác thực nguồn metadata và tính toàn vẹn chuỗi phân phối; nó không bảo đảm phần mềm không có bug hoặc mã độc.

11. Chuỗi xác thực APT

Trusted signing key
↓
Signed Release / InRelease
↓
Packages metadata + hashes
↓
Downloaded .deb files

Khi thêm nguồn, cần xác minh người giữ khóa, release tương ứng và cấu hình Signed-By. Không chạy script tải từ Internet bằng sudo mà chưa xem xét nguồn và nội dung.

Phần V — Executable và PATH

12. Lệnh python3 được tìm như thế nào?

python3 --version
type -a python3
command -v python3
echo "$PATH"

Shell có thể xử lý alias, function, builtin hoặc tìm executable trong PATH. PATH không phải cơ chế tìm shared library.

13. Vấn đề bảo mật PATH

Nếu thư mục không đáng tin đứng trước /usr/bin, executable giả mạo có thể được chạy. Kiểm tra bằng type -a và dùng đường dẫn tuyệt đối khi thích hợp.

Phần VI — ELF

14. ELF là gì?

Executable and Linkable Format là định dạng phổ biến của executable, object file, shared object và core dump trên Linux.

file /usr/bin/python3

17. Vì sao .bss không chứa hàng triệu byte zero?

static char buffer[1024 * 1024];

ELF có thể biểu diễn vùng zero-initialized bằng kích thước bộ nhớ lớn hơn dữ liệu thực lưu trong file. Điều này tiết kiệm dung lượng.

21. Dynamic linker là gì?

Với ELF động, kernel nạp interpreter từ PT_INTERP. Dynamic linker giải quyết shared objects, relocation, symbol resolution và khởi tạo liên quan.

readelf -l /usr/bin/python3
# INTERP: Requesting program interpreter ...

Phần IX — Tìm shared library

22. PATH khác đường tìm thư viện

Loader có thể xét RPATH, RUNPATH, LD_LIBRARY_PATH, ldconfig cache và các thư mục mặc định, theo quy tắc chính xác tùy tag và ngữ cảnh.

23. RPATH và RUNPATH

/opt/myapp/
├── bin/
│   └── app
└── lib/
    └── libcustom.so

# RUNPATH: $ORIGIN/../lib
readelf -d /opt/myapp/bin/app

$ORIGIN là vị trí thư mục chứa ELF object được xét. RPATH và RUNPATH có quy tắc khác nhau đối với dependency gián tiếp.

24. Vì sao không sửa LD_LIBRARY_PATH toàn hệ thống?

export LD_LIBRARY_PATH=/opt/oldlibs

Điều này có thể làm nhiều ứng dụng nạp nhầm thư viện, lỗi ABI và tăng rủi ro bảo mật. Hãy dùng cấu hình ứng dụng có kiểm soát.

Phần X — ABI và SONAME

25. API khác ABI thế nào?

API là giao diện ở mức source. ABI là hợp đồng ở mức binary: calling convention, symbol, data layout, stack, register, version...

int add(int a, int b);

26. Lỗi ABI

error while loading shared libraries:
libfoo.so.1: cannot open shared object file

version `GLIBC_2.xx' not found

Không symlink bừa libfoo.so.2 thành libfoo.so.1; tên khác có thể phản ánh ABI không tương thích.

27. SONAME

libexample.so      -> libexample.so.1
libexample.so.1    -> libexample.so.1.2.3
libexample.so.1.2.3

readelf -d /usr/lib/x86_64-linux-gnu/libz.so.1

SONAME thường là tên dependency được ghi trong binary. File phát triển, SONAME và file thực tế có thể được tổ chức thành chuỗi symlink.

Phần XI — Lab kiểm kê executable

28. Tìm executable và package sở hữu

command -v python3
type -a python3
readlink -f "$(command -v python3)"
dpkg-query -S /usr/bin/python3
dpkg-query -W python3
apt-cache policy python3

Symlink có thể thuộc package khác với file đích. dpkg-query đọc database package chứ không xác nhận file không bị sửa.

29. Kiểm tra ELF và dependencies

file /usr/bin/python3
readelf -h /usr/bin/python3
readelf -l /usr/bin/python3
readelf -d /usr/bin/python3
ldd /usr/bin/python3

Cẩn trọng: Không chạy ldd trên binary không tin cậy. Ưu tiên phân tích tĩnh bằng readelf; NEEDED chỉ hiển thị dependency trực tiếp được ghi trong dynamic section.

Phần XIII — Process vẫn dùng thư viện cũ

31. Tại sao upgrade xong vẫn cần restart?

Process có thể còn memory mapping của file thư viện cũ dù package trên đĩa đã được thay thế. Bản vá trên đĩa chưa chắc đã được process sử dụng.

Mô phỏng thư viện cũ và mới
Library trên đĩa: v1
Library process đang dùng: v1

Process đang sử dụng v1.

sudo grep '(deleted)' /proc/<PID>/maps
sudo lsof +L1

Đây là dấu hiệu hỗ trợ kiểm tra file cũ bị unlink. Nếu cập nhật kernel, có thể cần reboot để chạy kernel mới.

Phần XIV — Rollback và production

32. Một tình huống production: nâng cấp thành công nhưng hệ thống hỏng

Ứng dụng bán hàng v1 sử dụng bảng users(id,name). Bản v2 thay bằng users(id,first_name,last_name). Sau migration, ứng dụng v2 lỗi; downgrade binary về v1 không giúp vì database vẫn dùng schema v2.

-- Schema v1
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100)
);

-- Schema v2
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    first_name VARCHAR(50),
    last_name VARCHAR(50)
);

sudo apt install myapp=1.0

Package downgrade ≠ System rollback. Trạng thái phải xét cả binary, thư viện, cấu hình, database schema, dữ liệu, service và kernel.

Mô phỏng bốn trạng thái rollback
Application: v1.0
Database: Schema v1

Hoạt động bình thường

Executable và database cùng sử dụng schema v1.

1 / 4

Expand–Migrate–Contract

Để rollback dễ hơn, hãy thêm cột mới nhưng giữ cột cũ (Expand), chuyển dữ liệu và cập nhật logic (Migrate), chỉ xóa cột cũ khi không còn client phụ thuộc (Contract).

ALTER TABLE users
ADD COLUMN first_name VARCHAR(50),
ADD COLUMN last_name VARCHAR(50);

-- Chuyển dữ liệu theo quy tắc nghiệp vụ và xử lý ghi đồng thời

ALTER TABLE users DROP COLUMN name;
Vì sao không restore database ngay? Vì có thể mất giao dịch phát sinh sau backup. Cần xác định RPO, RTO và phương án đối soát dữ liệu.

Phần XV — Python Virtual Environment

33. Tại sao pip có thể làm hỏng hệ thống?

Ghi đè thư viện Python do distro quản lý có thể gây xung đột công cụ hệ thống. PEP 668 giúp đánh dấu môi trường Python được quản lý bên ngoài.

System Python — /usr/bin/python3
↙ ↘
Project A .venv
Package X 1.x, Y 2.x
Project B .venv
Package X 2.x, Z 3.x
sudo apt update
sudo apt install python3-venv
mkdir -p ~/python-lab
cd ~/python-lab
python3 -m venv .venv
source .venv/bin/activate
python -m pip install requests
which python
python -m pip --version
deactivate

venv cô lập dependency Python, không cô lập kernel, process và filesystem như một container được cấu hình phù hợp.

Phần XVII — Debug executable

35. command not found

echo "$PATH"
type -a myapp
command -v myapp
ls -l /opt/myapp/bin/myapp
/opt/myapp/bin/myapp

Chưa chắc package thiếu: có thể PATH sai hoặc shell đang ở môi trường khác.

36. No such file or directory dù file tồn tại

ls -l ./app
file ./app
readelf -l ./app
# Requesting program interpreter: /lib64/ld-linux-x86-64.so.2

ELF interpreter hoặc shebang interpreter có thể không tồn tại; ENOENT không nhất thiết chỉ file app bị thiếu.

37. Exec format error

file ./app
uname -m
readelf -h ./app
aarch64-linux-gnu-gcc main.c -o app

Binary x86-64 không tự chạy trên AArch64. Cần toolchain, ABI, libc và sysroot đúng.

38. GLIBC_x.y not found

getconf GNU_LIBC_VERSION
readelf --version-info ./app

Ứng dụng yêu cầu symbol version mà glibc trên target không có. Không copy bừa glibc mới vào /lib; nên build với sysroot tương thích hoặc nâng cấp môi trường có kiểm soát.

Phần XVIII — APT pinning

39. Tại sao APT chọn phiên bản này?

apt-cache policy libfoo
# Installed: 1.0
# Candidate: 2.0
# Version table:
#    2.0 500
#    1.0 500

APT dựa trên version và priority policy. Pinning cho phép ưu tiên nguồn/release, nhưng cấu hình sai có thể tạo lựa chọn version ngoài ý muốn.

Phần XIX — Package Lock

40. Vì sao không xóa lock khi APT đang chạy?

Hai package manager ghi cùng database có thể gây bất nhất. Lock giúp ngăn transaction xung đột. Đừng xóa /var/lib/dpkg/lock một cách máy móc.

ps aux | grep -E '[a]pt|[d]pkg'
sudo fuser -v /var/lib/dpkg/lock-frontend
sudo dpkg --audit
sudo dpkg --configure -a

Chỉ xem xét các lệnh phục hồi sau khi chắc chắn không còn transaction hợp lệ đang chạy và đã xác định trạng thái lỗi.

Phần XX — Embedded Linux và A/B update

41. Vì sao Embedded Linux không luôn dùng APT?

Thiết bị công nghiệp thường cần image tái lập, giới hạn flash và cập nhật an toàn. Buildroot thường tạo root filesystem image; Yocto có thể tạo package feed hoặc image tùy cấu hình.

Bootloader
↙ ↘
Slot A
Firmware v1
Slot B
Firmware v2
Mô phỏng cập nhật firmware A/B
Slot A — v1.0
Active
Slot B — v2.0
Inactive

Thiết bị đang sử dụng firmware v1.0.

Mô phỏng. Hệ thống thực còn cần boot counter, image verification, xử lý mất điện và dữ liệu dùng chung.

A/B update không bảo đảm rollback dữ liệu: nếu cả hai slot dùng chung phân vùng data đã migration, firmware cũ vẫn có thể lỗi.
