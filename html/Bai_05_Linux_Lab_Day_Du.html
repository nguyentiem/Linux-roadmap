Bài 05 — Yêu cầu phần cứng, cài đặt và môi trường Lab

Giáo trình Linux từ cơ bản đến Embedded Linux. Tài liệu HTML độc lập, có bảng, code, sơ đồ và các mô phỏng tương tác. Nội dung được biên soạn từ bài gốc và các phần giải thích, mở rộng trong cuộc hội thoại.

Mục tiêu và chuẩn bị

Hoàn thành bài 01–04. Chuẩn bị máy host có công cụ ảo hóa, ISO từ website chính thức và dung lượng trống. Mục tiêu là có VM có thể khôi phục để dùng xuyên suốt giáo trình.

Phần I — Tại sao phải xây dựng môi trường Lab?

1. Đặt vấn đề: Học Linux bằng cách nào?

Học Linux chỉ bằng cách đọc lệnh giống như học sửa ô tô mà không mở nắp capo. Khi học filesystem, bạn có thể muốn thử mount; khi học service, bạn có thể muốn thay đổi systemd; khi học mạng, bạn có thể vô tình mất SSH. Thử trực tiếp trên máy chính tạo rủi ro không cần thiết.

Lab là môi trường được chuẩn bị có chủ đích để thực hành và kiểm chứng. Một lab tốt phải có isolation (cô lập), reproducibility (tái lập), observability (quan sát) và recoverability (khôi phục).

Câu hỏi phản biện: Vì sao không cài lại Linux mỗi khi lỗi? Vì cài lại mất thời gian, khó tái hiện điều kiện ban đầu và không phải một chiến lược khôi phục tốt.

2. Lab là gì?

Tưởng tượng phòng thí nghiệm điện tử: có nguồn giới hạn dòng, đồng hồ đo, linh kiện thay thế và quy trình an toàn. VM là phòng thí nghiệm tương tự dành cho hệ điều hành. Bạn được phép thử nghiệm, quan sát, ghi nhận, rồi khôi phục.

3. Máy thật, máy ảo và container khác nhau thế nào?

Tiêu chí Máy thật Máy ảo Container
Kernel riêng Có Có Thường chia sẻ kernel host
Boot OS hoàn chỉnh Có Có Không boot kernel riêng
Lab bootloader Có Có Không phù hợp
Snapshot Tùy công cụ Thuận tiện Cơ chế khác
Cô lập Vật lý Cấp VM Cấp process/namespace

Ví dụ: docker run --rm ubuntu uname -r hiển thị kernel của môi trường chạy container, không phải một kernel riêng nằm trong Ubuntu image. Vì vậy container không thay thế VM cho bài boot, kernel và partition hệ thống.

Phần II — Hiểu đúng yêu cầu phần cứng

4. Một hệ điều hành Linux cần những gì?

Không có con số RAM hay dung lượng tối thiểu chung cho mọi Linux. Phải tách bốn vấn đề: kiến trúc CPU, distro/installer, driver thiết bị và workload ứng dụng. Một thiết bị nhúng tối giản khác hoàn toàn Ubuntu Desktop hoặc database server.

5. CPU Architecture — ISA

ISA (Instruction Set Architecture) là tập chỉ thị CPU hiểu. x86-64, ARMv7, AArch64 và RISC-V là những ví dụ. Mã máy x86-64 không chạy trực tiếp trên CPU ARM chỉ vì cùng sử dụng Linux.

#include <stdio.h>
int main(void) { printf("Hello Linux!\\n"); return 0; }

gcc main.c -o hello_x86
aarch64-linux-gnu-gcc main.c -o hello_arm64
file hello_x86 hello_arm64

Tại sao? Compiler sinh chỉ thị máy khác nhau. Ngoài ISA, còn cần tương thích ABI, dynamic linker và thư viện.

6. Virtualization khác Emulation

Virtualization thường chạy guest cùng ISA host, tận dụng hỗ trợ CPU và thực thi nhiều chỉ thị trực tiếp. Emulation mô phỏng ISA hoặc phần cứng khác, thường có chi phí hiệu năng lớn hơn. QEMU có thể làm cả hai: QEMU TCG để emulation, QEMU+KVM để acceleration.

Virtualization Emulation
ISA Thường giống host Có thể khác
Tốc độ Thường gần native Thường chậm hơn
Ví dụ KVM, Hyper-V QEMU TCG

7. vCPU là gì?

vCPU là CPU logic hypervisor trình bày cho guest, không phải một lõi vật lý được dành riêng vĩnh viễn. Cấp 8 vCPU không đảm bảo nhanh hơn 2 vCPU: phụ thuộc số luồng, scheduler và tải host. Nguyên tắc senior: đo trước, cấp tài nguyên theo nhu cầu.

8. RAM và swap

RAM là bàn làm việc; SSD là tủ tài liệu. Swap giống chuyển tài liệu từ bàn sang tủ: giúp giải phóng chỗ nhưng chậm hơn nhiều. Thiếu RAM có thể dẫn tới reclaim, swap, độ trễ lớn hoặc OOM killer. Với host 16 GB, ba VM 4 GB cùng host 5 GB có thể gây memory pressure nếu dùng hết.

free -h
cat /proc/meminfo

Câu hỏi: MemFree thấp có nghĩa RAM đã hết? Không; Linux dùng RAM làm page cache. MemAvailable thường hữu ích hơn khi đánh giá bộ nhớ có thể cấp cho workload mới.

9. Disk và Thin Provisioning

Với lab CLI, cấu hình khởi đầu hợp lý là 2 vCPU, 2–4 GB RAM, 25–40 GB disk. Host 16 GB RAM và SSD trống khoảng 100 GB giúp thuận tiện cho lab nhỏ; build kernel và nhiều VM cần thêm. Đây là ngân sách học tập, không phải tối thiểu chính thức của distro.

Thin provisioning cho phép ổ ảo được khai báo 40 GB nhưng file trên host chỉ lớn dần khi ghi. Nếu host hết dung lượng, guest vẫn có thể gặp lỗi I/O dù ổ ảo báo còn chỗ.

Phần III — Virtualization và hypervisor

10. Hypervisor là gì?

Hypervisor là lớp quản lý tài nguyên phần cứng ảo. Type 1 thường mô tả hypervisor gần phần cứng như ESXi; Type 2 thường mô tả phần mềm ảo hóa chạy trong host OS như VirtualBox. KVM và Hyper-V có kiến trúc thực tế tinh tế hơn cách phân loại đơn giản.

11. VT-x, AMD-V và nested virtualization

Intel VT-x và AMD-V/SVM cung cấp hỗ trợ ảo hóa phần cứng. Kiểm tra trên Linux host:

lscpu | grep -i virtualization
grep -E 'vmx|svm' /proc/cpuinfo

Flag xuất hiện chưa đảm bảo hypervisor được cấu hình đúng. Firmware, quyền và môi trường host vẫn quan trọng. Nested virtualization là chạy hypervisor trong guest VM; chỉ cần khi guest phải tạo VM tiếp, không cần cho một Linux VM thông thường.

Phần IV — ISO, checksum và boot

12. ISO là gì?

ISO là image của phương tiện cài đặt/khởi động, có thể chứa bootloader, kernel, initramfs, installer và package metadata. Gắn ISO vào VM tương đương đưa đĩa cài đặt vào ổ quang ảo.

13. Tại sao kiểm tra checksum?

sha256sum debian-installer.iso

So sánh SHA-256 với giá trị do nhà phát hành công bố để kiểm tra tính toàn vẹn. Nếu kẻ tấn công thay cả ISO và checksum cùng nguồn, checksum không đủ xác thực. Chữ ký số với khóa công khai đã xác minh giúp xác thực nguồn gốc.

14. Boot flow: từ nguồn điện đến shell

Quá trình boot PC thường có firmware UEFI/BIOS → bootloader → kernel → initramfs nếu cần → rootfs → PID 1 → login/shell. Firmware tìm thiết bị boot; bootloader nạp kernel; kernel khởi tạo bộ nhớ, scheduler, driver; initramfs có thể chuẩn bị rootfs; init/systemd khởi chạy user space.

ps -p 1 -o pid,comm,args

Câu hỏi: PID 1 có vai trò gì? Đây là tiến trình init đặc biệt, quản lý các tiến trình/dịch vụ theo mô hình init được dùng; nếu init chính kết thúc bất thường, hệ thống thường không thể tiếp tục bình thường.

Phần V — Quy trình cài Linux VM

15. Chọn distro

Debian và Ubuntu Server phù hợp để học CLI, Bash, APT và systemd. Dùng ISO chính thức, kiểm tra kiến trúc/phiên bản tài liệu.

16. Chọn phần mềm ảo hóa

Trên Windows có VirtualBox, VMware Workstation, Hyper-V; trên Linux có KVM/QEMU và libvirt. Giao diện và tùy chọn phụ thuộc phiên bản hypervisor.

17. Tạo VM

Trường Ví dụ cấu hình
Name linux-lab-01
CPU 2 vCPU
RAM 4096 MB
Disk 40 GB, ổ ảo mới
Network NAT
Firmware UEFI nếu hỗ trợ
Installation ISO chính thức

Chỉ cấp ổ ảo mới để tránh xóa dữ liệu máy thật. Chọn CLI/server, tạo user thường có quyền sudo, ghi hostname và cấu hình mạng. Sau cài đặt tháo ISO, boot lại từ ổ ảo, cập nhật package.

18. Disk, partition và filesystem

Disk là thiết bị lưu trữ; partition là vùng phân chia; filesystem là quy tắc tổ chức file; mount point là vị trí trong cây / nơi filesystem xuất hiện. Tưởng tượng disk là tòa nhà, partition là phòng, filesystem là hệ thống tủ kệ.

19. Mount root filesystem

findmnt /
df -h /
lsblk -f

/ có thể nằm trên /dev/vda2, LVM, mapper hoặc cấu trúc khác. Linux tổ chức filesystem trong một cây thư mục thống nhất, không cần ký tự ổ đĩa như C: hay D:.

Phần VI — Networking cho Lab

20. Card mạng ảo

Hypervisor trình bày virtual NIC cho guest. Guest vẫn cần driver, cấu hình IP và routing. Host có Internet không đảm bảo guest có mạng.

21. NAT

NAT thường cho phép VM truy cập Internet qua cơ chế dịch địa chỉ; inbound từ LAN thường cần port forwarding hoặc cấu hình khác. NAT không phải bảo mật tuyệt đối.

22. Bridged

VM tham gia mạng vật lý, có thể nhận IP từ DHCP LAN và được thiết bị khác truy cập nếu chính sách mạng cho phép. Phù hợp lab SSH/server nhưng tăng mức phơi bày dịch vụ; Wi-Fi và mạng doanh nghiệp có thể hạn chế.

23. Host-only và Internal

Host-only thường cho host giao tiếp với VM trong mạng riêng; Internal thường cô lập giữa các VM cùng mạng. Phù hợp lab firewall, database và thử nghiệm không muốn công khai ra LAN.

24. Chọn mô hình mạng

Bắt đầu bằng NAT; chuyển Bridged khi cần board thật hoặc máy khác truy cập VM; chọn mạng cô lập khi cần kiểm thử nhiều node. Sử dụng mô phỏng tương tác phía dưới để so sánh.

Phần VII — Kiểm tra sau cài đặt

25. Kiểm tra distro

cat /etc/os-release

Distro khác kernel. PRETTY_NAME mô tả hệ điều hành phân phối, không nhất thiết là phiên bản kernel.

26. Kiểm tra kernel

uname -r
uname -a
uname -m

uname -r cho biết kernel release; uname -m cho biết kiến trúc theo kernel.

27. Kiểm tra user

id
id -u

UID 0 là root; user thường nên thực hiện công việc hàng ngày, chỉ nâng quyền khi cần.

28. Kiểm tra sudo

sudo -v
sudo -l

sudo -v kiểm tra/làm mới xác thực theo chính sách, không đảm bảo user được chạy mọi lệnh. Dùng visudo khi chỉnh sửa sudoers.

29. Kiểm tra filesystem root

findmnt /
df -h /
df -i /

df -h xem dung lượng block; df -i xem inode. Có thể hết inode dù còn block trống nếu quá nhiều file nhỏ.

30. Kiểm tra IP

ip -br addr
ip link
ip route
ping -c 3 1.1.1.1
getent hosts debian.org
sudo apt update

Phân biệt interface, IP, route, DNS và repository. ICMP có thể bị chặn, nên ping thất bại chưa đủ kết luận mất toàn bộ Internet.

31. Kiểm tra PID 1

ps -p 1 -o comm=

Nếu nhánh lab mặc định dùng systemd, kỳ vọng systemd; nếu khác, cần kiểm tra init thực tế.

32. Tạo thư mục Lab

mkdir -p "$HOME/linux-lab"
ls -ld "$HOME/linux-lab"

$HOME linh hoạt hơn hardcode /home/student.

Phần VIII — Snapshot và khả năng phục hồi

33. Snapshot là gì?

Snapshot lưu trạng thái máy ảo hoặc storage tại một thời điểm. Tương tự checkpoint trong trò chơi: trước thí nghiệm khó, lưu một mốc để quay lại.

34. Snapshot hoạt động như thế nào?

Một số hypervisor dùng copy-on-write và delta disk. Snapshot có RAM khác snapshot disk-only. Snapshot không thay backup độc lập vì có thể phụ thuộc base disk, metadata và cùng storage host. Snapshot dài hạn có thể tăng độ phức tạp và dung lượng.

Phần XII — Lab: tạo, phá và khôi phục

35. Chuẩn bị baseline

Baseline là trạng thái chuẩn đã kiểm tra; snapshot là một phương tiện lưu trạng thái. Trước khi chụp, xác nhận boot, kernel, user, sudo, rootfs, network và repository.

cat /etc/os-release
uname -r
id
sudo -v
findmnt /
df -h /
ip -br addr
ip route
ps -p 1 -o comm=
sudo apt update
sudo apt upgrade
sudo reboot

Sau khi kiểm tra ổn định, tắt sạch:

sudo shutdown -h now

Tạo snapshot tên baseline-clean, ghi mô tả như Fresh installation; packages updated; network and sudo verified. Tắt sạch cho hệ thống cơ hội đồng bộ page cache và dừng service. Journaling không bảo đảm mọi dữ liệu ứng dụng đều được bảo toàn sau tắt đột ngột.

Câu hỏi phản biện: Tại sao snapshot tồn tại chưa có nghĩa recovery đáng tin? Vì chỉ có thử restore mới chứng minh đường khôi phục thực sự hoạt động.

36. Tạo file marker sau snapshot

mkdir -p "$HOME/linux-lab"
touch "$HOME/linux-lab/marker.txt"
echo "This file was created after snapshot" > "$HOME/linux-lab/marker.txt"
cat "$HOME/linux-lab/marker.txt"
stat "$HOME/linux-lab/marker.txt"

Marker là dấu vết để kiểm chứng trạng thái. stat cho thấy kích thước, quyền, owner, inode và timestamp.

37. Restore snapshot

Tắt VM, chọn baseline-clean trong hypervisor, Restore rồi boot lại. Chỉ thực hiện khi không có dữ liệu cần giữ sau snapshot.

ls -l "$HOME/linux-lab/marker.txt"

Nếu marker được tạo sau snapshot, sau restore đúng sẽ nhận No such file or directory. Dữ liệu ở shared folder, USB hoặc database ngoài VM có thể không thuộc phạm vi snapshot.

Phần XIII — Troubleshooting

38. Tư duy troubleshooting của senior

Quan sát triệu chứng → thu thập bằng chứng → xác định tầng lỗi → đặt giả thuyết → thử kiểm chứng → sửa tối thiểu → xác minh → ghi nhận. Đừng đổi DNS khi card mạng chưa kết nối; đừng cài lại OS khi boot order sai.

39. VM quay lại màn hình installer

Kiểm tra ISO còn gắn, boot order, ổ ảo, chế độ UEFI/Legacy và bootloader. Nếu tháo ISO mà báo No bootable medium, phải kiểm tra ổ ảo, EFI System Partition và cài đặt bootloader.

40. VM không có mạng

ip -br link
ip -br addr
ip route
ping -c 3 1.1.1.1
getent hosts debian.org
sudo apt update

Đi từ NIC → interface → IP → route → kết nối IP → DNS → repository. Các lỗi DNS, TLS, HTTP và repository signature có nguyên nhân khác nhau.

41. Sudo không hoạt động

sudo: command not found là thiếu lệnh/PATH; user is not in sudoers là authorization. Kiểm tra:

command -v sudo
id
groups

Authentication là xác minh bạn là ai; authorization là bạn được phép làm gì. Khắc phục qua console quản trị và chính sách distro.

42. VM rất chậm

top
uptime
free -h
df -h
lsblk
# nếu đã cài sysstat
iostat -xz 1

Kiểm tra CPU, memory pressure, swap, storage I/O và host contention. Load average cao không nhất thiết CPU 100%: Linux còn tính task runnable và một số task chờ không ngắt được.

Phần XIV — Thiết kế Lab tái lập

43. Configuration Inventory

Inventory ghi hostname, distro, kernel, architecture, CPU, RAM, disk, network, init và snapshot. Có thể thu thập tự động:

#!/usr/bin/env bash
set -eu
OUTPUT="$HOME/linux-lab/machine.txt"
mkdir -p "$HOME/linux-lab"
{
  echo '=== DATE ==='; date -Is
  echo '=== HOSTNAME ==='; hostname
  echo '=== OS ==='; cat /etc/os-release
  echo '=== KERNEL ==='; uname -a
  echo '=== CPU ==='; lscpu
  echo '=== MEMORY ==='; free -h
  echo '=== STORAGE ==='; lsblk -f
  echo '=== ROOT ==='; findmnt /
  echo '=== NETWORK ==='; ip -br addr
  echo '=== ROUTES ==='; ip route
  echo '=== INIT ==='; ps -p 1 -o pid,comm,args
} > "$OUTPUT"
echo "Inventory saved to: $OUTPUT"

Đừng chia sẻ inventory bừa bãi vì có thể chứa thông tin mạng và hệ thống.

44. Reproducibility và Infrastructure as Code

Một lab tái lập cần phiên bản OS/kernel, cấu hình VM, dữ liệu thử nghiệm, cách triển khai và rollback rõ ràng. Snapshot lưu trạng thái; IaC mô tả cách tạo trạng thái.

Vagrant.configure("2") do |config|
  config.vm.box = "generic/debian12"
  config.vm.provider "virtualbox" do |vb|
    vb.memory = 4096
    vb.cpus = 2
  end
end

Ví dụ phụ thuộc box và provider có còn được cung cấp, tương thích hay không. Có thể tìm hiểu Vagrant, cloud-init, Ansible, Packer khi đã hiểu quy trình thủ công.

Phần XV — Liên hệ với Embedded Linux

45. VM Lab và Board thật

Vấn đề: Vì sao học Linux x86-64 VM nếu đích là board ARM? VM cung cấp development environment ổn định để lập trình, cross-compile, build rootfs, kiểm tra shell, filesystem và mạng; board thật cung cấp SoC, peripheral và boot flow thực tế.

#include <stdio.h>
int main(void) { printf("Hello Embedded Linux!\\n"); return 0; }

gcc main.c -o hello_x86
arm-linux-gnueabihf-gcc main.c -o hello_arm
file hello_x86 hello_arm

Nếu copy binary x86-64 sang ARM, có thể gặp Exec format error. Đúng ISA vẫn chưa đủ nếu ABI, linker hoặc thư viện không phù hợp.

Odroid XU4 dùng Exynos 5422 với lõi Cortex-A15/A7 ARMv7-A 32-bit, do đó thường cần toolchain ARM32 tương thích, không phải mặc định AArch64.

45.2. Build, Host và Target

Trong phát triển ứng dụng nhúng, PC thường được gọi host development machine và board là target. Trong thuật ngữ xây GCC: build = máy thực hiện build; host = máy chạy công cụ đang build; target = kiến trúc mà compiler sinh mã. Phân biệt để không chọn sai sysroot/toolchain.

45.3. Native vs Cross-Compilation

Native compiler sinh binary cho chính kiến trúc đang chạy. Cross-compiler chạy trên PC nhưng sinh binary cho target khác. Cross-compilation hữu ích khi build kernel, rootfs, nhiều package hoặc target thiếu RAM/CPU. Native compilation trên board vẫn hợp lý với chương trình nhỏ.

46. Embedded Linux Boot Flow

Một chuỗi tổng quát: Power On → Boot ROM → SPL/firmware nếu có → U-Boot → Linux kernel → root filesystem → init/application. Boot ROM tìm nguồn boot; SPL có thể khởi tạo DRAM; U-Boot nạp kernel, DTB, initramfs và thiết lập boot arguments. Không phải board nào cũng dùng SPL hoặc U-Boot.

Tại sao kernel không tự boot ngay? Vì DRAM, image, trạng thái CPU và thông tin nền tảng có thể cần chuẩn bị trước.

47. Device Tree

Device Tree mô tả phần cứng cố định của SoC như UART, SPI, I2C, GPIO, interrupt, địa chỉ MMIO. DTS được biên dịch thành DTB bằng dtc.

uart0: serial@10000000 {
    compatible = "vendor,soc-uart";
    reg = <0x10000000 0x1000>;
    status = "okay";
};

Đây là ví dụ minh họa, không phải DTS thực tế của XU4. Device Tree là bản mô tả; driver là mã điều khiển. Chỉ có DT không thay được driver.

48. Root Filesystem trên Embedded Linux

Rootfs cung cấp /bin, /etc, /lib, /usr, /dev, /proc, /sys và ứng dụng. Có thể tạo bằng Buildroot, Yocto, Debian rootfs hoặc BusyBox. BusyBox gom nhiều tiện ích Unix vào một executable, thường tiết kiệm dung lượng nhưng không phải mọi option đều giống GNU coreutils.

49. Kernel image, Rootfs image và Firmware image

Kernel image như Image, zImage, uImage chứa kernel theo định dạng boot phù hợp. Rootfs image như rootfs.ext4 hoặc rootfs.squashfs chứa filesystem user space. Firmware image có thể là gói gồm bootloader, kernel, DTB, rootfs và metadata update. Không có một định dạng chung cho mọi board.

50. UART Console — đường cứu hộ

Khi board không lên màn hình và SSH chưa chạy, UART console thường cho thấy log từ U-Boot và kernel. Kết nối mức logic phù hợp:

Board TX  ---> USB-UART RX
Board RX  <--- USB-UART TX
Board GND ---- USB-UART GND

Phải kiểm tra mức điện áp UART, tuyệt đối không đưa tín hiệu RS-232 hoặc điện áp không tương thích vào chân SoC. 115200 8N1 là cấu hình phổ biến nhưng không phải mặc định mọi board. SSH phụ thuộc network stack và sshd; UART có thể hoạt động sớm hơn nhiều.

51. Phân tích lỗi boot trên board

Nếu log dừng sau Starting kernel ..., có thể kernel lỗi sớm hoặc console được cấu hình sai. Nếu thấy VFS: Cannot open root device, kiểm tra root=, driver storage, filesystem, initramfs và thiết bị được nhận diện. Đừng kết luận khi thiếu bằng chứng.

52. VM Snapshot và Firmware Recovery

Snapshot VM lưu trạng thái disk/RAM theo hypervisor. Firmware recovery có thể flash lại SD/eMMC, boot recovery hoặc sử dụng slot A/B. Flash lại image không nhất thiết khôi phục calibration hay partition dữ liệu riêng.

53. A/B Update

A/B update duy trì hai slot. Thiết bị chạy A, ghi firmware mới vào B, thử boot B, xác nhận health check; nếu lỗi, bootloader có thể rollback A. Thiết kế thực tế cần metadata boot, cơ chế xác nhận và tương thích dữ liệu khi rollback. Mô phỏng tương tác bên dưới.

56. Tổng kết Embedded Linux

Development host: compiler, toolchain, build system, source code → artifacts: bootloader, kernel, DTB, rootfs → deploy → target: boot ROM, bootloader, kernel, rootfs, init → debug/test/update. Kỹ sư Embedded Linux cần hiểu cả host development và target hardware.
