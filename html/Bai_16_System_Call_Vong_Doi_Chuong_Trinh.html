Bài 16 — System Call và vòng đời chương trình trong Linux

Từ lúc gõ ./program đến khi process kết thúc: ELF, fork/exec, thư viện C, file descriptor, I/O, errno, mmap, strace và debugging thực chiến.

1. Đặt vấn đề: Một chương trình C có thực sự tự chạy được không?

Chương trình nhỏ nhất tưởng như chỉ chạy main(), nhưng kernel, loader và runtime đã thực hiện rất nhiều công việc.

#include <stdio.h>
int main(void) {
    printf("Hello Linux!\n");
    return 0;
}
gcc hello.c -o hello
./hello

Những câu hỏi cần đặt ra: Ai nạp executable vào bộ nhớ? Ai tạo stack? printf đưa chữ ra terminal thế nào? Ai thu hồi tài nguyên? Tại sao printf không nhất thiết tạo write syscall ngay lập tức?

2. User Space và Kernel Space — Vì sao phải chia thành hai thế giới?

Hãy tưởng tượng ngân hàng: khách hàng không tự vào kho tiền mà phải qua nhân viên có quyền xác minh. User process tương tự khách hàng; kernel tương tự nhân viên quản lý tài nguyên; system call là quầy yêu cầu.

Ứng dụng yêu cầu kernel thực hiện thao tác cần đặc quyền qua system call.

System call là cơ chế user space yêu cầu dịch vụ kernel. Trên x86-64 thường dùng instruction syscall; trên ARM64 thường dùng svc. Không phải mọi truy cập bộ nhớ đều cần system call: memory đã mapping hợp lệ có thể được CPU truy cập trực tiếp.

int fd = open("data.txt", O_RDONLY);

Đường đi thường là: ứng dụng → libc wrapper → chuyển CPU vào kernel mode → kiểm tra quyền và tài nguyên → trả kết quả. Câu hỏi phản biện: nếu ứng dụng tự sửa page table hoặc đọc bộ nhớ process khác thì điều gì xảy ra? Chính sự cách ly và kiểm soát của kernel bảo vệ hệ thống.

4. Từ file executable đến process đang chạy

Executable là file chứa mã và metadata; process là thực thể đang thực thi có address space, trạng thái CPU, PID và tài nguyên riêng. Hai process có thể dùng cùng một executable.

./hello &
./hello &
Process con kết thúc, parent có thể thu hồi trạng thái qua wait/waitpid.
#include <stdio.h>
#include <unistd.h>
int main(void) {
    pid_t pid = fork();
    if (pid == 0) printf("Child PID: %ld\n", (long)getpid());
    else if (pid > 0) printf("Parent PID: %ld\n", (long)getpid());
    else { perror("fork"); return 1; }
    return 0;
}

fork() tạo process con, thường dùng copy-on-write để tránh sao chép ngay toàn bộ physical memory. Scheduler không bảo đảm thứ tự in parent/child.

execve(path, argv, envp);
printf("Before exec\n");
execl("/bin/echo", "echo", "Hello", (char *)NULL);
perror("execl");

execve thành công thay thế image chương trình trong process hiện tại và không quay lại caller; nó không tạo PID mới. Shell tạo child để shell còn sống tiếp nhận lệnh. Ngoại lệ: shell có thể chủ động dùng exec để tự thay thế; cũng có thể dùng posix_spawn.

6. File Descriptor — Tại sao không thao tác bằng pathname mãi?

Pathname là cách tìm file, FD là chỉ số trong bảng descriptor của process. FD 0 stdin, 1 stdout, 2 stderr. FD được trả từ open thường là 3 nhưng không bắt buộc.

FDTênÝ nghĩa
0stdinĐầu vào tiêu chuẩn
1stdoutĐầu ra tiêu chuẩn
2stderrĐầu ra lỗi
int fd = open("data.txt", O_RDONLY);
char buf[100];
ssize_t n = read(fd, buf, sizeof(buf));
close(fd);
Hai FD có thể cùng tham chiếu một open file description và chia sẻ offset.
int fd1 = open("data.txt", O_RDONLY);
int fd2 = dup(fd1);
char a[3], b[3];
read(fd1, a, 3); // ABC
read(fd2, b, 3); // DEF

Nếu mở cùng pathname hai lần độc lập, thông thường có hai open file description với offset riêng. Nếu dùng dup(), offset được chia sẻ.

7. read(), write() và Partial I/O

read(fd, buf, 100) không đảm bảo trả đủ 100 byte. Nó có thể trả số byte dương ít hơn yêu cầu mà vẫn thành công. Đối với regular file, 0 thường biểu thị EOF.

Giá trịÝ nghĩa
n > 0Đã đọc n byte
n == 0EOF trên regular file
n == -1Lỗi: kiểm tra errno

Mô phỏng partial read

read() = 35 bytes

ssize_t read_full(int fd, void *buf, size_t count) {
    size_t total = 0;
    while (total < count) {
        ssize_t n = read(fd, (char *)buf + total, count - total);
        if (n > 0) { total += (size_t)n; continue; }
        if (n == 0) break; // EOF
        if (errno == EINTR) continue;
        return -1;
    }
    return (ssize_t)total;
}
int write_all(int fd, const void *buf, size_t count) {
    size_t done = 0;
    while (done < count) {
        ssize_t n = write(fd, (const char *)buf + done, count - done);
        if (n > 0) { done += (size_t)n; continue; }
        if (n < 0 && errno == EINTR) continue;
        return -1;
    }
    return 0;
}

Hai hàm minh họa dành cho blocking FD, count hợp lệ (đặc biệt với ssize_t). Nonblocking FD cần xử lý EAGAIN/EWOULDBLOCK và poll/epoll; production code cần thiết kế rõ timeout, cancellation và partial progress. write thành công không đảm bảo dữ liệu đã bền vững trên ổ đĩa; cân nhắc fsync/fdatasync và filesystem.

8. errno — Linux thông báo lỗi thế nào?

Các wrapper POSIX thường trả -1 và đặt errno khi lỗi. errno thường thread-local. Không đọc errno để suy luận lỗi nếu return value không báo lỗi; syscall thành công không nhất thiết xóa errno.

#include <stdio.h>
#include <fcntl.h>
#include <errno.h>
int main(void) {
    int fd = open("missing.txt", O_RDONLY);
    if (fd == -1) { perror("open"); return 1; }
    return 0;
}

9. EINTR — Signal gián đoạn syscall

Khi process chờ blocking read và nhận signal, syscall có thể trả -1 với errno EINTR. Điều này không có nghĩa FD bị hỏng.

ssize_t n;
do {
    n = read(fd, buf, sizeof(buf));
} while (n == -1 && errno == EINTR);

SA_RESTART và loại syscall ảnh hưởng hành vi restart. Không retry mù quáng: nếu SIGTERM yêu cầu dừng, ứng dụng cần tôn trọng cancellation flag hoặc deadline. Phân biệt lỗi tạm thời, hủy công việc và lỗi vĩnh viễn.

10. mmap() — Đọc file mà không gọi read()

mmap tạo vùng ánh xạ trong virtual address space. Truy cập qua pointer có thể gây page fault, thay vì mỗi lần truy cập đều tạo read syscall.

void *p = mmap(NULL, length, PROT_READ, MAP_PRIVATE, fd, 0);
char first = ((char *)p)[0];

read()

File / page cache
↓ kernel copy
User buffer

mmap()

File / page cache
↕ mapping / page fault
Virtual memory access
#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>
int main(void) {
    int fd = open("data.txt", O_RDONLY);
    if (fd == -1) { perror("open"); return 1; }
    struct stat st;
    if (fstat(fd, &st) == -1) { perror("fstat"); close(fd); return 1; }
    if (st.st_size == 0) { close(fd); return 0; }
    void *p = mmap(NULL, (size_t)st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
    if (p == MAP_FAILED) { perror("mmap"); close(fd); return 1; }
    char first = ((char *)p)[0];
    printf("First byte: %c\n", first);
    munmap(p, (size_t)st.st_size);
    close(fd);
    return 0;
}

Ví dụ giả định kích thước phù hợp và không bị truncate đồng thời; file bị truncate có thể gây SIGBUS khi truy cập mapping. mmap không luôn nhanh hơn read: tùy kiểu truy cập, cache, page fault, overhead. strace không thấy read không có nghĩa chương trình không đọc file.

11. Lab chính: Phân tích read-one.c

mkdir -p ~/linux-lab/syscalls
cd ~/linux-lab/syscalls
sudo apt update
sudo apt install build-essential strace
nano read-one.c
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>
#include <errno.h>

int main(int argc, char **argv)
{
    if (argc != 2)
        return 2;

    int fd = open(argv[1], O_RDONLY);

    if (fd == -1) {
        perror("open");
        return 1;
    }

    char buf[128];
    ssize_t n;

    do {
        n = read(fd, buf, sizeof buf);
    } while (n == -1 && errno == EINTR);

    if (n == -1) {
        perror("read");
        close(fd);
        return 1;
    }

    ssize_t done = 0;

    while (done < n) {
        ssize_t w = write(
            STDOUT_FILENO,
            buf + done,
            (size_t)(n - done)
        );

        if (w == -1 && errno == EINTR)
            continue;

        if (w <= 0) {
            perror("write");
            close(fd);
            return 1;
        }

        done += w;
    }

    if (close(fd) == -1) {
        perror("close");
        return 1;
    }

    return 0;
}

argc != 2: kiểm tra đúng một argument filename; status 2 là quy ước ứng dụng. open(): mở file và kiểm tra lỗi. char buf[128]: buffer local, thường nằm trên stack. read(): đọc một lần thành công, tối đa 128 byte, không phải bản thay thế cat. write loop: xử lý partial write và EINTR. close(): giải phóng FD.

gcc -Wall -Wextra -O0 -g read-one.c -o read-one
printf 'syscall example\n' > sample.txt
./read-one sample.txt
syscall example

Wall/Wextra bật cảnh báo; O0 hạn chế tối ưu hóa; -g thêm thông tin debug.

12. strace — Quan sát syscall thực tế

strace quan sát syscall và signal, thường thông qua ptrace. Trace chứa cả hoạt động loader/runtime.

strace ./read-one sample.txt
strace -o trace.log -e trace=execve,openat,read,write,close ./read-one sample.txt
cat trace.log
openat(AT_FDCWD, "sample.txt", O_RDONLY) = 3
read(3, "syscall example\n", 128) = 16
write(1, "syscall example\n", 16) = 16
close(3) = 0

openat: AT_FDCWD dùng working directory cho đường dẫn tương đối; trả FD 3. read yêu cầu 128 byte nhưng nhận 16. write ghi 16 byte ra stdout FD 1. close trả 0. open() trong source có thể được libc triển khai bằng openat() syscall: API không nhất thiết trùng tên syscall.

13. Lab lỗi: ENOENT, EACCES và exit code

strace -o missing.log ./read-one no-such-file
echo $?
openat(AT_FDCWD, "no-such-file", O_RDONLY) = -1 ENOENT

ENOENT nghĩa là đường dẫn không tìm thấy thành phần cần thiết; exit status ứng dụng là 1. EACCES thường liên quan quyền, nhưng có thể ở thư mục cha hoặc chính sách bảo mật.

printf 'secret\n' > secret.txt
chmod 000 secret.txt
./read-one secret.txt
chmod 600 secret.txt

Root hoặc process có capability phù hợp có thể cho kết quả khác. Không chmod bừa bãi: kiểm tra directory execute/search permission, ACL, SELinux, AppArmor.

15. return, exit, _exit và wait

return từ main trong hosted C thông thường tương đương kết thúc qua exit(status). exit xử lý stdio flush và exit handlers; _exit không flush stdio như exit. Trên Linux/glibc, _exit wrapper thường gọi exit_group để kết thúc thread group.

int main(void) { return 0; }
waitpid(child_pid, &status, 0);

Sau fork, child trước exec thường tránh chạy lại cleanup handlers hoặc flush buffer không phù hợp. Process đã kết thúc nhưng parent chưa wait có thể thành zombie: không còn chạy code nhưng giữ trạng thái kernel để parent thu hồi. Kết thúc thực thi khác thu hồi trạng thái.

16. Debug thực chiến Embedded Linux

Ứng dụng báo "Failed to open device". Đừng vội sửa driver: kiểm tra theo từng tầng.

ls -l /dev/your-device

namei -l /dev/your-device

Tầng 1 pathname: node có tồn tại? Tầng 2 permission: process có quyền? Tầng 3 syscall: errno nào? Tầng 4 kernel/driver: dmesg nói gì? Tầng 5 timing/concurrency: read đang blocking đúng hợp đồng hay thực sự bị treo?
