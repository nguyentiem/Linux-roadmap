Bài 25 — Dịch vụ mạng, Reverse Proxy và Firewall

Giải thích theo góc nhìn senior: đặt vấn đề, kiến trúc, socket, Nginx, Netfilter, nftables, conntrack, TLS, SSH, debugging và thực hành. HTML độc lập có sơ đồ SVG, tương tác và bài kiểm tra JavaScript.

1. Đặt vấn đề — chương trình chạy nhưng không truy cập được

Giả sử ODROID chạy Linux nhận dữ liệu điều khiển BLDC và cung cấp HTTP API. Bạn chạy chương trình, curl trên chính ODROID thành công nhưng laptop truy cập IP LAN lại thất bại. Vì sao? Để trả lời, cần phân biệt listener, socket, routing, firewall, reverse proxy và TLS/SSH.

Chương trình đã chạy, mạng vẫn hoạt động, tại sao laptop không truy cập được?

2. Bức tranh tổng thể: Client → Firewall → Nginx → Backend

Client gửi request qua mạng; routing đưa gói đến server; Netfilter/firewall áp dụng chính sách; Nginx tiếp nhận HTTP, có thể kết thúc TLS và chuyển request tới backend. Nginx còn sống không có nghĩa backend còn hoạt động.

3. Socket thực sự là gì?

Socket là đối tượng giao tiếp do hệ điều hành cung cấp. Ứng dụng sử dụng file descriptor và system call để giao tiếp mạng.

c
int server_fd = socket(AF_INET, SOCK_STREAM, 0);
bind(server_fd, ...);
listen(server_fd, 10);
int client_fd = accept(server_fd, ...);
recv(client_fd, buffer, sizeof(buffer), 0);
send(client_fd, response, response_len, 0);
HàmVai trò
socket()Tạo socket
bind()Gắn địa chỉ local
listen()Bắt đầu lắng nghe TCP
accept()Nhận kết nối đã được thiết lập từ hàng đợi
recv()Nhận dữ liệu
send()Gửi dữ liệu
close()Đóng descriptor
❓ Câu hỏi phản biện

Tại sao cần cả bind() và listen()? bind chọn địa chỉ; listen chuyển socket TCP sang chế độ chờ kết nối. backlog không phải giới hạn tổng số client được phục vụ.

4. Bind 127.0.0.1, 0.0.0.0 và IP LAN

127.0.0.1 chỉ nhận kết nối loopback trong cùng network namespace. 0.0.0.0 là wildcard bind mọi IPv4 local phù hợp, không có nghĩa vượt firewall. Bind IP LAN chỉ nhận kết nối đến IP đó. Địa chỉ :: là wildcard IPv6; dual-stack phụ thuộc IPV6_V6ONLY và cấu hình.

Thử đổi địa chỉ bind

✕ Laptop không thể kết nối trực tiếp qua IP LAN đến listener loopback.

bash
sysctl net.ipv6.bindv6only
ss -lntp

Trong Docker, 127.0.0.1 của container không mặc nhiên là 127.0.0.1 của host. Loopback hạn chế phạm vi truy cập, nhưng không phải xác thực người dùng.

❓ Câu hỏi phản biện

Nếu backend điều khiển motor bind 0.0.0.0, thiết bị khác có thể tiếp cận nếu mạng/firewall cho phép. Có nên đặt một reverse proxy xác thực ở phía trước?

5. Vì sao cần Reverse Proxy?

Backend có thể tự phục vụ HTTP nhưng Nginx giúp kết thúc TLS, định tuyến nhiều backend, ghi log, giới hạn request, cân bằng tải và phục vụ static files. Forward proxy đại diện phía client; reverse proxy đại diện phía server.

Forward proxyReverse proxy
Đại diện clientĐại diện server
Client thường biết proxyClient thường thấy endpoint công khai
Kiểm soát Internet của clientĐịnh tuyến và bảo vệ backend
❓ Câu hỏi phản biện

Nginx có chỉ sửa IP đích như NAT? Không: HTTP reverse proxy đọc request tầng ứng dụng, chọn upstream, có thể thay header và dùng TCP connection riêng.

6. Hai kết nối TCP và TLS termination

TCP A: 192.168.1.50:53000 → 192.168.1.100:443
TCP B: 127.0.0.1:41000 → 127.0.0.1:8080

Client ── HTTPS ──> Nginx ── HTTP ──> Backend

Nginx và client có một kết nối TCP, Nginx và backend có kết nối TCP khác. Nginx có thể tái sử dụng kết nối upstream. TLS termination tại Nginx không bảo đảm đoạn Nginx → backend cũng được mã hóa. Nếu upstream qua mạng không tin cậy, cân nhắc HTTPS upstream.

❓ Câu hỏi phản biện

HTTPS từ laptop có đồng nghĩa mã hóa end-to-end đến backend không? Không, phụ thuộc cấu hình upstream.

8. Cấu hình Nginx từng dòng

Tạo /etc/nginx/conf.d/linux-lab.conf nếu nginx.conf có include conf.d/*.conf:

nginx
server {
    listen 127.0.0.1:8081;
    server_name localhost;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 2s;
        proxy_read_timeout 5s;
    }
}

server là virtual server block; listen chọn địa chỉ/port; server_name tham gia chọn virtual host, không phải firewall; location / khớp tiền tố URI; proxy_pass gửi request đến upstream. Có/không có URI phía sau proxy_pass có thể thay đổi cách xử lý đường dẫn.

nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
location /static/ {
    root /var/www;
}
Client GET http://127.0.0.1:8081/test
                  ↓
Nginx → GET http://127.0.0.1:8080/test

9. Forwarded headers và an toàn

nginx
proxy_set_header Host $host;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;

Host chuyển hostname đã được Nginx xử lý. X-Forwarded-For mang chuỗi địa chỉ qua proxy; X-Forwarded-Proto thông báo scheme. Client có thể tự giả mạo X-Forwarded-For. $proxy_add_x_forwarded_for có thể nối thêm địa chỉ client vào header do client cung cấp. Backend chỉ nên tin header theo trusted-proxy chain được cấu hình đúng; không dùng header tùy ý để xác thực.

http
X-Forwarded-For: 192.168.1.50, 10.0.0.5
X-Forwarded-Proto: https
❓ Câu hỏi phản biện

Nếu client tự gửi X-Forwarded-For: 1.2.3.4 thì backend có nên coi 1.2.3.4 là danh tính đáng tin không? Không.

10. Timeout và HTTP status

proxy_connect_timeout giới hạn thiết lập kết nối upstream. proxy_read_timeout giới hạn khoảng chờ giữa hai lần đọc upstream, không phải toàn bộ thời lượng response. Backend gửi dữ liệu đều đặn có thể kéo dài response vượt 5 giây.

nginx
proxy_connect_timeout 2s;
proxy_read_timeout 5s;

12. Packet qua Linux network stack

Ethernet NIC → NIC Driver → Linux Network Stack
       → Routing / Netfilter → TCP/UDP → Socket → Application

Đây là sơ đồ logic. Kernel có nhiều điểm xử lý, tùy giao thức, routing, NAT và hook. Phân biệt packet local-delivery và packet forwarding rất quan trọng.

13. Netfilter: PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING

PREROUTING xử lý packet đến trước quyết định định tuyến tương ứng; INPUT dành cho packet đến local host; FORWARD dành cho packet được chuyển tiếp; OUTPUT dành cho packet tạo cục bộ; POSTROUTING dành cho packet chuẩn bị đi ra.

❓ Câu hỏi phản biện

Một packet gửi đến Nginx chạy trên chính server đi INPUT hay FORWARD? INPUT. Nginx sau đó có thể tạo kết nối upstream khác; không phải packet TCP gốc tự biến thành FORWARD.

14. Firewall: ACCEPT, DROP, REJECT

Firewall thường xét source/destination IP, port, protocol, interface và trạng thái kết nối. ACCEPT cho phép packet tiếp tục, DROP bỏ packet, REJECT từ chối và có thể gửi thông báo lỗi. ACCEPT ở một base chain không bảo đảm các base chain khác cùng hook sẽ không drop packet.

VerdictÝ nghĩa
ACCEPTCho packet tiếp tục xử lý
DROPBỏ packet không tự phản hồi
REJECTTừ chối với thông báo phù hợp nếu có thể

15. Cấu trúc nftables: Table → Chain → Rule

Table inet linux_course
  └── Chain input (hook input, priority 10)
       └── tcp dport 8081 counter
nft
table inet linux_course {
    chain input {
        type filter hook input priority 10;
        policy accept;
        tcp dport 8081 counter
    }
}

Family inet hỗ trợ IPv4/IPv6; tên chain chỉ là nhãn, hook input mới quyết định vị trí; priority nhỏ hơn chạy trước trong cùng hook. policy accept là mặc định chain. Counter chỉ đếm, không phải một chính sách hardening đầy đủ.

16. Lab nftables đếm packet không làm mất SSH

bash
sudo nft list ruleset
nft --version
# Nếu chưa có: sudo apt install nftables

sudo nft add table inet linux_course
sudo nft 'add chain inet linux_course input { type filter hook input priority 10; policy accept; }'
sudo nft add rule inet linux_course input tcp dport 8081 counter
curl --fail http://127.0.0.1:8081/
sudo nft list table inet linux_course
sudo nft delete table inet linux_course
nft
table inet linux_course {
    chain input {
        type filter hook input priority 10; policy accept;
        tcp dport 8081 counter packets 5 bytes 300
    }
}

Số packet/byte chỉ minh họa. Loopback vẫn đi qua các hook Netfilter thích hợp. Counter tăng chỉ chứng minh packet khớp rule, không chứng minh HTTP 200 hoặc xác thực thành công. Không dùng nft flush ruleset để dọn lab vì sẽ xóa cả rule khác.

17. Connection Tracking là gì?

Conntrack theo dõi flow và liên kết hai chiều, hỗ trợ stateful firewall và NAT. Trạng thái conntrack không giống hoàn toàn TCP state và không liên quan trực tiếp đến đăng nhập ứng dụng.

Conntrack stateÝ nghĩa
newKết nối mới theo phân loại conntrack
establishedĐã nhận diện traffic hai chiều
relatedTraffic liên quan flow khác
invalidKhông phân loại hợp lệ
nft
ct state established,related accept

Rule established,related thường cho phép traffic phản hồi nhưng không thay thế rule cho phép các kết nối mới hợp lệ.

Client→ SYN →Server
Bước 1 — SYN

Client gửi SYN yêu cầu mở kết nối. Conntrack: NEW.

19. TLS: HTTPS bảo vệ điều gì?

TLS mã hóa dữ liệu khi truyền, bảo vệ toàn vẹn và giúp xác thực server nếu certificate được xác minh đúng. Cần kiểm tra hostname, trust chain, thời hạn và đồng hồ. TLS không tự xác thực quyền gọi API nghiệp vụ.

bash
curl -v https://api.example.com
# curl -k bỏ qua xác minh certificate: không dùng như cách sửa lỗi production
❓ Câu hỏi phản biện

Client dùng HTTPS có bảo đảm toàn bộ đường đến backend mã hóa? Không, nếu Nginx kết thúc TLS rồi dùng HTTP upstream.

Nếu host key thay đổi, cần xác minh fingerprint qua kênh đáng tin trước khi cập nhật known_hosts. Đừng xóa cảnh báo một cách máy móc.

21. Firewall khi đang SSH: tránh tự khóa máy

Không áp dụng default DROP trên server chỉ có SSH nếu chưa có console/đường quản trị dự phòng. Phân tích loopback, established/related, SSH từ subnet quản trị, HTTP/HTTPS, IPv6, ICMPv6, DHCP/DNS tùy nhu cầu. Giữ phiên SSH hiện tại và thử phiên thứ hai trước khi kết thúc.

nft
ip saddr 192.168.1.0/24 tcp dport 22 ct state new accept
bash
sudo nft list ruleset
ip route
ss -lntp

Rule SSH trên chỉ minh họa, không phải ruleset hoàn chỉnh. Phải có cơ chế rollback được thử nghiệm trước khi thay đổi firewall.
