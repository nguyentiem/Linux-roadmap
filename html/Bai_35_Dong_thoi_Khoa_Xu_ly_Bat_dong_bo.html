1. Đặt vấn đề: Một CAN Gateway hoạt động sai dù từng thread đều đúng

Giả sử một Embedded Linux gateway có thread nhận CAN, thread xử lý telemetry, thread gửi TCP và thread ghi log. Từng thread riêng lẻ chạy đúng, nhưng khi chạy cùng lúc, thống kê frame đôi khi sai, ứng dụng có lúc treo, CPU tăng đột biến.

Câu hỏi: Nếu từng hàm đều đúng, tại sao cả hệ thống vẫn sai? Vì thứ tự xen kẽ giữa các thread có thể làm thay đổi kết quả. Đây là điểm xuất phát của concurrency.

// Hai thread cùng cập nhật
shared_stats.frames_received++;
// Mỗi thread có thể đọc cùng giá trị cũ,
// rồi cùng ghi ra một giá trị mới.

2. Concurrency, parallelism và asynchronous

Concurrency là tổ chức nhiều công việc có thể tiến triển xen kẽ; parallelism là nhiều công việc thực sự chạy đồng thời trên các CPU/core; asynchronous là khởi phát một công việc mà không nhất thiết phải đợi nó hoàn tất ngay tại điểm gọi.

Ví dụ đời sống: một đầu bếp luân phiên chế biến nhiều món là concurrency; hai đầu bếp cùng nấu là parallelism; đặt món rồi nhận thông báo khi món xong là asynchronous. Ba khái niệm liên quan nhưng không đồng nghĩa.

3. Race condition và phép tăng counter không nguyên tử

Câu lệnh counter++ không tự động là một thao tác nguyên tử. Nó có thể được thực hiện như ba bước: đọc → cộng → ghi. Nếu hai thread đọc cùng giá trị 0, cả hai đều có thể ghi 1 thay vì kết quả 2.

// Tương đương logic (không phải lệnh máy bắt buộc)
int temp = counter;
temp = temp + 1;
counter = temp;

Mô phỏng lost update — từng bước

Shared counter: 0
Thanh ghi A: —
Thanh ghi B: —

Data race trong C/C++ xảy ra khi các truy cập xung đột đến cùng vị trí nhớ thiếu quan hệ đồng bộ thích hợp và ít nhất một truy cập là ghi; chương trình có thể có undefined behavior. Race condition là khái niệm rộng hơn: kết quả phụ thuộc vào thứ tự sự kiện, kể cả khi không có data race theo định nghĩa ngôn ngữ.

4. Invariant và ranh giới critical section

Invariant là điều kiện phải luôn đúng ở những thời điểm quan sát hợp lệ. Ví dụ balance_A + balance_B = total. Nếu chuyển tiền giữa hai tài khoản mà chỉ bảo vệ một phép gán, invariant có thể bị phá vỡ.

pthread_mutex_lock(&accounts_lock);
accounts[from] -= amount;
accounts[to]   += amount;
pthread_mutex_unlock(&accounts_lock);

Mutex phải bảo vệ toàn bộ invariant, không chỉ một biến riêng lẻ. Ngược lại, giữ mutex bao trùm cả network I/O sẽ tạo contention.

5. Mutex: cơ chế, ưu điểm và chi phí

Mutex bảo đảm chỉ một thread tại một thời điểm sở hữu khóa. Thread không lấy được mutex có thể phải chờ. Mutex không tự động bảo vệ mọi biến; chỉ bảo vệ các đường code thực sự tuân thủ cùng một giao thức khóa.

pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;
void *worker(void *arg) {
    for (int i = 0; i < 1000000; ++i) {
        pthread_mutex_lock(&mutex);
        ++counter;
        pthread_mutex_unlock(&mutex);
    }
    return NULL;
}

6. Lab C11: unsafe, mutex và atomic

So sánh ba cách tăng counter. Chế độ unsafe chỉ để minh họa lỗi; data race là undefined behavior nên không được dựa vào kết quả quan sát để khẳng định hành vi.

#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>
#define N 1000000
static long unsafe_counter;
static long mutex_counter;
static atomic_long atomic_counter;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
void *unsafe_worker(void *p) {
    for (int i=0;i<N;i++) unsafe_counter++; // data race!
    return NULL;
}
void *mutex_worker(void *p) {
    for (int i=0;i<N;i++) {
        pthread_mutex_lock(&lock);
        mutex_counter++;
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}
void *atomic_worker(void *p) {
    for (int i=0;i<N;i++)
        atomic_fetch_add_explicit(&atomic_counter, 1, memory_order_relaxed);
    return NULL;
}
int main(void) {
    pthread_t t[4];
    void *(*workers[])(void*)={unsafe_worker,mutex_worker,atomic_worker};
    const char *names[]={"unsafe","mutex","atomic"};
    for(int m=0;m<3;m++) {
        for(int i=0;i<4;i++) pthread_create(&t[i],NULL,workers[m],NULL);
        for(int i=0;i<4;i++) pthread_join(t[i],NULL);
        printf("%s: %ld\n",names[m],m==0?unsafe_counter:m==1?mutex_counter:atomic_load(&atomic_counter));
    }
}
gcc -std=c11 -O2 -pthread demo.c -o demo
./demo

Production code cần kiểm tra giá trị trả về của pthread API. Để benchmark nghiêm túc, hãy chạy nhiều lần, tách từng chế độ và kiểm soát ảnh hưởng của compiler, CPU affinity, cache và contention.

7. CAS và bài toán giới hạn counter

CAS (compare-and-swap) chỉ ghi giá trị mới nếu giá trị hiện tại vẫn bằng giá trị kỳ vọng. Nếu có thread khác sửa trước, thao tác thất bại và cần đọc lại. CAS hữu ích khi cập nhật có điều kiện, ví dụ giới hạn số slot ở mức 100.

int old = atomic_load(&slots);
while (old < 100) {
    if (atomic_compare_exchange_weak(&slots, &old, old + 1)) {
        // Đã lấy một slot
        break;
    }
    // Nếu thất bại, old được cập nhật từ slots
}

8. Memory ordering: relaxed, acquire, release, seq_cst

Atomicity không đồng nghĩa với thứ tự quan sát mọi dữ liệu. memory_order_relaxed phù hợp cho bộ đếm thống kê không dùng để đồng bộ dữ liệu khác. release khi công bố trạng thái và acquire khi nhận trạng thái có thể tạo quan hệ happens-before thích hợp.

// Producer
payload = 42;
atomic_store_explicit(&ready, true, memory_order_release);

// Consumer
if (atomic_load_explicit(&ready, memory_order_acquire)) {
    printf("%d\n", payload);
}

Ví dụ trên giả định producer chỉ công bố một lần, payload không bị sửa đồng thời sau công bố, và các đối tượng được khởi tạo đúng. seq_cst thêm ràng buộc thứ tự toàn cục cho các thao tác seq_cst, nhưng không thay thế thiết kế ownership.

9. Vì sao volatile không thay mutex/atomic?

volatile chủ yếu tác động đến cách compiler xử lý các truy cập volatile; nó không tạo mutual exclusion, không biến phép cộng thành atomic và không tự tạo happens-before giữa thread.

volatile int counter = 0;
// counter++ từ nhiều thread vẫn không an toàn.

Trong MCU, volatile thường xuất hiện với thanh ghi memory-mapped I/O. Nhưng DMA, cache coherency, memory barrier và truy cập ngoại vi có những quy tắc riêng; không thể coi volatile là giải pháp tổng quát cho mọi đồng bộ phần cứng.

11. Futex: fast path user space và slow path kernel

Futex là nền tảng hỗ trợ nhiều cơ chế đồng bộ user space trên Linux. Khi không tranh chấp, nhiều thao tác khóa có thể hoàn thành hoàn toàn trong user space; khi phải chờ, hệ thống có thể sử dụng futex syscall để ngủ và đánh thức.

strace -f -e futex ./demo

Không phải mỗi lần gọi pthread mutex đều gây syscall. Đây là một lý do mutex có thể rất hiệu quả khi không tranh chấp.

12. Producer–Consumer và condition variable

Producer thêm phần tử vào bounded queue; consumer đợi khi queue rỗng. Condition variable cho phép nhả mutex và ngủ một cách phối hợp, tránh busy waiting.

pthread_mutex_lock(&mutex);
while (queue_empty() && running) {
    pthread_cond_wait(&not_empty, &mutex);
}
if (!queue_empty()) {
    item = queue_pop();
}
pthread_mutex_unlock(&mutex);

Tại sao dùng while thay vì if? Vì có thể có spurious wakeup; hơn nữa, sau khi được đánh thức, thread khác có thể đã tiêu thụ phần tử trước khi ta giành lại mutex. Với bounded queue, producer cũng cần chờ hoặc áp dụng chính sách khi đầy.

13. Deadlock: bốn điều kiện và lock ordering

Deadlock là tình trạng các bên chờ lẫn nhau và không thể tiến triển. Bốn điều kiện Coffman: mutual exclusion, hold-and-wait, no preemption và circular wait. Không phải mọi lần block đều là deadlock.

// Thread A                    // Thread B
lock(mutex_A);                lock(mutex_B);
lock(mutex_B);                lock(mutex_A);
// Có thể tạo vòng chờ A ↔ B.

13.4. Cách phổ biến nhất: Lock ordering

Quy định thứ tự toàn cục A → B → C. Thread nào cần nhiều khóa phải lấy theo thứ tự đó và thường nhả theo thứ tự ngược lại. Điều này loại bỏ vòng chờ phát sinh từ các khóa tuân thủ thứ tự.

void update_data(void) {
    pthread_mutex_lock(&mutex_A);
    pthread_mutex_lock(&mutex_B);
    /* Update shared data */
    pthread_mutex_unlock(&mutex_B);
    pthread_mutex_unlock(&mutex_A);
}

Với dự án lớn, xây dựng lock hierarchy: system_lock(1) → device_lock(2) → queue_lock(3) → log_lock(4). Code review phải kiểm tra thứ tự này. Lock ordering không tự giải quyết self-deadlock, block I/O vô hạn hoặc logic condition variable sai.

Mô phỏng lock ordering

Thread A: Chưa lấy khóa
Thread B: Chưa lấy khóa

13.5. Timeout có giải quyết deadlock không?

int rc = pthread_mutex_timedlock(&mutex_B, &deadline);
if (rc != 0) {
    pthread_mutex_unlock(&mutex_A);
    return rc;
}

Timeout giúp giới hạn một lần chờ và hỗ trợ recovery nhưng không tự sửa invariant hay hoàn tác tài nguyên đã giữ. pthread_mutex_timedlock chuẩn dùng deadline tuyệt đối theo CLOCK_REALTIME.

14. Deadlock, livelock và starvation

Deadlock: thread chờ vòng tròn, không tiến triển. Livelock: các thread vẫn chạy và liên tục nhường nhau nhưng không hoàn thành. Starvation: một thread không có cơ hội thực thi hoặc dùng tài nguyên trong thời gian quá dài.

while (1) {
    if (pthread_mutex_trylock(&lock_A) == 0) {
        if (pthread_mutex_trylock(&lock_B) == 0) {
            process();
            pthread_mutex_unlock(&lock_B);
            pthread_mutex_unlock(&lock_A);
            break;
        }
        pthread_mutex_unlock(&lock_A);
    }
}

Nếu nhiều thread cùng retry đồng bộ nhịp, chúng có thể livelock. Backoff giúp giảm xung đột nhưng không thay thế chứng minh tiến triển.

15. Priority inversion và priority inheritance

Thread ưu tiên thấp L giữ mutex; thread ưu tiên cao H cần mutex nên block; thread trung bình M chiếm CPU khiến L không được chạy để nhả mutex. H bị trì hoãn gián tiếp bởi M.

pthread_mutexattr_t attr;
pthread_mutex_t mutex;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT);
pthread_mutex_init(&mutex, &attr);
pthread_mutexattr_destroy(&attr);

Priority inheritance tạm nâng ưu tiên hiệu dụng của L khi H chờ mutex L giữ. Code thực tế phải kiểm tra lỗi và khả năng hỗ trợ. Nó không thay thế lock ordering.

16. Debugging deadlock với GDB, strace và ThreadSanitizer

Khi ứng dụng treo, thu thập bằng chứng trước khi restart nếu an toàn. Kiểm tra thread và stack, xác định khóa nào đang chờ và ai sở hữu.

ps -T -p <PID>

Nhiều thread ở pthread_mutex_lock() chưa chứng minh deadlock; TSan chỉ phát hiện các race trên đường chạy quan sát được và không chứng minh chương trình không có race.

17. Asynchronous programming và epoll

Blocking I/O có thể khiến thread phải chờ dữ liệu. Nonblocking I/O trả EAGAIN/EWOULDBLOCK khi chưa sẵn sàng; epoll giúp một event loop theo dõi nhiều descriptor.

int flags = fcntl(fd, F_GETFL, 0);
if (flags >= 0) fcntl(fd, F_SETFL, flags | O_NONBLOCK);
int epfd = epoll_create1(0);
struct epoll_event ev = {.events=EPOLLIN, .data.fd=socket_fd};
epoll_ctl(epfd, EPOLL_CTL_ADD, socket_fd, &ev);
while (running) {
    struct epoll_event events[32];
    int n = epoll_wait(epfd, events, 32, -1);
    if (n < 0) { if (errno == EINTR) continue; break; }
    for (int i=0;i<n;i++) handle_event(events[i].data.fd);
}

Event loop không nên chạy công việc CPU-intensive hoặc blocking dài. Kiến trúc thường kết hợp event loop → task queue → worker pool → output queue.

18. Kernel process context, IRQ context và workqueue

Trong process context, kernel code có thể ngủ nếu trạng thái cho phép. Hard IRQ context không được gọi API có thể ngủ như mutex_lock thông thường.

// KHÔNG hợp lệ trong hard IRQ context thông thường:
irqreturn_t irq_handler(int irq, void *dev) {
    mutex_lock(&lock);
    /* work */
    mutex_unlock(&lock);
    return IRQ_HANDLED;
}

Giải pháp là ghi nhận sự kiện trong IRQ handler rồi chuyển công việc có thể ngủ sang workqueue hoặc threaded interrupt phù hợp.

20. RCU — Read-Copy-Update và grace period

RCU phù hợp khi nhiều reader và ít writer. Writer tạo phiên bản mới, công bố phiên bản mới, rồi đợi grace period trước khi thu hồi dữ liệu cũ. Reader đã bắt đầu trước đó vẫn có thể đang dùng phiên bản cũ.

RCU không thay mọi mutex: writer có thể vẫn cần phối hợp với writer khác, và quản lý lifetime đòi hỏi kỷ luật nghiêm ngặt.

21. PREEMPT_RT và ngữ nghĩa spinlock

PREEMPT_RT cải thiện khả năng dự đoán latency bằng thay đổi nhiều cơ chế kernel. Trên PREEMPT_RT, spinlock_t có ngữ nghĩa dựa trên rtmutex; raw_spinlock_t giữ cơ chế spinlock mức thấp. Không nên giả định spinlock_t luôn tắt preemption trên mọi kernel.

uname -a
zgrep CONFIG_PREEMPT /proc/config.gz
# Hoặc xem cấu hình kernel trong /boot

22. Production case: CAN Gateway mất frame, CPU cao, ứng dụng treo

Ba hiện tượng có thể đến từ ba nhóm nguyên nhân độc lập: queue/driver/socket overflow; busy waiting hoặc lock contention; và deadlock do thứ tự khóa. Đừng quy mọi lỗi cho race condition.

// CAN RX thread
lock(queue_mutex);
lock(log_mutex);

// Logging thread
lock(log_mutex);
lock(queue_mutex);
// Nguy cơ deadlock: thứ tự ngược nhau.

Theo dõi frames_received, frames_processed, frames_dropped, queue_depth, processing_latency và tình trạng CAN bus. Chỉ số cần phân biệt mất tại hardware, kernel socket buffer và application queue.

23. Backpressure: producer nhanh hơn consumer

Nếu producer nhận 10.000 frame/s, consumer xử lý 8.000 frame/s, backlog tăng 2.000 frame/s. Queue 20.000 frame từ rỗng sẽ đầy sau khoảng 10 giây nếu tốc độ không đổi.

Mô phỏng CAN Gateway Queue

Backlog tăng: 2.000 frame/s
Queue đầy sau: 10 s

Giả định queue ban đầu rỗng, dung lượng 20.000 frame, tốc độ không đổi.

Khi queue đầy, phải chọn chính sách có chủ đích: block producer, drop mới, drop cũ, điều tiết nguồn hoặc tăng năng lực xử lý. Với CAN, việc chặn thread nhận quá lâu có thể đẩy mất frame sang tầng kernel.

24. Lock contention và critical section

Mutex đúng nhưng hệ thống vẫn chậm nếu giữ mutex khi xử lý frame, ghi log và network I/O. Hãy copy dữ liệu dùng chung dưới khóa rồi xử lý bản sao bên ngoài nếu invariant cho phép.

// Dễ gây contention
pthread_mutex_lock(&mutex);
process_frame(frame);
send_to_network(frame); // Có thể block
write_log(frame);
pthread_mutex_unlock(&mutex);

// Tốt hơn nếu dữ liệu có thể snapshot an toàn
pthread_mutex_lock(&mutex);
copy_shared_state(&local_state);
pthread_mutex_unlock(&mutex);
process_frame(&local_state);
send_to_network(&local_state);
write_log(&local_state);

Amdahl's Law — tăng thread không đảm bảo tăng tốc tuyến tính

Nếu tỷ lệ công việc tuần tự là s, tốc độ tăng lý thuyết khi dùng N worker là Speedup = 1 / (s + (1-s)/N).

25. False sharing: khác biến nhưng cùng cache line

Hai thread chỉ cập nhật hai biến khác nhau nhưng nằm cùng cache line vẫn có thể gây cache coherence traffic. Đây là false sharing; không phải data race.

Padding và alignment có thể giảm false sharing nhưng tăng memory footprint. Hãy đo trước và sau khi thay đổi.

26. Nguyên tắc thiết kế concurrency của senior engineer

  1. Giảm shared mutable state.
  2. Chỉ định ownership dữ liệu rõ ràng.
  3. Ưu tiên message passing khi phù hợp.
  4. Không giữ mutex qua blocking I/O nếu tránh được.
  5. Quy định lock ordering và review.
  6. Giữ critical section ngắn nhưng đủ bảo vệ invariant.
  7. Thiết kế shutdown và cancellation từ đầu.
  8. Đo contention, latency, throughput trước khi tối ưu.
  9. Không dùng volatile thay atomic.
  10. Không dùng sleep() để “sửa” race.

Ví dụ shutdown: nếu worker đang chờ condition variable, thread chính đặt running=0 rồi join nhưng không signal/broadcast, worker có thể không bao giờ thức dậy. Trạng thái dừng phải được đồng bộ, worker được đánh thức và kiểm tra lại predicate.
