Bài 01 — Nền tảng máy tính và hệ điều hành

Giải thích chuyên sâu theo tư duy Senior Linux / Embedded Linux Engineer

CPU · Process · Thread · Memory · Scheduler · Page Cache · Interrupt · Timer · DMA · Kernel · Lab

Bài học giải thích mối quan hệ giữa phần cứng và Linux, sử dụng ví dụ xuyên suốt cat hello.txt, câu hỏi phản biện, sơ đồ, code và các mô phỏng tương tác. Mọi thành phần hoạt động ngoại tuyến trong một file HTML, không dùng thư viện hay tài nguyên mạng.

Phần I — Nhìn máy tính như một hệ thống hoàn chỉnh

1. Tại sao cần học kiến trúc máy tính trước khi học Linux?

Giả sử bạn đang phát triển hệ thống Embedded Linux đọc cảm biến, nhận CAN, ghi log và gửi dữ liệu Ethernet. Cứ sau vài phút dữ liệu lại trễ 200 ms, trong khi CPU chỉ sử dụng 15%. Liệu CPU thấp chứng minh hệ thống không có vấn đề? Không. Thread có thể đang chờ I/O, bị scheduler trì hoãn, bị khóa mutex, chịu cache miss hoặc interrupt. Hiểu mối quan hệ giữa phần cứng và hệ điều hành giúp tìm đúng nút thắt.

Phần II — CPU thực sự thực thi chương trình như thế nào?

3. CPU có hiểu ngôn ngữ C, Python hay Bash không?

#include <stdio.h>
int main(void) {
    int a = 10;
    int b = 20;
    printf("%d\n", a + b);
    return 0;
}

CPU không hiểu cú pháp C. CPU thực thi lệnh máy của ISA (Instruction Set Architecture), ví dụ x86-64, ARM64 hoặc RISC-V. Các thao tác bao gồm nạp dữ liệu, cộng, so sánh, nhảy và truy cập bộ nhớ.

Source code — main.c
↓
Compiler / Linker
↓
Executable ELF
↓
Kernel + Loader
↓
CPU thực thi machine instructions

Quan sát mã máy:

gcc -O0 -g main.c -o main
objdump -d -M intel ./main

Ví dụ assembly minh họa (không bảo đảm compiler sinh chính xác):

mov eax, 10
add eax, 20

Phản biện: Nếu CPU chỉ hiểu machine code, tại sao Python chạy được? Vì Python interpreter bản thân là chương trình mã máy. CPython thường biên dịch Python thành bytecode rồi interpreter thực thi; mọi công việc cuối cùng vẫn được thực hiện bằng lệnh máy.

C → Compiler → Machine code → CPU
Python → Interpreter/Bytecode → Mã máy interpreter → CPU

CPU hiện đại có pipeline, branch prediction và out-of-order execution, vì vậy đây là mô hình khái niệm chứ không phải mỗi lần chỉ có một lệnh. Register giữ toán hạng và trạng thái: Program Counter / Instruction Pointer, Stack Pointer, general-purpose registers, status flags và control registers. Quy tắc gọi hàm liên quan đến ABI.

void foo(void) { int x = 10; }

CPU cần biết vị trí hàm, cách chuyển điều khiển và cách quay lại. Register và cache nhanh hơn RAM nên CPU không muốn lấy mọi toán hạng trực tiếp từ RAM. Đây là cầu nối đến memory hierarchy.

Phần III — Program, Process và Thread

5. Tại sao có file chương trình rồi vẫn cần process?

/usr/bin/cat là file chương trình. Hai terminal chạy cat hello.txt thường tạo hai process riêng. Program là mã/dữ liệu được lưu; process là thực thể thực thi có không gian địa chỉ và tài nguyên do kernel quản lý. Ví dụ: công thức nấu ăn là program; mỗi đầu bếp nấu theo công thức là một lần thực thi.

6. Bên trong một process có những gì?

Stack — lời gọi hàm, biến cục bộ
Memory mappings — thư viện, mmap
Heap — malloc / new
Data / BSS — biến global/static
Text — mã chương trình
Minh họa vùng địa chỉ ảo; bố trí thực tế phụ thuộc ASLR, kiến trúc và chương trình.
#include <stdlib.h>
void example(void) {
    int a = 10;
    int *p = malloc(100 * sizeof(int));
    if (p != NULL) { p[0] = a; free(p); }
}

Biến cục bộ có thể ở stack hoặc register. Bộ nhớ malloc là vùng cấp phát động, không đồng nghĩa kernel lập tức cấp đủ RAM vật lý. Allocator có thể tái sử dụng vùng cũ; trang vật lý có thể chỉ được cấp khi chạm vào trang. Câu hỏi: malloc(1 GB) thành công có chắc chiếm 1 GB RAM? Không. Phụ thuộc overcommit và việc truy cập trang.

Phần IV — CPU Core, Logical CPU và Scheduling

8. Socket, core và hardware thread

Socket(s):             1
Core(s) per socket:    4
Thread(s) per core:    2
CPU(s):                8

1 socket × 4 core × 2 thread/core = 8 logical CPU. SMT cho phép hai hardware thread chia sẻ một phần tài nguyên core; 8 logical CPU không tương đương 8 core độc lập.

1 CPU Socket
Core 1 → Logical 0, 1
Core 2 → Logical 2, 3
Core 3 → Logical 4, 5
Core 4 → Logical 6, 7

SMT có thể tận dụng tài nguyên rảnh khi một hardware thread chờ bộ nhớ, nhưng hai thread cũng có thể cạnh tranh tài nguyên. Trong VM, topology mà lscpu thấy có thể do hypervisor trình bày.

8.2. Amdahl's Law — vì sao thêm core không tự động nhanh gấp N?

S(N) = 1 / ((1 − P) + P / N)

P là tỷ lệ song song hóa; N là số core; S(N) là mức tăng tốc lý tưởng. Nếu 80% tuần tự và chỉ 20% song song, dù có vô hạn core, tăng tốc tối đa vẫn chỉ 1,25×.

9. Scheduler và context switch

Scheduler chọn thread runnable nào được chạy trên logical CPU. Khi chuyển từ thread A sang B, hệ thống lưu/khôi phục trạng thái cần thiết: một phần của context switch. User → kernel mode không tự động đồng nghĩa chuyển thread; interrupt cũng không chắc dẫn đến context switch.

Mô phỏng lập lịch một logical CPU

Đây là mô hình minh họa, không phải CFS/EEVDF thật.

CPU thấp không chứng minh latency thấp: thread có thể chờ read(), mutex hoặc I/O và không tiêu thụ CPU trong lúc chờ.

Phần V — Thứ bậc bộ nhớ và Cache

10. CPU GHz nhưng tại sao vẫn phải chờ?

CPU 3 GHz có chu kỳ khoảng 0,333 ns, nhưng không có nghĩa mỗi lệnh hay truy cập dữ liệu đều hoàn tất trong một chu kỳ. Truy cập RAM có thể mất hàng chục đến hàng trăm ns. Memory hierarchy giúp giảm khoảng cách tốc độ.

11. Register, cache, RAM và storage

Registers
L1 Cache
L2 Cache
L3 / LLC
RAM
SSD / HDD

Ví dụ sửa chữa: register là linh kiện trên tay, cache là linh kiện sát bên, RAM là ngăn kéo, SSD là kho. CPU cache thường dùng SRAM, còn RAM chính thường dùng DRAM. Đây là các loại phần cứng khác nhau.

12. Cache hit và cache miss

Cache hit: dữ liệu đã ở tầng cache đang kiểm tra. Cache miss: phải tìm ở tầng khác. L1 miss chưa chắc phải đọc RAM vì có thể hit ở L2/L3. Nhiều CPU có cache line 64 byte: với int 4 byte, một line có thể chứa 16 phần tử liền nhau.

13. Temporal locality và spatial locality

Temporal locality: dữ liệu vừa dùng có thể sớm dùng lại. Spatial locality: dữ liệu ở địa chỉ gần nhau có thể được truy cập kế tiếp.

for (int i = 0; i < 1000; i++) sum += arr[i];
// Duyệt liên tiếp thường thuận lợi cho cache hơn
// lần theo con trỏ node nằm rải rác trong RAM.

Mô phỏng tính cục bộ

Chỉ minh họa vị trí truy cập, không đo cache hit/miss thực tế.

Trong Embedded Linux, buffer liên tục thường thuận lợi cho locality khi xử lý dữ liệu CAN/UART/Ethernet. Tuy nhiên, array không luôn tốt hơn linked list trong mọi thuật toán: phải xét yêu cầu và benchmark thực tế.

Phần VI — RAM, Virtual Memory, Page Fault và Swap

14. Vì sao process không dùng trực tiếp địa chỉ RAM vật lý?

Hai process có thể cùng thấy địa chỉ ảo 0x1000 nhưng ánh xạ đến hai trang vật lý khác nhau. MMU dịch địa chỉ ảo qua page table và kiểm tra quyền; TLB lưu đệm thông tin dịch địa chỉ, khác với data cache.

Process A
Virtual 0x1000
↓ MMU / page table
Physical Page 5
Process B
Virtual 0x1000
↓ MMU / page table
Physical Page 19

15. Page fault có phải lỗi chương trình?

Không nhất thiết. Trang hợp lệ nhưng chưa hiện diện có thể tạo page fault; kernel xử lý rồi cho process tiếp tục. Truy cập bất hợp lệ có thể gây SIGSEGV. Minor page fault giải quyết không cần I/O lấy trang từ storage; major page fault cần I/O.

/usr/bin/time -v ./my_program

16. Swap có phải RAM mở rộng?

Swap hỗ trợ quản lý trang khi thiếu bộ nhớ nhưng storage thường chậm hơn RAM. zram có thể tạo swap nén trong RAM. Swap thrashing có thể làm hệ thống chậm nghiêm trọng.

               total    used    free  buff/cache  available
Mem:            8Gi     5Gi   500Mi      2.5Gi       3Gi

free thấp chưa chắc thiếu RAM. Linux dùng RAM cho cache và có thể thu hồi. Cần xem available, swap, reclaim, PSI và ảnh hưởng thực tế.

Phần VII — Storage và Page Cache

17. Tại sao đọc file lần hai thường nhanh hơn?

Linux giữ dữ liệu file trong page cache. Lần đầu có thể cần storage I/O; lần tiếp theo có thể đọc từ RAM nếu cache còn tồn tại.

18. write() thành công đã an toàn trên SSD chưa?

write(fd, buffer, size);
fsync(fd);

write() thành công không bảo đảm dữ liệu đã bền vững trên thiết bị. Buffering, page cache và writeback có thể trì hoãn ghi. fsync() yêu cầu đồng bộ, nhưng độ bền thực tế còn phụ thuộc filesystem, controller, cache thiết bị và flush. Với thiết bị ghi log dễ mất điện, cần cân bằng durability, latency và write amplification; gọi fsync sau mỗi bản ghi có thể tốn kém.

Phần VIII — Interrupt, Timer và DMA

19–20. Polling là gì?

CPU có thể liên tục hỏi thiết bị đã sẵn sàng chưa (polling), hoặc thiết bị báo sự kiện (interrupt).

while (!(STATUS_REG & RX_READY)) {
    // Busy-wait
}
read_data();

Polling có thể lãng phí CPU khi chờ lâu, nhưng có lợi trong một số workload tốc độ cao. Linux networking sử dụng cơ chế phối hợp như NAPI.

21–22. Interrupt và context switch

CAN Controller nhận frame
↓ IRQ
CPU / Interrupt Controller
↓
Kernel interrupt handler / Driver
↓
Đánh thức tác vụ nhận dữ liệu

Interrupt giống chuông cửa: thay vì liên tục kiểm tra cửa, bạn phản ứng khi có chuông. Nhưng quá nhiều interrupt cũng gây overhead. Interrupt không nhất thiết là context switch: sau handler, thread đang chạy có thể tiếp tục.

23. Timer dùng để làm gì?

Timer hỗ trợ timeout, đánh thức thread, các tác vụ định kỳ và scheduling. nanosleep() yêu cầu ngủ một khoảng nhưng không bảo đảm thread chạy lại đúng thời điểm tuyệt đối.

struct timespec ts = { .tv_sec = 0, .tv_nsec = 10000000 };
nanosleep(&ts, NULL);

24. DMA là gì? Vì sao vẫn cần driver?

NIC / Peripheral
⇄ DMA ⇄
RAM / Buffers
CPU + Driver: descriptor · buffer · mapping · sync · completion

DMA cho phép thiết bị truyền dữ liệu với bộ nhớ mà CPU không phải copy từng byte. Driver vẫn cấp buffer, thiết lập descriptor, DMA mapping, quản lý ownership và cache coherency. Trên một số ARM không coherent, đồng bộ sai có thể khiến CPU thấy dữ liệu cũ.

Liên hệ CAN/TWAI ESP32: CAN controller xử lý giao thức, transceiver chuyển đổi tín hiệu điện, CPU/driver quản lý truyền nhận. Không được suy ra mọi CAN controller đều dùng DMA.

Phần IX — Hệ điều hành thực sự làm gì?

25. Vì sao cần hệ điều hành?

Nếu không có OS, mỗi ứng dụng phải tự quản lý sector đĩa, RAM, CPU, thiết bị và quyền truy cập. Linux cung cấp abstraction, resource management và isolation/protection.

26. Abstraction — trừu tượng hóa thiết bị

int fd = open("hello.txt", O_RDONLY);
int tty = open("/dev/ttyUSB0", O_RDWR);
Application: open / read / write / close
↓
Linux Kernel: VFS / I/O subsystems
↓
Filesystem
TTY Driver
Device Driver

Không phải thiết bị nào cũng có ngữ nghĩa file thường: có ioctl(), mmap(), socket. SocketCAN thường truy cập qua socket thay vì mở /dev/can0. Abstraction không xóa giới hạn vật lý.

27. Resource management

Kernel lập lịch thread, quản lý bộ nhớ, I/O, quyền và thu hồi tài nguyên. Phần lớn mã ứng dụng vẫn chạy trong user mode.

Process root vẫn chạy mã ứng dụng trong user mode; root không đồng nghĩa luôn chạy ở CPU kernel mode.

Phần XI — Lab: lập hồ sơ máy Linux

Quan sát MemTotal, MemFree, MemAvailable, Buffers, Cached, SwapTotal và SwapFree. RAM used cao chưa đủ chứng minh thiếu bộ nhớ.

Phần XII — Latency và Throughput

39. Tại sao xử lý nhiều yêu cầu mà vẫn phản hồi chậm?

Latency là thời gian một yêu cầu hoàn tất. Throughput là lượng công việc mỗi đơn vị thời gian. Trạm thu phí 10 làn xử lý nhiều xe/phút, nhưng thời gian một xe qua làn không tự giảm.

Little's Law

L = λ × W

L là số công việc trung bình trong hệ thống; λ là tốc độ hoàn thành; W là thời gian trung bình. Ví dụ 100 request/s × 0,2 s = 20 request trung bình đang trong hệ thống, khi thỏa điều kiện áp dụng.

**# Bài 01 — Nền tảng máy tính và hệ điều hành** [Mục lục]\(../README.md) · [Bài 02 →]\(02-linux-va-distro.md) **## Mục tiêu và chuẩn bị** Không yêu cầu kiến thức Linux trước đó. Sau bài này, bạn phải giải thích được CPU thực thi chương trình, bộ nhớ giữ dữ liệu và hệ điều hành chia sẻ tài nguyên như thế nào. Phần lệnh có thể thực hiện sau khi cài VM ở bài 05. Hãy giữ một ví dụ xuyên suốt: bạn chạy chương trình đọc một file rồi in nội dung ra màn hình. CPU thực thi lệnh của chương trình; RAM chứa lệnh và dữ liệu đang dùng; kernel giúp chương trình tìm file, truy cập thiết bị và chia CPU với các chương trình khác. **## 1. Từ chương trình đến CPU** Chương trình trên đĩa là dữ liệu. Khi chạy, hệ điều hành tạo tiến trình và thiết lập không gian địa chỉ để CPU lấy lệnh, giải mã rồi thực thi. Thanh ghi giữ trạng thái đang xử lý: vị trí lệnh, toán hạng, con trỏ stack. CPU không trực tiếp hiểu Python hoặc Bash; interpreter của chúng là chương trình mã máy đang thực thi. **\*\*Chương trình\*\*** là mã và dữ liệu được lưu trong file; **\*\*tiến trình\*\*** là một lần chương trình đang chạy, có không gian địa chỉ và tài nguyên do hệ điều hành quản lý. Một chương trình có thể có nhiều tiến trình. **\*\*Thread\*\*** là luồng thực thi bên trong tiến trình: các thread chia sẻ nhiều tài nguyên của tiến trình nhưng mỗi thread có trạng thái thực thi và stack riêng. Ví dụ, với \`cat hello.txt\`, shell yêu cầu khởi chạy \`cat\`; CPU thực thi mã máy của \`cat\`. Khi \`cat\` cần mở và đọc file rồi ghi ra terminal, nó gọi **\*\*system call\*\*** để kernel xử lý phần cần quyền truy cập tài nguyên. Python interpreter cũng là một chương trình mã máy: nó đọc và thực hiện ý nghĩa mã Python, chứ CPU không tự hiểu cú pháp Python. Mã và dữ liệu được ánh xạ vào không gian địa chỉ; các trang cần thiết có thể được nạp theo nhu cầu, không phải toàn bộ chương trình luôn nằm trong cache. **### Diễn giải từng bước: chạy \`cat hello.txt\`** 1\. Shell đọc dòng lệnh bạn nhập. Nó phân tích \`cat\` là tên chương trình và \`hello.txt\` là đối số. Shell tìm file thực thi tương ứng với \`cat\` theo \`PATH\`. 2\. Shell yêu cầu kernel tạo một tiến trình con và chạy chương trình \`cat\`. Kernel chuẩn bị không gian địa chỉ ảo, ánh xạ mã chương trình và thư viện cần thiết, tạo stack ban đầu rồi đặt trạng thái để CPU bắt đầu thực thi. 3\. CPU thực thi các lệnh máy của \`cat\`. Khi cần dữ liệu, CPU tìm trong thanh ghi và cache; nếu không có, nó lấy từ tầng thấp hơn. Nếu trang bộ nhớ cần dùng chưa có trong RAM, có thể xảy ra **\*\*page fault\*\*** để kernel xử lý. Page fault không mặc nhiên là lỗi chương trình; nó có thể là một phần bình thường của cơ chế nạp trang theo nhu cầu. 4\. \`cat\` yêu cầu kernel mở và đọc file. Dữ liệu có thể đã nằm trong page cache của RAM, hoặc kernel phải nhờ tầng filesystem và driver lấy từ thiết bị lưu trữ. 5\. Sau khi nhận dữ liệu, \`cat\` yêu cầu ghi ra terminal và kết thúc. Kernel thu hồi tài nguyên của tiến trình; shell tiếp tục nhận lệnh mới. Đường đi thực tế có thể khác ở từng hệ thống: thư viện thường bọc system call, file có thể được đọc thành nhiều lần, và CPU có thể tạm dừng \`cat\` để chạy thread khác. Điều quan trọng là phân biệt **\*\*lệnh máy CPU thực thi\*\*** với **\*\*dịch vụ kernel cung cấp\*\***. Một socket CPU có thể chứa nhiều core. Một core có thể cung cấp nhiều hardware thread nhờ SMT, nhưng các thread đó vẫn chia sẻ một số tài nguyên thực thi. Vì thế 8 logical CPU không mặc nhiên bằng 8 core vật lý. Trong VM, vCPU còn phải được hypervisor lập lịch lên tài nguyên host. Ví dụ **\*\*1 socket × 4 core/socket × 2 thread/core = 8 logical CPU\*\***. Một thread phần mềm thường chỉ thực thi trên một logical CPU tại mỗi thời điểm; thêm logical CPU không tự làm phần việc tuần tự nhanh gấp đôi. Trong VM, thông tin topology mà \`lscpu\` thấy là cấu hình được trình bày cho guest, không nhất thiết là topology vật lý của host. **\*\*Lập lịch CPU\*\*** nghĩa là kernel chọn thread nào được chạy trên logical CPU nào. Nếu số thread sẵn sàng chạy nhiều hơn số logical CPU, chúng phải thay phiên. Khi đổi từ thread này sang thread khác, hệ thống phải lưu và khôi phục trạng thái thực thi; đó là một phần của **\*\*context switch\*\***. Vì việc chuyển đổi có chi phí, tạo thật nhiều thread không tự động làm chương trình nhanh hơn. Ngược lại, nếu một thread đang chờ đọc dữ liệu, CPU có thể chạy thread khác trong thời gian chờ. Ví dụ một phép tính gồm 80% công việc tuần tự và 20% có thể chia đều cho nhiều core. Dù có thêm rất nhiều core, phần 80% tuần tự vẫn phải chạy; vì vậy tổng thời gian không thể giảm tuyến tính theo số core. Đây là cách tự kiểm tra một lời quảng cáo kiểu “8 logical CPU nên chương trình nhanh gấp 8 lần”. **## 2. Thứ bậc bộ nhớ** \`\`\`text Register → cache L1/L2/L3 → RAM → SSD/HDD   thường nhanh, nhỏ             thường chậm hơn, lớn hơn \`\`\` Cache giữ bản sao dữ liệu để giảm thời gian chờ RAM. Nếu CPU phải chờ RAM, chưa thể kết luận ổ đĩa chậm: RAM và storage là các tầng khác nhau. Cache tận dụng hai kiểu **\*\*locality\*\***: theo thời gian (vừa dùng một giá trị thì có thể dùng lại sớm) và theo không gian (vừa dùng một địa chỉ thì có thể dùng tiếp địa chỉ gần đó). Bởi vậy, duyệt mảng liên tiếp thường thuận lợi cho cache hơn lần theo con trỏ rải rác. Đây là xu hướng, không phải bảo đảm cho mọi workload. RAM và storage trao đổi dữ liệu qua bộ điều khiển và bus; ổ đĩa 1 TB không làm máy có thêm 1 TB RAM. Swap có thể dùng storage hỗ trợ khi thiếu RAM nhưng thường chậm hơn RAM vật lý. Hãy tưởng tượng bạn đọc một cuốn sách: thông tin đang nhớ trong đầu giống dữ liệu rất gần CPU; trang sách đang mở giống cache; sách trên bàn giống RAM; sách cất trong tủ giống storage. Ví dụ này chỉ giúp hình dung **\*\*chi phí lấy dữ liệu\*\***: cấu trúc phần cứng thật phức tạp hơn và dữ liệu không nhất thiết đi qua từng tầng theo đúng một hàng thẳng. **\*\*Latency\*\*** là thời gian chờ một lần truy cập hoặc một yêu cầu hoàn tất. **\*\*Throughput\*\*** là tổng lượng công việc hoàn thành trong một khoảng thời gian. Một thiết bị có thể xử lý rất nhiều yêu cầu cùng lúc nhưng từng yêu cầu vẫn phải chờ lâu. Khi phân tích hiệu năng, hãy hỏi rõ đang đo thời gian của *\*một yêu cầu\** hay số yêu cầu *\*mỗi giây\**. RAM lưu trạng thái đang hoạt động và thường mất dữ liệu khi mất điện. Storage giữ dữ liệu lâu dài, nhưng ghi vào bộ đệm RAM chưa đồng nghĩa dữ liệu đã bền vững trên thiết bị. Bài 23 sẽ giải thích writeback và \`fsync\`. Linux còn dùng RAM làm **\*\*page cache\*\*** cho dữ liệu file. Lần đầu đọc một file có thể cần truy cập thiết bị; lần sau đọc cùng nội dung có thể được phục vụ từ RAM. Vì cache có thể được thu hồi khi ứng dụng cần bộ nhớ, \`free\` báo nhiều RAM \`used\` không tự nó chứng minh máy thiếu RAM. Cần nhìn thêm \`available\`, hoạt động swap và tình trạng ứng dụng. **## 3. Interrupt, timer và DMA** Interrupt cho phép thiết bị báo sự kiện để CPU xử lý, thay vì CPU luôn hỏi thiết bị đã xong chưa. Một số đường I/O vẫn dùng polling tùy thiết bị và tải công việc. Timer tạo cơ sở để hệ điều hành theo dõi thời gian, đánh thức tác vụ và đánh giá việc chuyển task; một sự kiện timer không đồng nghĩa chắc chắn có chuyển tiến trình ngay lúc đó. DMA cho phép thiết bị truyền dữ liệu với bộ nhớ mà CPU không phải sao chép từng byte; CPU và driver vẫn thiết lập buffer, đồng bộ khi cần và xử lý hoàn tất. Hệ điều hành cung cấp ba chức năng cốt lõi: trừu tượng hóa thiết bị, phân phối tài nguyên và cách ly hoạt động. Tiến trình nhìn thấy file thay cho chi tiết sector, không gian địa chỉ riêng thay cho toàn bộ RAM vật lý. \- **\*\*Trừu tượng hóa:\*\*** ứng dụng làm việc với file và socket thay vì tự điều khiển sector đĩa hoặc thanh ghi thiết bị. \- **\*\*Phân phối tài nguyên:\*\*** scheduler chọn thread chạy trên CPU; kernel quản lý RAM và yêu cầu I/O của nhiều tiến trình. \- **\*\*Cách ly và kiểm soát:\*\*** mỗi tiến trình có không gian địa chỉ ảo riêng; quyền truy cập và ranh giới user/kernel giới hạn tác động của chương trình lên chương trình khác. Địa chỉ ảo không phải địa chỉ RAM vật lý mà ứng dụng trực tiếp quản lý. **### Nối các khái niệm bằng một lần đọc file** \`\`\`text cat hello.txt   → shell khởi chạy tiến trình cat   → CPU chạy mã cat; dữ liệu cần dùng nằm trong cache/RAM   → cat gọi kernel để mở và đọc file   → kernel/filesystem/driver lấy dữ liệu từ page cache hoặc thiết bị   → thiết bị có thể dùng DMA và báo hoàn tất   → kernel trả dữ liệu; cat yêu cầu ghi ra terminal \`\`\` Nếu file đã nằm trong page cache, lần đọc có thể không cần truy cập ổ đĩa. Nếu tiến trình đang chờ I/O, scheduler có thể cho thread khác chạy. Vì thế cần phân biệt **\*\*CPU đang xử lý\*\*** với **\*\*tiến trình đang chờ\*\***. **## 4. Lab: lập hồ sơ máy** Trong terminal Linux, chạy các lệnh chỉ đọc: \`\`\`bash lscpu free -h lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS findmnt -no SOURCE,TARGET / cat /proc/cpuinfo | head -n 25 cat /proc/meminfo | head \`\`\` Ghi số socket, core/socket, thread/core, logical CPU; tổng RAM; nguồn của filesystem gắn tại \`/\`. Nếu trường topology không xuất hiện trong VM, ghi rõ giới hạn quan sát thay vì suy ra cấu hình host. \`lsblk\` cũ có thể dùng \`MOUNTPOINT\` thay \`MOUNTPOINTS\`; môi trường tối giản thiếu \`findmnt\` có thể xem \`/proc/mounts\`. Đọc \`free -h\` ở hai cột \`total\` và \`available\`. \`available\` ước lượng bộ nhớ có thể cấp cho ứng dụng mới mà không phải swap mạnh; \`used\` cao chưa đủ chứng minh máy sắp hết RAM vì Linux còn dùng RAM làm cache. Dùng \`findmnt\` xác định nguồn của \`/\`, rồi \`lsblk\` lần theo disk → partition → filesystem → mountpoint. Giải thích vì sao dung lượng đĩa không cộng vào RAM và vì sao tăng logical CPU không đảm bảo ứng dụng nhanh tuyến tính. **## 5. Mẹo và lỗi thường gặp** \- Phân biệt MB (1.000.000 byte) với MiB (1.048.576 byte) khi so sánh số liệu; công cụ có thể dùng hệ đơn vị khác nhau. \- Latency là thời gian một yêu cầu mất để hoàn tất; throughput là lượng công việc hoàn thành trong một khoảng thời gian. \- Phần trăm CPU phụ thuộc công cụ: một tiến trình đa luồng có thể vượt 100% khi 100% tương ứng một logical CPU. \- Tăng throughput không luôn giảm latency của từng yêu cầu; phải đọc đúng phép đo và tải thử nghiệm. \- Dữ liệu ứng dụng đã ghi chưa chắc đã bền trên đĩa vì có thể còn ở buffer của ứng dụng, kernel hoặc thiết bị. **## 6. Tự kiểm tra** 1\. CPU chờ RAM có nghĩa là ổ đĩa chậm không? **\*\*Không; đó là các tầng khác nhau.\*\*** 2\. Vì sao DMA vẫn cần driver? **\*\*Driver cấu hình giao dịch và xử lý đồng bộ/hoàn tất.\*\*** 3\. Một chương trình chỉ dùng một thread có tận dụng toàn bộ 8 core không? **\*\*Không tự động; cần phần việc song song và phần mềm hỗ trợ.\*\*** 4\. Máy báo 8 logical CPU từ 4 core có nghĩa hiệu năng gấp đôi 4 core không? **\*\*Không; SMT chia sẻ tài nguyên, kết quả phụ thuộc workload.\*\*** 5\. \`free\` báo RAM \`used\` cao có chắc máy sắp hết RAM không? **\*\*Không; cần xem \`available\`, cache và dấu hiệu thiếu bộ nhớ.\*\*** 6\. Khi \`cat\` đọc file đã có trong page cache, có bắt buộc đọc SSD lần nữa không? **\*\*Không; kernel có thể trả dữ liệu từ RAM.\*\*** **## Đọc thêm** Tra \`man lscpu\`, \`man free\`, \`man lsblk\`, \`man findmnt\`; xem định nghĩa trường trong manual trước khi diễn giải số liệu.
