Bài 32 — Phân tích CPU và bộ nhớ chuyên sâu trong Linux

Linux Performance Engineering · CPU Scheduling · Memory Management · NUMA · PSI · Cgroups · Troubleshooting

Bài 31 đã giúp chúng ta hình thành tư duy tìm bottleneck (nút thắt hiệu năng). Bài 32 đi sâu vào hai tài nguyên quan trọng nhất của hệ thống: CPU và RAM.

Điều quan trọng nhất không phải học thuộc top, free, vmstat hay perf, mà là suy luận: Một ứng dụng chạy chậm, làm thế nào chứng minh chính xác nó chậm vì CPU không đủ, vì phải chờ CPU, vì thiếu bộ nhớ, vì tranh chấp khóa, hay vì bị Linux giới hạn tài nguyên?

Chúng ta liên kết bài 17 (memory), bài 19 (scheduler), bài 31 (bottleneck), rồi đi vào cách điều tra thực tế như khi xử lý sự cố production.

Phần I — Tư duy nền tảng: CPU cao không đồng nghĩa CPU là bottleneck

1. Đặt vấn đề: Server chậm, có nên nâng cấp CPU?

Giả sử server Linux chạy API. Bình thường: 1.000 request/giây; phản hồi trung bình 20 ms; CPU 40%; RAM 60%. Một ngày, request mất 500 ms, CPU 95%, RAM vẫn còn trống, khách hàng báo timeout.

Người mới: “CPU 95%, nâng 4 core lên 8 core!”. Senior hỏi: 95% CPU đang thực sự làm việc gì?

Có thể CPU tính toán cần thiết, xử lý quá nhiều syscall, chạy vòng lặp vô nghĩa, nhiều thread tranh mutex, xử lý interrupt, bị quota, hoặc liên tục cache miss. CPU 95% cũng không có nghĩa mọi request đang chờ CPU.

Ví dụ đời sống: Nhà hàng

CPU core là đầu bếp; process/thread là đơn hàng; run queue là hàng đơn chờ; RAM là bàn chuẩn bị nguyên liệu; disk là kho xa; mutex là dụng cụ chỉ một người dùng; CPU quota là giới hạn thời gian làm việc.

Nếu nhà hàng chậm, hỏi: đầu bếp bận nấu, đơn xếp hàng, chờ nguyên liệu, tranh chảo, hay quản lý hạn chế giờ làm? Cùng một triệu chứng, nhiều nguyên nhân khác nhau.

Phần II — CPU thực sự hoạt động như thế nào?

2. Phân biệt CPU time, wall time và waiting time

Giả sử request cần 10 ms tính toán, 30 ms chờ disk, 40 ms chờ network, 20 ms chờ scheduler cấp CPU. Tổng thời gian thực là 100 ms, nhưng CPU execution chỉ khoảng 10 ms. Đây là ví dụ tuần tự, không chồng lấn.

T_{wall}=10+30+40+20=100\text{ ms}
T_{CPU}=10\text{ ms}
Timeline request — 100 ms
10203040
🟢 CPU 10 ms🟠 Runnable wait 20 ms⚪ Disk 30 ms🟣 Network 40 ms

Câu hỏi: Thêm CPU gấp đôi, request giảm còn 50 ms? Không nhất thiết. Nếu xóa toàn bộ runnable wait, vẫn còn 80 ms. Phải phân tách latency trước khi tối ưu.

CPU time là thời gian process/thread thực sự thực thi trên CPU, gồm user time và system time:

T_{CPU}=T_{user}+T_{system}

Wall time là thời gian đồng hồ thực trôi từ bắt đầu đến kết thúc.

/usr/bin/time -v ./my_program

User time (seconds): 1.80
System time (seconds): 0.20
Elapsed (wall clock) time: 0:05.00

CPU time 2 giây, wall time 5 giây. Phần còn lại có thể là sleeping, scheduler wait, I/O và các loại chờ khác; không thể quy hết cho I/O. Process đa luồng có thể có CPU time lớn hơn wall time do chạy song song.

3. CPU utilization: 100% nghĩa là gì?

Một logical CPU thường chạy một luồng thực thi tại một thời điểm. Một thread CPU-bound có thể tiêu thụ gần 100% một logical CPU; 4 thread có thể tiêu thụ 4 CPU. top có thể hiển thị process đa luồng tới 400% ở chế độ Irix. Cách chuẩn hóa khác nhau giữa công cụ.

Mô phỏng CPU utilization

Utilization lý tưởng75%
Thread chờ CPU0

Mô hình lý tưởng: worker luôn runnable, không quota/affinity/overhead.

Thử 4 CPU và 8 worker: utilization 100% nhưng 4 worker không thể chạy đồng thời. Chúng ở run queue.

Phần III — Run queue, scheduler và CPU contention

4. Runnable khác Running thế nào?

Running: đang thực thi trên CPU. Runnable: đủ điều kiện chạy nhưng chưa được CPU phục vụ. Sleeping: chờ sự kiện, timer, I/O hoặc điều kiện đồng bộ.

Trong Linux, trạng thái R của ps bao gồm cả đang chạy và runnable đang chờ. Task runnable chờ CPU khác task sleeping chờ network, dù cả hai đều làm tăng request latency.

5. Run queue length

Run queue phản ánh lượng công việc runnable. Với 4 CPU, 2 task có thể chạy đồng thời; 4 task dùng hết 4 CPU; 8 task cạnh tranh CPU; 40 task có thể là quá tải nghiêm trọng. Đây là mô hình đơn giản, chưa xét affinity, SMT, quota, ưu tiên và per-CPU runqueue.

vmstat 1

 r  b   swpd   free   buff  cache  si so  us sy id wa
 8  0      0 500000  12000 800000 70 10  0 20 10  0

r=8 nghĩa là có 8 task runnable tại mẫu đó, không chứng minh hệ thống liên tục quá tải. So với số CPU thực sự khả dụng:

nproc

Phản biện: Run queue 8 trên 32 CPU có thể bình thường; container quota 2 CPU dù host 32 CPU có thể rất căng. Run queue phải đặt cạnh capacity và giới hạn.

6. CPU utilization cao nhưng run queue thấp

Ví dụ CPU utilization 95%, run queue khoảng 1, server 16 CPU: chưa đủ kết luận CPU bottleneck. Có thể một số CPU bận interrupt, task bị affinity hoặc số liệu đo khác phạm vi.

mpstat -P ALL 1
pidstat -u -t 1
taskset -pc <PID>
cat /proc/<PID>/status | grep Cpus_allowed_list

16 CPU của host không đồng nghĩa process được phép chạy trên cả 16 CPU.

Phần IV — User time, system time, iowait, irq và softirq

7. CPU accounting

top

%Cpu(s): 65.0 us, 20.0 sy, 5.0 id, 8.0 wa, 1.0 hi, 1.0 si
Trường Ý nghĩa Câu hỏi
us User-space execution Code ứng dụng làm gì?
sy Kernel execution Kernel path nào tốn CPU?
id Idle CPU có rảnh không?
wa I/O wait accounting Có I/O gây đình trệ không?
hi Hardware interrupt Thiết bị nào tạo interrupt?
si Software interrupt Network/deferred processing nào hoạt động?
st Steal time Hypervisor có lấy mất thời gian vCPU?

7.1 User time cao

Ứng dụng xử lý ảnh chạy vòng lặp tính toán sẽ có us cao. Dùng profiling tìm hot path:

perf record -g -p <PID> -- sleep 15
perf report

Hot path là đoạn code được thực thi nhiều hoặc tiêu tốn phần lớn CPU time; không cần tối ưu toàn bộ code.

7.2 System time cao

Ghi từng byte có thể sinh rất nhiều syscall:

for (int i = 0; i < 1000000; i++) {
    write(fd, "x", 1);
}

Thay bằng batch:

write(fd, buffer, 1000000);

Số syscall giảm mạnh, nhưng hiệu quả phụ thuộc buffering và storage. sy cao còn có thể do page fault, filesystem, network, reclaim và interrupt, không chỉ số syscall.

strace -c -p <PID>

strace có overhead đáng kể, cẩn trọng với production nhạy latency.

7.3 Iowait

Iowait không phải thời gian CPU đang thực thi I/O. Nó là accounting CPU trong điều kiện idle và có I/O đang chờ theo cơ chế Linux. Iowait cao không đo chính xác latency request; iowait thấp không chứng minh disk khỏe.

iostat -xz 1

Kết hợp latency ứng dụng, block I/O và I/O PSI.

7.4 Softirq cao

Network packet processing có thể đẩy CPU softirq lên cao, nhất là nhiều packet nhỏ.

cat /proc/softirqs
mpstat -P ALL 1

Nếu processing tập trung một CPU, kiểm tra RSS/RPS, interrupt affinity và thiết kế network. Tăng worker ứng dụng chưa chắc giải quyết được.

Phần V — Context switch

8. Context switch là gì?

CPU đang chạy A, scheduler chuyển sang B. Kernel duy trì và chuyển trạng thái thực thi, bookkeeping, có thể ảnh hưởng address space, cache/TLB locality.

Chi phí không cố định, phụ thuộc phần cứng, kernel và trạng thái cache.

Voluntary: task tự chờ, chẳng hạn blocking read(). Involuntary: scheduler preempt task vì cạnh tranh hoặc task ưu tiên cao hơn.

pidstat -w -p <PID> 1

cswch/s: voluntary context switches/s. nvcswch/s: non-voluntary switches/s.

Context switch cao không tự động là xấu: event-driven server có thể switch nhiều mà vẫn hiệu quả. Cần liên hệ throughput, latency, runnable wait và CPU profiling.

Phần VI — CPU migration và cache locality

9. Vì sao migration có thể làm chậm?

Thread A chạy trên CPU 0, thường đọc dữ liệu đã ở cache thuận lợi. Scheduler chuyển sang CPU 3, dữ liệu có thể cần lấy lại từ cấp cache khác hoặc memory hierarchy.

Cache thực tế có nhiều cấp, có thể chia sẻ; migration không có nghĩa mất toàn bộ cache. Scheduler vẫn migration để cân bằng tải: trade-off load balancing ↔ cache locality.

perf stat -e cpu-migrations,context-switches -- ./my_program
taskset -c 2 ./my_program

Pin CPU có thể gây mất cân bằng hoặc remote NUMA. Không phải tối ưu mặc định.

Phần VII — Hardware performance counters: Cache miss, branch miss, IPC

10. CPU utilization không nói CPU hữu ích đến đâu

Hai chương trình đều 100% một CPU nhưng A xử lý 1 triệu phần tử/s, B xử lý 5 triệu/s. CPU bận không cho biết lượng công việc hữu ích hoàn thành.

11. Instructions per cycle — IPC

IPC=\frac{Instructions\ retired}{CPU\ cycles}

2 tỷ instruction / 1 tỷ cycle = IPC 2. IPC cao/thấp không thể đánh giá tuyệt đối nếu chưa biết architecture và workload.

perf stat -e cycles,instructions -- ./my_program

Ví dụ 1 tỷ cycles, 500 triệu instructions → IPC 0.5. Không đủ chứng minh memory bottleneck: có thể cache miss, dependency chain, branch misprediction, pipeline stall hoặc instruction mix.

12. Cache miss

Truy cập mảng tuần tự thường có locality tốt:

for (int i = 0; i < N; i++) {
    sum += array[i];
}

Truy cập chỉ số ngẫu nhiên có thể kém locality:

for (int i = 0; i < N; i++) {
    sum += array[random_index[i]];
}

perf stat -e cache-references,cache-misses -- ./my_program

cache-misses phụ thuộc PMU và cách kernel ánh xạ sự kiện; không phải mọi miss của mọi cấp cache.

13. Branch misprediction

CPU dự đoán hướng nhánh để thực thi suy đoán:

if (value > threshold) {
    process_a();
} else {
    process_b();
}

Nếu khó dự đoán, CPU có thể phải bỏ công việc suy đoán và nạp lại pipeline.

perf stat -e branches,branch-misses -- ./my_program

Phản biện: Branch miss cao có nên bỏ mọi if? Không. Branchless code có thể tăng instruction hoặc memory access. Đo throughput/latency thực tế.

Phần VIII — Memory: RAM còn trống mà ứng dụng vẫn chậm?

14. Virtual memory từ bài 17

Process làm việc với virtual address space. MMU, page table và TLB ánh xạ địa chỉ ảo sang vật lý. Một vùng có thể reserve mà chưa có physical page, fault-in khi truy cập, bị reclaim/swap, hoặc chia sẻ giữa process.

Virtual Size ≠ Resident RAM.

15. VIRT, RSS, PSS, USS

Giả sử process A có 50 MiB private resident, B có 30 MiB; hai process cùng chia sẻ library 20 MiB, toàn bộ resident và chia sẻ đều.

Metric Process A Process B
RSS 70 MiB 50 MiB
PSS 60 MiB 40 MiB
Private resident (xấp xỉ USS) 50 MiB 30 MiB

Tổng RSS = 120 MiB nhưng resident physical khác biệt chỉ 100 MiB. Tổng PSS = 100 MiB vì phân bổ shared memory theo tỷ lệ chia sẻ.

cat /proc/<PID>/smaps_rollup

Các trường thường gặp: Rss, Pss, Pss_Anon, Pss_File, Pss_Shmem, Private_Clean, Private_Dirty (tùy kernel). Thu thập smaps_rollup có chi phí, không nên lấy quá dày trên production.

Phần IX — Reserve, touch và page fault

16. Cấp phát 1 GiB chưa chắc dùng 1 GiB RAM

void *p = mmap(NULL, 1024UL * 1024 * 1024,
    PROT_READ | PROT_WRITE,
    MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);

mmap() thành công có thể chỉ tạo vùng địa chỉ ảo. Khi ghi vào từng page, kernel mới cấp physical page tương ứng theo cơ chế demand paging:

for (size_t i = 0; i < size; i += 4096) {
    ((char *)p)[i] = 1;
}

Giả định page size 4096 byte; hành vi thực tế chịu ảnh hưởng huge pages, zero page, overcommit.

Mô phỏng Reserve và Touch

Virtual pages
16/16 page được reserve
Physical resident pages
0/16 resident

Vùng địa chỉ ảo tồn tại nhưng chưa cần physical page riêng.

17. Minor và major page fault

Page fault không tự động là lỗi chương trình. CPU cần kernel xử lý một tình huống translation/access.

Minor fault: xử lý mà không cần đọc page từ backing storage tại thời điểm đó, như lần đầu ghi anonymous page.

Major fault: phải chờ I/O để đưa dữ liệu cần thiết vào memory theo phân loại Linux, như file-backed page không resident.

Major fault không đồng nghĩa mọi disk read; không phải mọi memory stall đều là page fault.

ps -o pid,min_flt,maj_flt,rss,vsz,comm -p <PID>
pidstat -r -p <PID> 1

Phần X — Memory pressure và reclaim

18. RAM gần đầy có luôn là vấn đề?

Không. Linux tận dụng RAM làm cache.

free -h

              total   used   free  buff/cache available
Mem:           16Gi    5Gi  500Mi    10Gi       9Gi

free=500MiB không tự chứng minh thiếu RAM. MemAvailable là ước lượng memory có thể cấp mà không cần swap đáng kể, không phải cam kết tuyệt đối.

19. Reclaim là gì?

RAM như bàn làm việc: hồ sơ đang dùng, hồ sơ đã dùng, tài liệu có thể lấy lại từ kho. Khi thiếu chỗ, phải dọn. Linux reclaim clean file-backed pages, xử lý dirty pages, có thể swap anonymous pages hoặc thu hồi cache khác.

Background reclaim: kswapd thu hồi trước. Direct reclaim: task cấp phát phải tham gia reclaim, có thể làm tăng latency. Ứng dụng có thể chậm trước khi OOM.

vmstat 1
grep -E 'pgscan|pgsteal|allocstall|pswpin|pswpout' /proc/vmstat

si/so trong vmstat là swap-in/out. Counter /proc/vmstat tích lũy từ boot; phải lấy chênh lệch nhiều mẫu để biết tốc độ.

Phần XI — PSI: Đo thời gian đình trệ

20. Vì sao CPU% và RAM% chưa đủ?

Hai server cùng dùng 90% RAM: A workload ổn định, không reclaim, latency tốt; B reclaim liên tục, p99 cao. PSI — Pressure Stall Information đo thời gian task bị stall do tài nguyên.

cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io

21. some, full, avg10, avg60, avg300, total

some avg10=12.00 avg60=8.00 avg300=3.00 total=12000000
full avg10=4.00 avg60=2.00 avg300=1.00 total=4000000

Với memory PSI: some có ít nhất một task không-idle bị stall; full tất cả task không-idle trong phạm vi đo cùng stall; avg10/60/300 là xu hướng theo cửa sổ giây; total là thời gian tích lũy microsecond. avg10=12 là tỷ lệ thời gian, không phải 12 task.

Mô phỏng PSI — cửa sổ 10 giây

3 giây có stall; 7 giây không stall.

Đây là tỷ lệ thời gian có stall, không phải số task chờ.

CPU utilization đo mức CPU bận; CPU PSI some đo thời gian có runnable task chờ CPU. Memory/I/O PSI đo stall tương ứng. System-level cpu full không được đọc giống memory full; cgroup lại có phạm vi riêng.

Tài liệu chính thức: https://docs.kernel.org/accounting/psi.html

Phần XII — Cgroup: Host còn CPU/RAM nhưng container vẫn chậm?

22. Đặt vấn đề

Host 32 CPU, 128 GiB RAM; container quota 2 CPU, memory limit 2 GiB. Container vẫn có thể throttling/OOM khi host dư tài nguyên. Capacity host ≠ capacity workload được phép sử dụng.

23. CPU quota và throttling

Cgroup v2:

cat /sys/fs/cgroup/cpu.max

200000 100000

Quota 200.000 microsecond CPU time trong chu kỳ 100.000 microsecond = trung bình 2 CPU. Không phải pin vào đúng 2 CPU cố định.

Mô phỏng CPU quota

CPU demand
Quota được cấp

Throttling thực tế còn phụ thuộc phân phối CPU bandwidth theo chu kỳ.

cat /sys/fs/cgroup/cpu.stat

nr_periods 10000
nr_throttled 3500
throttled_usec 24000000

nr_throttled: số chu kỳ có throttling. throttled_usec: accounting thời gian throttling tích lũy, không phải latency request trực tiếp. Host 20% CPU mà container throttled? Kiểm tra quota trước khi mua CPU host.

24. Memory cgroup và OOM

cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/memory.events

low 0
high 15
max 28
oom 2
oom_kill 1

high liên quan vượt ngưỡng memory.high; max là các lần usage sắp vượt memory.max; oom là sự kiện OOM; oom_kill đếm process bị OOM killer tiêu diệt theo accounting. Không phải mỗi max đều OOM.

Đọc đúng cgroup của process/container:

cat /proc/<PID>/cgroup

Root /sys/fs/cgroup không nhất thiết là cgroup workload.

Phần XIII — NUMA: RAM không còn đồng nhất

25. NUMA là gì?

Non-Uniform Memory Access: CPU truy cập local RAM và remote RAM có thể khác latency/bandwidth. Ví dụ hai văn phòng, mỗi văn phòng có kho riêng: lấy tài liệu ở kho gần thường thuận tiện hơn.

Remote không phải luôn chậm đáng kể với mọi workload; phụ thuộc kiến trúc và tải.

26. Kiểm tra NUMA

numactl --hardware

available: 2 nodes (0-1)
node 0 cpus: 0 1 2 3
node 0 size: 16384 MB
node 1 cpus: 4 5 6 7
node 1 size: 16384 MB

numastat
numastat -p <PID>
cat /proc/<PID>/numa_maps

Pin process CPU node 0 nhưng memory ở node 1 có thể gây remote access:

taskset -c 0-3 ./app
numactl --cpunodebind=0 --membind=0 ./app

CPU placement và memory placement phải xét cùng nhau. Binding có thể thất bại nếu không đáp ứng chính sách memory; VM lộ một node không chứng minh host vật lý không NUMA.

Phần XIV — Lab 1: CPU-bound so với Sleeping

27. Mục tiêu lab

Chứng minh process tồn tại không có nghĩa dùng CPU; CPU-bound tiêu thụ CPU time; sleeping có wall time nhưng gần như không tiêu thụ CPU; ps, pidstat, wchan cho các góc nhìn khác nhau. Chạy trong VM/lab có kiểm soát.

28. Chạy CPU-bound

Terminal 1:

timeout 10s python3 -c 'while True: pass' &
wrapper_pid=$!
ps -eo pid,ppid,stat,pcpu,wchan:24,args --forest
wait "$wrapper_pid"

timeout giới hạn 10 giây; Python tạo busy loop; & chạy background; $! lưu PID job background (thường timeout); ps --forest tìm Python con; wait chờ kết thúc. timeout có thể trả 124 khi hết thời gian, không phải lỗi bất ngờ của lab.

Terminal 2:

pidstat -u -w 1 10

Python có thể dùng gần 100% một logical CPU; trên máy 8 CPU, CPU tổng thể chỉ khoảng 12.5%.

29. Chạy sleeping task

sleep 10 &
sleep_pid=$!
ps -p "$sleep_pid" -o pid,stat,pcpu,wchan:24,args
wait "$sleep_pid"

sleep chờ timer, không chạy CPU liên tục. wchan có thể hiển thị wait channel nếu hỗ trợ và đủ quyền.

Quan sát CPU-bound Sleeping
Wall time Khoảng 10 s Khoảng 10 s
CPU time Có thể gần 10 CPU-s Gần 0
CPU usage Cao trên 1 core Rất thấp
Trạng thái Chủ yếu R Chủ yếu S
Wchan Thường không chờ Có thể hiện wait channel

Các số thực tế phụ thuộc scheduler, quota và VM. Vì sao sleep 10 mất 10 giây mà CPU time không phải 10 giây? Thời gian tồn tại khác thời gian được CPU thực thi.

Phần XV — Lab 2: Reserve và Touch bộ nhớ

30. Tạo chương trình thí nghiệm

import mmap
import os
import time

SIZE = 64 * 1024 * 1024
page_size = os.sysconf("SC_PAGE_SIZE")
mem = mmap.mmap(-1, SIZE)

print("PID:", os.getpid(), flush=True)
print("Reserved 64 MiB", flush=True)
input("Press Enter to touch memory...")

for offset in range(0, SIZE, page_size):
    mem[offset] = 1

print("Touched all pages", flush=True)
input("Press Enter to exit...")
mem.close()

Lưu memory_lab.py, chạy:

nano memory_lab.py
python3 memory_lab.py

Terminal khác:

cat /proc/<PID>/smaps_rollup
vmstat 1
cat /proc/pressure/memory
pidstat -r -p <PID> 1

Trước touch, virtual mapping tồn tại nhưng không nhất thiết resident đủ 64 MiB; sau touch, RSS thường tăng. Nếu 64 MiB không gây pressure, không được kết luận reclaim tốt. Lab chỉ chứng minh mapping/residency, chưa đánh giá reclaim/OOM.

Phần XVI — Memory leak: RSS tăng có phải leak?

31. Đặt vấn đề

RSS 100 MiB ban đầu, 300 MiB sau 1.000 request, 500 MiB sau 2.000 request. Có thể leak thật, allocator giữ memory tái sử dụng, hoặc cache tăng. RSS còn phụ thuộc residency và shared mappings.

Memory leak là memory không còn cần thiết nhưng vẫn bị giữ hoặc không giải phóng đúng cách.

void handle_request(void) {
    char *buffer = malloc(1024);
    if (buffer == NULL) return;
    process(buffer);
    // Quên free(buffer)
}

Một triệu request × 1 KiB ≈ 977 MiB bị giữ. Nhưng free() không bảo đảm RSS giảm ngay: allocator có thể giữ memory, fragmentation và cơ chế trả page về OS ảnh hưởng kết quả.

char *p = malloc(1024 * 1024);
free(p);

Phân biệt bằng RSS/PSS time series, request count, live objects, cache size, allocator stats và heap profile. Nếu live allocation tăng không giới hạn qua các chu kỳ tương đương, giả thuyết leak mạnh hơn.

Ba kiểu tăng memory giả định

🟠 Leak liên tục🟢 Cache đạt giới hạn🟣 Ổn định

Dữ liệu mô phỏng, không phải kết quả đo thực tế.

Đường tăng liên tục không tự động chứng minh leak; cache tăng rồi ổn định có thể bình thường. Không phải mọi leak đều tuyến tính.

Phần XVII — Thread chờ khóa: Thêm CPU không giải quyết?

32. Lock contention

8 thread cùng cập nhật shared counter:

pthread_mutex_lock(&lock);
shared_counter++;
pthread_mutex_unlock(&lock);

Critical section ngắn có thể ổn; nhưng nếu giữ mutex khi chạy công việc 100 ms:

pthread_mutex_lock(&lock);
do_expensive_work(); // 100 ms
pthread_mutex_unlock(&lock);

Tối đa xấp xỉ 1 / 0.1 = 10 operations/s qua đoạn serial, giả sử mỗi operation bắt buộc đi qua và không có overhead khác. Thêm 100 thread không làm đoạn độc quyền chạy đồng thời.

Định luật Amdahl

S(N)=\frac{1}{s+\frac{1-s}{N}}

Nếu phần tuần tự 40%, speedup tối đa khi N tiến tới vô hạn là 1/0.4 = 2.5×.

Mô phỏng định luật Amdahl

Speedup lý tưởng
Giới hạn N → ∞

Bỏ qua overhead synchronization, scheduling và memory bandwidth.

Hướng tối ưu: giảm thời gian giữ lock; chuyển I/O ra ngoài critical section khi an toàn; sharding; per-thread/per-CPU counter; atomic khi phù hợp; giảm shared mutable state. Lock-free không luôn nhanh và có thể tăng coherence traffic, khó bảo đảm correctness.

Phần XIX — Case study: Cùng chậm, ba nguyên nhân

38. Case A — CPU-bound thật

CPU utilization: 98%
CPU PSI some: cao
Run queue: cao
Memory PSI: thấp
CPU throttling: không đáng kể

Profiler cho thấy hàm parse chiếm CPU. Tối ưu thuật toán, giảm allocation/copy, batch, cải thiện locality, tăng CPU nếu workload scale được. Không chỉ tăng RAM.

39. Case B — Memory pressure

CPU utilization: 45%
Memory PSI some: cao
Major faults: tăng
Reclaim: tăng mạnh
Swap-in: xuất hiện

Cache lớn gây latency. Đo working set — tập dữ liệu truy cập tích cực trong khoảng thời gian có ý nghĩa; kiểm tra eviction, giảm dữ liệu giữ, kiểm tra cgroup, tăng RAM nếu working set cần thiết vượt capacity. Không phải toàn bộ virtual memory là working set.

40. Case C — CPU quota throttling

Host CPU utilization: 15%
Container cpu.stat: throttling tăng
Container latency: cao

Host 32 CPU, container quota 1 CPU. Tối ưu quota hoặc CPU demand, không vội mua thêm CPU host.

Phần XXIII — Kiến thức mở rộng: Các vấn đề tương tự

44. CPU bottleneck và memory bottleneck có thể đồng thời

Ứng dụng xử lý dữ liệu: CPU tính nhiều, working set lớn hơn cache, cache miss cao, memory bandwidth gần bão hòa. Tăng CPU có thể làm core cạnh tranh bandwidth hơn, throughput không tăng tương ứng. CPU và memory phải xem cùng nhau.

45. Memory bandwidth khác memory latency

Latency: một lần truy cập mất bao lâu. Bandwidth: truyền được bao nhiêu dữ liệu mỗi giây. Như đường cao tốc: thời gian một xe đi từ A đến B khác số xe đi qua mỗi giây. Pointer chasing thường nhạy latency; streaming dữ liệu lớn thường nhạy bandwidth. Tăng RAM capacity không tự động tăng bandwidth hoặc giảm latency.

46. False sharing

struct Counters {
    long a;
    long b;
};

Thread 0 ghi a, thread 1 ghi b. Hai biến khác nhau có thể cùng cache line, khiến cache coherence chuyển quyền sở hữu qua lại. False sharing có thể giảm bằng tách biến ghi thường xuyên sang cache line khác, nhưng padding tăng memory footprint: phải đo trước/sau.

47. Tail latency và coordinated omission

Average 20 ms nhưng p99 500 ms có thể do scheduler, reclaim, GC, page faults, lock. Benchmark phải tránh coordinated omission: load generator ngừng/giảm gửi request khi hệ thống chậm khiến đo thiếu độ trễ người dùng trải nghiệm. Cần time series và latency distribution.

Performance=f(Execution,Waiting,Contention,Limits)

Đây là mô hình tư duy, không phải công thức vật lý thay số trực tiếp.
