Linux, GNU/Linux và bản phân phối

Giải thích chuyên sâu từ kernel, user space, GNU, distro, package, repository, version và backport đến container và Embedded Linux.

33 mục học · Code có thể sao chép · Sơ đồ · Câu hỏi phản biện · Lab tương tác · Hoạt động ngoại tuyến

Bài học này bắt đầu từ một câu hỏi nền tảng: Tại sao hai thiết bị đều chạy Linux, nhưng chương trình chạy tốt trên thiết bị này lại không chạy được trên thiết bị kia?

  • Ubuntu chạy được apt install nginx, nhưng một thiết bị nhúng báo apt: not found.
  • Một máy dùng systemctl restart nginx, máy khác không có systemctl.
  • Binary x86 không chạy trực tiếp trên board ARM.
  • Hai máy báo cùng kernel version nhưng driver có thể khác.

Muốn hiểu các hiện tượng này, ta phải xem Linux là một hệ thống gồm nhiều lớp có trách nhiệm khác nhau, không phải một khối phần mềm duy nhất.

Phần I — Linux thực sự là gì?

1. Khi nói “Tôi đang sử dụng Linux”, thực chất đang sử dụng cái gì?

Máy tính có CPU thực thi chỉ thị, RAM lưu dữ liệu đang sử dụng, ổ đĩa lưu file, card mạng truyền dữ liệu và các thiết bị nhập/xuất. Xét chương trình C đơn giản:

c
#include <stdio.h>

int main(void)
{
    printf("Hello Linux\n");
    return 0;
}
bash
gcc main.c -o main
./main
output
Hello Linux
❓ CPU có biết printf() là gì không?

Không. CPU thực thi chỉ thị máy; printf() là giao diện do thư viện C cung cấp.

❓ printf() có trực tiếp điều khiển màn hình không?

Thông thường không. Với stdout nối tới terminal, thư viện C xử lý định dạng và buffering, có thể gọi write(); kernel xử lý thao tác ghi, còn terminal emulator hiển thị dữ liệu.

Luồng printf() tới terminal

↓
Thư viện C (glibc / musl)

↓

↓
Linux Kernel
Kiểm tra file descriptor, thực hiện ghi
↓

Lưu ý: printf() có thể buffer dữ liệu trước khi gọi write(). Nếu stdout được redirect sang file hoặc pipe thì đích ghi sẽ khác terminal.

1.1. Application — Ứng dụng

Ứng dụng là chương trình thực hiện công việc cụ thể: nginx phục vụ web, cat đọc file, ls liệt kê thư mục, Python chạy chương trình, hoặc phần mềm điều khiển motor.

1.2. Library — Thư viện

Thư viện là mã có thể dùng lại. Ví dụ printf() thuộc thư viện C; glibc và musl là hai implementation. Không phải hàm thư viện nào cũng gọi kernel: strlen() có thể chạy hoàn toàn trong user space.

1.3. Kernel — Nhân hệ điều hành

Kernel quản lý process/thread, virtual memory, scheduler, filesystem, device drivers, network stack và phân quyền. Kernel không làm thay mọi việc của ứng dụng; nó cung cấp cơ chế để ứng dụng sử dụng tài nguyên an toàn, có kiểm soát.

❓ Tại sao không viết toàn bộ ứng dụng vào kernel?

Mã kernel có đặc quyền cao; lỗi truy cập bộ nhớ có thể làm sập toàn hệ thống. User space được cách ly bởi virtual memory và các cơ chế bảo vệ khác.

Phần II — Kernel Space và User Space

3. Tại sao phải phân chia hai không gian?

Kernel space là môi trường thực thi có đặc quyền cao của kernel và module. User space là môi trường của ứng dụng, shell, thư viện và nhiều dịch vụ.

4. Tại sao chương trình không trực tiếp điều khiển phần cứng?

Nếu hai chương trình tùy ý ghi lên ổ đĩa, dữ liệu có thể bị phá hỏng. Kernel cung cấp giao diện có kiểm soát và trừu tượng hóa phần cứng.

c
#include <fcntl.h>
#include <unistd.h>

int main(void)
{
    int fd = open("data.txt", O_WRONLY | O_CREAT, 0644);
    if (fd < 0) return 1;
    write(fd, "Hello\n", 6);
    close(fd);
    return 0;
}

open() yêu cầu mở file, write() ghi, close() giải phóng descriptor. Kernel kiểm tra quyền, filesystem và các tầng I/O. Ứng dụng không cần biết ổ đĩa là SATA, NVMe hay flash.

❓ write() trả về thành công nghĩa là dữ liệu đã chắc chắn xuống thiết bị lưu trữ?

Không. Dữ liệu có thể còn trong page cache. Khi cần yêu cầu đồng bộ xuống thiết bị lưu trữ, có thể dùng fsync() hoặc cơ chế phù hợp.

Phần III — GNU/Linux: Vì sao Linux kernel chưa đủ?

5. Biên dịch kernel xong đã có hệ điều hành hoàn chỉnh chưa?

Sau khi build kernel image, chẳng hạn Image trên ARM64, kernel có thể khởi tạo CPU, memory management, scheduler và driver. Nhưng để thành hệ thống hữu ích, thường cần init, thư viện, công cụ, shell (nếu cần), dịch vụ và ứng dụng. Hệ tối giản không bắt buộc có Bash.

6. GNU là gì?

GNU là dự án phần mềm tự do cung cấp nhiều công cụ Unix-like. GNU/Linux nhấn mạnh sự kết hợp Linux kernel với các thành phần GNU; không phải mọi hệ Linux đều dùng GNU.

7. Lệnh ls thuộc Linux hay GNU?

ls không nằm trong kernel. Trên Debian/Ubuntu thường thuộc GNU Coreutils; trên hệ nhúng có thể là applet BusyBox.

Thiết bị IoT có RAM và root filesystem hạn chế cần những lệnh như ls, cp, mv, cat, mkdir, rm, sh. GNU Coreutils cung cấp các chương trình riêng; BusyBox gom nhiều applet vào một executable.

Phần V — Linux Distribution (Distro)

9. Vì sao tồn tại Ubuntu, Debian, Fedora, Arch Linux?

Ai chọn kernel, thư viện, shell, init, repository, cấu hình và chính sách cập nhật? Distro là sản phẩm tích hợp và bảo trì các thành phần ấy. Hai xe dùng cùng động cơ vẫn khác hộp số, hệ thống điện và bảo trì; hai distro dùng Linux kernel vẫn có thể rất khác nhau.

9.1. Định nghĩa Distribution

Linux distribution là hệ thống tích hợp từ kernel, user space, package manager, cấu hình, kho phần mềm và chính sách hỗ trợ do tổ chức/nhóm phát hành duy trì.

❓ Ubuntu dựa trên Debian, vậy mọi tutorial Debian dùng được trên Ubuntu?

Không. Ubuntu có thể chọn phiên bản package, repository, cấu hình và lịch cập nhật khác Debian.

12. Vì sao cài kernel mới vẫn thấy kernel cũ?

Kernel K2 có thể đã được cài lên đĩa, trong khi RAM vẫn đang thực thi K1. Chỉ khi reboot và bootloader thực sự chọn K2 thì uname -r mới báo kernel mới.

Cài package ≠ thay kernel đang chạy

↓

↓
Reboot, bootloader chọn kernel
↓
Sau reboot: có thể chạy K2 → kiểm tra uname -r

Khi cập nhật để sửa driver Ethernet mà lỗi vẫn tồn tại, hãy kiểm tra kernel image, Device Tree, modules và boot configuration, không chỉ package manager.

Phần VII — Backport

13. Vì sao kernel cũ chưa chắc thiếu bản vá?

Backport là đưa một bản sửa từ nhánh mới về nhánh cũ đang được hỗ trợ, điều chỉnh để phù hợp với code/API của nhánh cũ.

Minh họa backport bản sửa
bash
apt changelog <ten-package>

Cần đối chiếu changelog, advisory và trạng thái package của distro, không chỉ so số upstream version hoặc suy đoán tình trạng CVE.

Phần VIII — Package, Repository và Dependency

14. Tại sao cài một ứng dụng kéo theo nhiều package?

Dependency là thành phần một package cần để hoạt động hoặc cài đúng cách. Như hệ camera cần camera, nguồn, dây và thiết bị lưu trữ, ứng dụng có thể cần thư viện mã hóa, nén và runtime.

bash
sudo apt install nginx

15. Package là gì?

Package là đơn vị phần mềm đóng gói có tên, version, kiến trúc, metadata dependency, file phần mềm và có thể có script cài đặt.

text
nginx
libssl...
libc...

Các tên chỉ minh họa thành phần, không phải danh sách dependency cố định của mọi Nginx.

16. Repository là gì?

Repository là nguồn package và metadata để package manager tìm, xác minh, tải và cài. Hình dung repository là kho hàng, package là sản phẩm, package manager là bộ phận mua hàng, dependency là danh sách linh kiện.

16.1. APT hoạt động như thế nào?

↓

↓

↓
Kiểm tra trạng thái ứng dụng / dịch vụ

Package cài thành công không đồng nghĩa dịch vụ chạy đúng: nginx có thể lỗi vì cổng 80 đang được dùng.

17. Vì sao không nên trộn repository?

Release hiện tại có thể dùng libX v1 trong khi repository khác cung cấp app B cần libX v2. Resolver có thể báo xung đột hoặc cài bộ thư viện làm phần mềm cũ không tương thích.

ABI — Application Binary Interface bao gồm các quy ước tương thích ở mức binary, như gọi hàm và bố trí dữ liệu. Thay đổi ABI không tương thích có thể khiến chương trình cũ lỗi.

❓ Dependency resolver thành công có bảo đảm runtime an toàn?

Không. Resolver chỉ giải các ràng buộc metadata; không đảm bảo mọi script, ứng dụng tùy biến và hành vi runtime tương thích. Cần kiểm thử và rollback.

Phần IX — Fixed Release và Rolling Release

18. Vì sao distro cập nhật với tốc độ khác nhau?

Fixed release (ví dụ Debian Stable) giữ nền tảng tương đối ổn định trong vòng đời release và có bước nâng cấp lớn riêng. Rolling release (ví dụ Arch Linux) cập nhật nhiều package liên tục hơn.

Mô hình phát hành (minh họa)
Sơ đồ không biểu diễn độ ổn định hoặc số lượng bản vá thực tế.

Trong Embedded Linux, cần cân nhắc khả năng tái tạo firmware, BSP, driver, bảo trì bảo mật, kiểm thử, OTA, rollback và vòng đời sản phẩm.

❓ Rolling release luôn tốt hơn vì package mới hơn?

Không. Package mới có tính năng và hỗ trợ phần cứng mới nhưng cũng có thể thay đổi không tương thích.

Phần X — Lab: Nhận diện một hệ Linux

19. Vì sao phải nhận diện máy trước tutorial?

Lệnh apt install nginx không chạy trên mọi distro. Phải nhận diện user space, kernel, architecture, PID 1 và package manager trước khi áp dụng hướng dẫn.

20. Các lệnh cần thực hiện

bash
cat /etc/os-release
uname -r
uname -m
ps -p 1 -o pid,comm,args
command -v apt
command -v dnf
command -v pacman
command -v systemctl

20.1. cat /etc/os-release

Nhận diện distro/release user space, ví dụ ID=debian và VERSION_ID="13". Không chứng minh kernel được build bởi cùng distro.

20.2. uname -r

Chuỗi release của kernel thực sự đang chạy, không phải phiên bản package kernel mới nhất trên đĩa.

20.3. uname -m

Kiến trúc mà kernel báo cho môi trường chạy, ví dụ x86_64 hoặc aarch64.

20.4. ps -p 1 -o pid,comm,args

Xem PID 1 trong môi trường quan sát. Trong container, PID 1 có thể là tiến trình đầu tiên của container, không phải init host.

20.5. command -v

bash
command -v apt
# Ví dụ: /usr/bin/apt

Chỉ xác định shell có tìm thấy lệnh trong PATH, không chứng minh repository chính thức hay cấu hình phù hợp.

Phần XII — Liên hệ Embedded Linux

23. Vì sao distro quan trọng với kỹ sư nhúng?

Board có thể dùng Debian rootfs, Buildroot tạo rootfs tối giản, hoặc Yocto Project build image cho sản phẩm. Buildroot và Yocto chủ yếu là hệ thống xây dựng embedded Linux, không đơn giản là distro desktop.

Device Tree không phải tầng thực thi nằm giữa kernel và root filesystem; sơ đồ liệt kê thành phần cần quan tâm.

25. Ví dụ board ARM: Binary không chạy

bash
gcc app.c -o app
scp app user@board:/tmp/
# Trên board:
/tmp/app
output

Một nguyên nhân là binary x86_64 được chạy trên ARM. Cần cross-compile với toolchain đúng kiến trúc, ABI và target root filesystem.

bash
aarch64-linux-gnu-gcc app.c -o app
file app
readelf -h app
readelf -l app
uname -m
❓ Hai board cùng ARM64 và cùng Linux kernel có chắc chạy chung một binary?

Không. Có thể khác glibc/musl, dynamic loader, version thư viện hoặc runtime. Cần xét architecture + ABI/toolchain + root filesystem.

output
No such file or directory

File ứng dụng có thể tồn tại mà lỗi vẫn xảy ra vì ELF interpreter được khai báo trong binary không có trên target. Dùng readelf -l để kiểm tra mục INTERP.

bash
ls -l ./app
readelf -l ./app

Phần XIV — Các vấn đề tương tự

27. Linux kernel và Linux API/ABI

c
printf()
malloc()
open()
read()
write()

printf() và malloc() là hàm thư viện, đôi khi dẫn đến system call. open(), read(), write() là giao diện thư viện thường dùng system call. Phân biệt điều này khi quan sát bằng strace.

28. Kernel driver và User-space driver

Không phải toàn bộ logic điều khiển thiết bị nằm trong kernel. Ứng dụng có thể giao tiếp qua /dev, sysfs, socket, ioctl hoặc framework driver user space. Các thao tác đặc quyền vẫn do kernel kiểm soát.

text
/dev/...
sysfs
socket
ioctl

29. Distro và BSP

BSP — Board Support Package — có thể gồm bootloader, kernel patches, Device Tree, drivers, build config và rootfs/recipe. Một board dùng Debian user space chưa chắc chạy kernel Debian tiêu chuẩn.

30. Package Update và Firmware Update

Embedded Linux có thể cập nhật image hoặc A/B partition thay vì nâng cấp package riêng lẻ.

text
Partition A: firmware hiện tại
Partition B: firmware mới

Thiết bị ghi bản mới vào B rồi chuyển boot. Cơ chế rollback tùy thiết kế. Cần cân nhắc tính nhất quán, dung lượng, bảo mật, kiểm thử và khả năng phục hồi.

33. Bài thực hành cuối

bash
echo "=== DISTRO ==="
cat /etc/os-release

echo "=== KERNEL ==="
uname -r

echo "=== ARCHITECTURE ==="
uname -m

echo "=== INIT ==="
ps -p 1 -o pid,comm,args

echo "=== PACKAGE MANAGERS ==="
for cmd in apt dnf pacman apk; do
    command -v "$cmd" || true
done

echo "=== SHELL ==="
readlink -f /bin/sh

echo "=== LS IMPLEMENTATION ==="
command -v ls
ls --version 2>&1 | head -n 3

Lưu ý: ls --version không được mọi implementation hỗ trợ; thông báo lỗi cũng là dữ liệu để phân tích.
