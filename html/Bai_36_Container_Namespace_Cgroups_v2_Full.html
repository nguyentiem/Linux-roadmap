MỤC 01 / 46

Đặt vấn đề: Vì sao Linux cần container?

Một IoT Gateway chạy nhiều dịch vụ: CAN Reader, MQTT Client, SQLite, REST API và monitoring. Nếu MQTT Client bị memory leak, nó có thể chiếm hết RAM, gây reclaim, swap hoặc OOM; CAN Reader dù độc lập vẫn bị ảnh hưởng.

Câu hỏi phản biện: Tại sao process độc lập vẫn ảnh hưởng nhau? Bởi vì process có address space riêng nhưng chia sẻ CPU, RAM vật lý, kernel, I/O và những tài nguyên cấp hệ thống. Process isolation không đồng nghĩa resource isolation.

Một giải pháp là tách mỗi service thành VM, nhưng VM thường cần guest kernel, bộ nhớ, thiết bị ảo và chi phí quản lý. Container giải quyết bài toán bằng cách chia sẻ kernel nhưng tạo góc nhìn và giới hạn tài nguyên thích hợp.

Ví dụ đời sống: Tòa chung cư có nhiều căn hộ. Mỗi căn có không gian riêng nhưng vẫn dùng chung kết cấu, điện nước và hệ thống kỹ thuật. Namespace như ranh giới góc nhìn; cgroup như hạn mức sử dụng; security như quyền ra vào; rootfs như nội thất của căn hộ.

MỤC 02 / 46

Container là tổ hợp cơ chế

Container là môi trường thực thi các Linux process được cấu hình bằng namespace, cgroups, root filesystem và chính sách bảo mật. Kernel không có một syscall duy nhất tên create_container().

Câu hỏi Cơ chế
Process nhìn thấy gì? PID, mount, network, UTS, IPC, user, cgroup, time namespaces
Process dùng được bao nhiêu tài nguyên? Cgroups v2
Process được phép làm gì? DAC, capabilities, seccomp, SELinux/AppArmor
Process nhìn thấy filesystem nào? Rootfs, mounts, OverlayFS

Container chia sẻ kernel host. Image Ubuntu trên host Debian không tạo ra Ubuntu kernel riêng. Root trong user namespace không mặc nhiên là root host; rootless vẫn cần đánh giá mount, device, network và kernel attack surface.

MỤC 03 / 46

PID namespace: cùng process, PID khác nhau

PID namespace tạo góc nhìn PID riêng. Một process có thể là PID 1200 trên host nhưng là PID 1 bên trong namespace con.

HOST:       1 systemd | 510 sshd | 1200 mqtt-service | 1500 can-reader
CONTAINER:  1 mqtt-service | 2 mqtt-helper

Đó vẫn là cùng task, không phải bản sao process. Trên host có thể kiểm tra ánh xạ:

cat /proc/1200/status | grep NSpid
# Ví dụ: NSpid: 1200 1

PID 1 đặc biệt về signal handling và child reaping. Nếu application trực tiếp làm PID 1, cần xử lý SIGTERM, zombie, graceful shutdown. Dockerfile dạng exec CMD ["python3", "app.py"] thường tốt hơn shell form CMD python3 app.py về chuyển signal. Một init nhỏ như tini có thể hỗ trợ.

Phản biện: PID 1 container có kill được PID 1 host không? Không chỉ vì cùng số PID: đó là các task khác nhau và kernel kiểm tra namespace, credentials và quyền signal.

MỤC 04 / 46

Mount namespace, rootfs và mount propagation

Mount namespace phân tách góc nhìn mount tree. Nó không tự tạo filesystem mới. Container runtime còn chuẩn bị rootfs và chuyển root directory bằng pivot_root hoặc cơ chế tương ứng.

HOST:       /etc  /home  /var  /data
CONTAINER:  /bin  /etc   /app  /tmp

chroot chỉ đổi root directory khi phân giải đường dẫn, không tự tạo PID namespace, giới hạn RAM/CPU hoặc security boundary hoàn chỉnh.

Mount propagation gồm shared, slave, private, unbindable. Nếu không kiểm soát propagation, thao tác mount có thể lan giữa các namespace theo quan hệ mount.

findmnt -o TARGET,PROPAGATION

Câu hỏi: Có mount namespace rồi là không thể ảnh hưởng mount host? Không; phải xét mount propagation và đặc quyền.

MỤC 05 / 46

Network namespace, veth và bridge

Network namespace tách interfaces, địa chỉ IP, routing table, socket binding và các trạng thái network theo namespace. Veth pair giống dây Ethernet ảo có hai đầu; một đầu trong container, một đầu host, có thể kết nối qua Linux bridge.

sudo ip netns add ns-a
sudo ip netns add ns-b
sudo ip link add veth-a type veth peer name veth-b
sudo ip link set veth-a netns ns-a
sudo ip link set veth-b netns ns-b
sudo ip -n ns-a addr add 10.10.0.2/24 dev veth-a
sudo ip -n ns-b addr add 10.10.0.3/24 dev veth-b
sudo ip -n ns-a link set lo up
sudo ip -n ns-b link set lo up
sudo ip -n ns-a link set veth-a up
sudo ip -n ns-b link set veth-b up
sudo ip netns exec ns-a ping -c 3 10.10.0.3
sudo ip netns del ns-a
sudo ip netns del ns-b

Lab dùng veth trực tiếp, không cần bridge. Hai container có thể cùng bind 0.0.0.0:8080 trong network namespaces riêng; khi publish cùng IP:port trên host vẫn có thể xung đột.

MỤC 07 / 46

Namespace chưa đủ: giới thiệu cgroups

Namespace chỉ đổi góc nhìn; một process while True: pass vẫn có thể tiêu thụ CPU. Cgroups (control groups) tổ chức các task để accounting và điều khiển tài nguyên. Cgroups v2 có cây phân cấp thống nhất.

/sys/fs/cgroup/
├── system.slice/
│   ├── ssh.service/
│   └── mqtt.service/
├── user.slice/
└── machine.slice/

nice thay đổi ưu tiên scheduling tương đối, không áp một quota CPU cứng. cpu.max giới hạn CPU bandwidth theo period.

MỤC 08 / 46

cpu.max: quota và period

cpu.max chứa hai giá trị: quota và period tính bằng microsecond.

50000 100000

Nhóm có 50.000 µs CPU time trong period 100.000 µs: tương đương 0,5 CPU trung bình. CPUQuota=50% không phải 50% của toàn bộ 8 CPU; CPUQuota=400% tương đương ngân sách 4 CPU, không cam kết luôn chạy trên bốn core.

[\text{CPU capacity tương đương}=\frac{\text{quota}}{\text{period}}]

Host có thể còn nhiều CPU rảnh nhưng container vẫn bị throttle nếu dùng hết quota. Quota là policy, không phải cơ chế chỉ hoạt động khi host bận.

MỤC 09 / 46

CPU throttling và multi-threaded workload

Giả sử quota 20 ms CPU time trên period 100 ms, có 4 worker CPU-bound chạy đồng thời trên 4 core. Trong mô hình lý tưởng, ngân sách có thể hết sau khoảng 20/4 = 5 ms wall-clock. Sau đó cgroup có thể bị throttle đến kỳ bổ sung ngân sách.

cat /sys/fs/cgroup/<path>/cpu.stat

Các counter: usage_usec, user_usec, system_usec, nr_periods, nr_throttled, throttled_usec, đôi khi nr_bursts, burst_usec.

[\text{Throttle period ratio}=\frac{\Delta nr_throttled}{\Delta nr_periods}]

Tỷ lệ period bị throttle không đồng nghĩa tỷ lệ hiệu năng mất đi. Phải kết hợp application latency, runnable tasks và CPU PSI.

MỤC 10 / 46

cpu.weight: chia tương đối khi tranh chấp

cpu.weight thường nằm trong khoảng 1–10000, mặc định 100. Hai nhóm có weight 100 và 300 có thể chia tài nguyên đang tranh chấp theo tỷ lệ gần 1:3 trong điều kiện phù hợp. Nếu nhóm A không cần CPU, B có thể tận dụng CPU còn rảnh, miễn không vướng giới hạn khác.

Thuộc tính cpu.max cpu.weight
Mục đích Giới hạn bandwidth Ưu tiên tương đối
Khi host rảnh Vẫn có thể throttle Có thể tận dụng CPU
Khi tranh chấp Vẫn chịu quota Phân phối theo weight

Phản biện: weight 300 có bảo đảm 75% CPU mọi lúc? Không; còn phụ thuộc hierarchy, cpuset, workload và các giới hạn khác.

MỤC 11 / 46

Memory controller: vì sao host còn RAM mà container OOM?

memory.max=536870912 giới hạn cgroup ở 512 MiB, bất kể host có thể còn 10 GiB RAM. Nếu reclaim không đủ, memcg OOM có thể xảy ra.

  • memory.current: mức memory được accounting, không đơn giản là tổng RSS.
  • memory.high: ngưỡng reclaim/throttling; vượt ngưỡng không trực tiếp kích hoạt OOM killer chỉ vì vượt high.
  • memory.max: giới hạn cứng của memory controller.
  • memory.low: bảo vệ reclaim theo best effort.
  • memory.min: bảo vệ mạnh hơn trong phạm vi hiệu lực.
cat /sys/fs/cgroup/<path>/memory.current
cat /sys/fs/cgroup/<path>/memory.events

memory.events và cách đọc OOM

low 0
high 124
max 10
oom 2
oom_kill 1
oom_group_kill 0

high đếm các sự kiện liên quan ngưỡng high; max phản ánh những lần usage chuẩn bị vượt max; oom là tình huống OOM được ghi nhận; oom_kill là số process bị kill được accounting. Các counter không đồng nghĩa nhau. memory.events có tính phân cấp; dùng memory.events.local nếu cần sự kiện riêng cgroup.

Systemd thường sở hữu và quản lý cgroup hierarchy trên Linux hiện đại. Không tùy tiện mkdir hoặc ghi trực tiếp trong subtree của systemd/runtime; dùng resource-control interface hoặc delegation thích hợp.

stat -fc %T /sys/fs/cgroup

Lab 1: CPU quota bằng transient service

sudo systemd-run --unit=linux-cpu-lab \
  -p CPUQuota=50% -p RuntimeMaxSec=15s \
  /usr/bin/python3 -c 'while True: pass'
systemctl show linux-cpu-lab -p ControlGroup -p CPUQuotaPerSecUSec
lab_cgroup=$(systemctl show linux-cpu-lab -p ControlGroup --value)
if [[ -n "$lab_cgroup" && -d "/sys/fs/cgroup$lab_cgroup" ]]; then
  sudo cat "/sys/fs/cgroup$lab_cgroup/cpu.max"
  sudo cat "/sys/fs/cgroup$lab_cgroup/cpu.stat"
fi
sudo systemctl stop linux-cpu-lab || true
sudo systemctl reset-failed linux-cpu-lab || true

Service chạy ngắn nên phải kiểm tra path không rỗng và cgroup còn tồn tại. Không đọc nhầm root cgroup rồi kết luận đó là service. Nếu unit đã tồn tại, chọn tên mới.

Lab cải tiến có sampling:

#!/usr/bin/env bash
set -euo pipefail
unit="linux-cpu-lab-$$"
sudo systemd-run --unit="$unit" -p CPUQuota=50% -p RuntimeMaxSec=20s \
  /usr/bin/python3 -c 'while True: pass'
sleep 1
cg=$(systemctl show "$unit" -p ControlGroup --value)
[[ -n "$cg" && -d "/sys/fs/cgroup$cg" ]] || exit 1
for i in {1..5}; do
  [[ -f "/sys/fs/cgroup$cg/cpu.stat" ]] || break
  echo "Sample $i"
  cat "/sys/fs/cgroup$cg/cpu.stat"
  sleep 2
done
sudo systemctl stop "$unit" || true
sudo systemctl reset-failed "$unit" || true

Lab 2: PID namespace không cần Docker

sudo unshare --mount --pid --fork --mount-proc \
  sh -c 'echo "PID trong namespace: $$"; ps -ef'

--pid chuẩn bị PID namespace cho child, --fork tạo child, --mount tạo mount namespace, --mount-proc mount procfs phù hợp. Nếu /proc vẫn là procfs của namespace ngoài, ps có thể cho góc nhìn không nhất quán.

readlink /proc/self/ns/pid
sudo unshare --pid --fork --mount --mount-proc \
  sh -c 'readlink /proc/self/ns/pid; ps -ef'
sudo lsns -t pid

Một số môi trường hạn chế unshare. Ghi lại giới hạn thay vì thay sysctl host một cách tùy tiện.

MỤC 16 / 46

Rootfs và OverlayFS

OverlayFS kết hợp lowerdir, upperdir, workdir và merged view. Khi sửa file chỉ có ở lower, có thể xảy ra copy-up. Khi xóa một entry từ lower trong merged view, OverlayFS có thể tạo whiteout để che entry đó.

LOWER: /etc/config=v1, /app/main
UPPER: /etc/config=v2, /tmp/data
MERGED: /etc/config=v2, /app/main, /tmp/data

Image layers không thay thế volume cho dữ liệu cần giữ. Xóa container có thể làm mất writable layer; volume cũng không tự động đồng nghĩa đã backup.

docker run -v app-data:/var/lib/app my-app
MỤC 17 / 46

Capabilities, seccomp và MAC

Namespace và cgroups không tạo security boundary đầy đủ. Cần đánh giá DAC, capabilities, seccomp, SELinux/AppArmor, thiết bị và mount exposure.

docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE my-app

CAP_SYS_ADMIN đặc biệt rộng; CAP_NET_ADMIN liên quan quản trị network; CAP_NET_RAW liên quan raw socket. Seccomp lọc syscall nhưng không phải hệ thống phân quyền file. SELinux/AppArmor là Mandatory Access Control. Tránh --privileged nếu không thật cần và hạn chế Docker socket bind mount.

Case study: MQTT chậm dù host CPU rảnh

Host 8 CPU, 16 GiB RAM. MQTT cgroup có CPUQuota=50% và MemoryMax=512 MiB. Host chỉ 15% CPU nhưng MQTT latency cao. Không thể loại trừ CPU bottleneck.

cat /sys/fs/cgroup/<path>/cpu.max
cat /sys/fs/cgroup/<path>/cpu.stat
cat /sys/fs/cgroup/<path>/memory.events
cat /sys/fs/cgroup/<path>/memory.pressure
cat /sys/fs/cgroup/<path>/io.stat

Đo counter theo thời gian; kiểm tra cả cgroup cha. Một parent CPUQuota=100% có thể giới hạn cả subtree dù child có CPUQuota=200%.

MỤC 23 / 46

Câu hỏi phản biện nâng cao

  • Một process trong container có thể mmap() 2 GiB dù memory.max=512MiB không? Có thể, vì virtual mapping không nhất thiết cấp physical pages ngay; charge diễn ra theo page faults và loại mapping.
  • CPUQuota=100% trên host 16 core có thể chạy trên 16 core không? Nhiều thread có thể chạy đồng thời trong một phần period, nhưng tổng ngân sách tương đương một CPU.
  • Image chứa kernel module có tự load được không? Không mặc nhiên; module tác động host kernel và cần quyền, compatibility, policy.
  • cpu.stat không có throttling có chứng minh không nghẽn CPU? Không; có thể do affinity, saturation, scheduling delay, cpuset hoặc host contention.
MỤC 24 / 46

Tổng kết phần nền tảng

Namespace kiểm soát góc nhìn. Cgroups kiểm soát tài nguyên. Security policy kiểm soát quyền. Rootfs cung cấp môi trường filesystem. Tất cả vẫn dựa trên host kernel.

Khi debug: kiểm tra namespace, cgroup, quyền, host resource pressure và vị trí lưu dữ liệu. Đừng coi container là một máy tính độc lập.

};

CLONE_INTO_CGROUP có thể tạo child trực tiếp trong cgroup được chỉ định trên kernel hỗ trợ và khi đáp ứng điều kiện. Runtime phải đồng bộ parent/child để UID/GID mapping, cgroup, mounts, network và security được cấu hình trước khi application chạy. unshare() tách một số trạng thái; setns() tham gia namespace tồn tại. CLONE_NEWPID áp dụng cho các child tạo tiếp theo nên thường cần fork.

Hai task có cùng namespace inode của một loại thường tham chiếu cùng namespace đó tại thời điểm quan sát. Namespace có thể sống tiếp sau process ban đầu nếu còn tham chiếu qua process, file descriptor hoặc namespace bind mount.

MỤC 30 / 46

Memory accounting: anon, file, slab, reclaim, OOM

Tổng RSS có thể đếm trùng shared pages; memory.current dùng accounting theo cgroup, gồm anonymous memory, page cache và một số kernel memory. memory.stat có anon, file, kernel, slab, sock, shmem, file_mapped, pgfault, pgmajfault, pgscan, pgsteal. Không cộng các field này tùy tiện vì có các phân loại con chồng lấp.

Clean file-backed pages thường reclaim dễ hơn; dirty pages có thể cần writeback; anonymous pages có thể cần swap hoặc cơ chế khác. Memory pressure kéo dài có thể tăng latency mà chưa OOM. memory.oom.group hỗ trợ xử lý workload như một nhóm theo quy tắc memcg OOM.

Lab trong VM:

import time
blocks=[]

    blocks.append(bytearray(8*1024*1024))
    print(len(blocks)*8,"MiB",flush=True)
    time.sleep(0.2)
'
cg=$(systemctl show memory-lab -p ControlGroup --value)
if [[ -n "$cg" && -d "/sys/fs/cgroup$cg" ]]; then
  cat "/sys/fs/cgroup$cg/memory.current"

cpuset, taskset, affinity và NUMA

cpu.max giới hạn CPU time; cpu.weight chia CPU khi tranh chấp; cpuset.cpus giới hạn CPU placement; sched_setaffinity() đặt affinity cho task.

Pinning sai có thể làm hiệu năng tệ hơn nếu CPU được chọn gánh IRQ, thermal throttling hoặc các workload khác. MỤC 32 / 46

I/O controller: io.stat, io.max, io.weight

CPU và RAM bình thường nhưng SQLite vẫn có thể chậm do I/O throttling, fsync latency, writeback hoặc storage saturation.

lsblk -o NAME,MAJ:MIN,SIZE,TYPE,MOUNTPOINTS

Ví dụ 8:0 rbytes=10485760 wbytes=5242880 rios=120 wios=80 biểu diễn I/O accounting theo block device major:minor. io.max có thể giới hạn rbps, wbps, riops, wiops theo thiết bị, ví dụ 8:0 rbps=10485760 wbps=5242880. io.weight là phân chia tương đối khi controller/scheduler hỗ trợ phù hợp.

[\text{WriteRate}=\frac{\Delta wbytes}{\Delta t}]

Throughput thấp không tự chứng minh throttling; cần kết hợp I/O PSI và thiết bị.

PSI: Pressure Stall Information

CPU usage đo thời gian CPU đã sử dụng; PSI giúp quan sát thời gian task bị stall vì áp lực CPU, memory, I/O.

cat /proc/pressure/cpu

Ví dụ some avg10=12.50 avg60=4.20 avg300=1.10 total=12345678: avg10/60/300 là pressure trung bình trên các cửa sổ tương ứng; total tính microsecond. some nghĩa là có ít nhất một task bị stall; full phản ánh tất cả non-idle tasks trong phạm vi phù hợp cùng stall. CPU full pressure cấp hệ thống có các đặc điểm riêng, không nên diễn giải như mọi metric thông thường.

OverlayFS nâng cao: copy-up, metadata và page cache

Copy-up có thể phát sinh chi phí khi sửa file lower. Metadata operations như chmod, chown, rename, unlink có thể tạo copy-up/whiteout. Workload nhiều file nhỏ hoặc database random writes/fsync cần đánh giá storage backend. Metacopy và các tùy chọn có thể làm hành vi khác nhau.

Lab (VM, filesystem hỗ trợ OverlayFS):

mkdir -p ~/overlay-lab/{lower,upper,work,merged}
echo 'version=1' > ~/overlay-lab/lower/config.txt
sudo mount -t overlay overlay \
  -o lowerdir="$HOME/overlay-lab/lower",upperdir="$HOME/overlay-lab/upper",workdir="$HOME/overlay-lab/work" \
  "$HOME/overlay-lab/merged"
cat ~/overlay-lab/merged/config.txt
echo 'version=2' | sudo tee ~/overlay-lab/merged/config.txt
cat ~/overlay-lab/lower/config.txt
cat ~/overlay-lab/upper/config.txt
cat ~/overlay-lab/merged/config.txt
sudo umount ~/overlay-lab/merged
rm -rf ~/overlay-lab

Kỳ vọng lower vẫn v1, upper và merged v2. Kiểm tra mount đã tháo trước khi cleanup; chú ý file do root tạo.

MỤC 36 / 46

Networking nâng cao: DNAT, SNAT, conntrack

Với docker run -p 8080:80 nginx, một đường đi điển hình là client → host network stack → netfilter DNAT → bridge/veth → container eth0 → nginx. Một số cấu hình dùng userland proxy, rootless networking hoặc đường đi khác.

  • Veth pair: hai đầu Ethernet ảo.
  • Bridge: kết nối L2, học MAC.
  • DNAT: thay đổi destination IP/port.
  • SNAT/masquerade: thay đổi source khi đi ra mạng.
  • Conntrack: theo dõi luồng; bảng đầy có thể làm kết nối mới lỗi/drop.
docker inspect <container> --format '{{.State.Pid}}'
sudo nsenter -t <PID> -n ip addr

MỤC 38 / 46

PID 1, SIGTERM, zombie và graceful shutdown

docker stop thường gửi stop signal (mặc định SIGTERM) đến container init, chờ rồi có thể SIGKILL. PID 1 có ngữ nghĩa signal và reaping đặc biệt. Shell-form CMD có thể khiến signal không đến application đúng như mong muốn.

import signal
import time
running = True

def handle_sigterm(signum, frame):
    global running
    print('Received SIGTERM', flush=True)
    running = False

signal.signal(signal.SIGTERM, handle_sigterm)
while running:
    time.sleep(0.1)
print('Cleanup resources')

Ứng dụng production cần đóng socket, flush, transaction cleanup, dừng worker, timeout. Init nhỏ hỗ trợ child reaping và signal forwarding:

docker run --init my-app

--init không thay thế graceful shutdown đúng cách.
