Mục tiêu và phương pháp học

Hiểu cách ghép các công cụ Unix bằng luồng byte, tách dữ liệu khỏi lỗi và kiểm tra kết quả thực thi. Mỗi chủ đề đi từ bài toán đời sống tới cơ chế Linux, ví dụ lệnh, phản biện và kinh nghiệm triển khai thực tế.

Điều kiện: kiến thức shell và thư mục/file của Bài 06–07. Các ví dụ ưu tiên Bash và GNU/Linux; hành vi một số lệnh có thể khác trên Unix khác.

MỤC 01

1. Tại sao Linux cần luồng dữ liệu?

Một chương trình C gọi printf() không cần biết terminal đang sử dụng HDMI, UART hay SSH. Nó ghi vào stdout; thư viện C và kernel đảm nhận đường đi dữ liệu.

c
#include <stdio.h>
int main(void) { printf("Hello Linux\n"); return 0; }
Chương trình → stdio (FILE *) → write() → Kernel → Terminal / File / Pipe
Tư duy Unix: tách logic xử lý khỏi nơi dữ liệu đến và đi. Giống nhà máy chỉ tạo sản phẩm, băng chuyền quyết định vận chuyển tới đâu.
MỤC 02

2. Nếu chương trình tự quyết định mọi thứ?

Nếu ứng dụng phải tự viết logic xuất terminal, ghi file và giao tiếp chương trình khác, code sẽ bị phụ thuộc vào môi trường. File descriptor tạo ra giao diện thống nhất cho I/O.

Câu hỏi: Khi đổi đầu ra từ terminal sang file, có nhất thiết sửa source code? Không: shell có thể thay đổi kết nối FD.
MỤC 03

3. File Descriptor là gì?

FD là số nguyên không âm trong bảng FD của tiến trình, tham chiếu một đối tượng I/O đang mở: file, terminal, pipe, socket hoặc thiết bị.

c
int fd = open("data.txt", O_RDONLY);

FD 3 không phải inode hay địa chỉ bộ nhớ. Nó là một chỉ số trong bảng FD của tiến trình.

MỤC 04

4. Mô hình bên trong Linux

Process FD table       Kernel open file descriptions
FD 0 ────────────────→ terminal input
FD 1 ────────────────→ terminal output
FD 2 ────────────────→ terminal error
FD 3 ────────────────→ data.txt (offset, flags)
                                  ↓
                                inode → data blocks

FD là handle của tiến trình; open file description chứa trạng thái mở và offset; inode mô tả file trong filesystem. Hai lần open() độc lập thường có offset riêng; dup() và fork() có thể tạo các FD cùng chia sẻ offset.

MỤC 05

5. Ba FD chuẩn: 0, 1, 2

FDTênÝ nghĩa
0stdinĐầu vào chuẩn
1stdoutKết quả thông thường
2stderrLỗi và chẩn đoán
              ┌─────────────┐
stdin (FD 0) → │   Process   │ → stdout (FD 1)
              └─────────────┘ → stderr (FD 2)

Hai luồng stdout và stderr độc lập dù mặc định có thể cùng hiện trên terminal. Tách lỗi khỏi dữ liệu giúp các công cụ nối được với nhau.

MỤC 06

6. Quan sát FD thực tế

bash
ls -l /proc/self/fd
sleep 300 &
pid=$!
ls -l "/proc/$pid/fd"
kill "$pid"

Đích có thể là /dev/pts/0, pipe hoặc file. /proc/self trỏ tới tiến trình truy cập nó, nên khi gọi qua ls cần lưu ý ngữ cảnh tiến trình.

MỤC 07

7. Redirect: lưu kết quả không sửa chương trình

bash
ls > files.txt

Shell đổi stdout sang file; bản thân ls không cần biết đích của FD 1.

MỤC 08

8. Ai thực hiện redirect?

Shell → fork/chuẩn bị tiến trình → open("files.txt") → dup2(fd, 1) → execve("ls") → write(1, ...)

Redirect do shell thiết lập trước khi lệnh chạy. Với shell builtin, cách triển khai có thể khác nhưng nguyên lý vẫn là shell thiết lập FD.

MỤC 09

9. Dấu >: ghi đè file

bash
echo "Hello" > output.txt
echo "Important data" > data.txt
false > data.txt
cat data.txt
c
open("output.txt", O_WRONLY | O_CREAT | O_TRUNC, 0666);

O_TRUNC làm file về kích thước 0 ngay khi mở thành công, trước khi chương trình tạo output. Quyền file mới còn chịu ảnh hưởng của umask/ACL.

Câu hỏi: Vì sao redirect sai làm mất dữ liệu dù chương trình chưa chạy? Vì shell đã mở file với O_TRUNC.

MỤC 13

13. Vì sao redirect stdout không tự redirect stderr?

bash

ls existing.txt missing.txt > result.txt 2> error.txt

> chỉ thay FD 1; 2> thay FD 2. Terminal có thể hiển thị cả hai nhưng chúng vẫn là hai luồng khác nhau.

MỤC 14

14. 2>&1 nghĩa là gì?

bash
cmd > out 2>&1

2>&1 nhân bản đích FD 1 hiện tại sang FD 2; không phải ghi vào file có tên “1”. Về cơ chế gần với dup2(1,2).

MỤC 15

15. Thứ tự redirect: >out 2>&1 khác 2>&1 >out

Thử thay đổi thứ tự

Redirection được xử lý từ trái sang phải. Nhân bản FD là sao chép tham chiếu tại thời điểm thao tác, không tạo liên kết động với số FD gốc.

MỤC 17

17. /dev/null là gì?

bash
find / -name "*.conf" 2>/dev/null

Ghi vào /dev/null sẽ bỏ dữ liệu; đọc từ đó trả EOF. Không nên che stderr vô tội vạ vì có thể mất thông tin debug quan trọng.

MỤC 18

18. Pipe: ghép chương trình nhỏ

bash
sort fruits.txt | uniq -c

sort sắp xếp, uniq -c đếm các dòng trùng liền kề. Vì uniq không gom những dòng giống nhau nằm rải rác, thường cần sort trước.

MỤC 19

19. Pipe hoạt động như thế nào?

┌───────────┐  FD 1   ┌─────────────────┐  FD 0   ┌───────────┐
│   sort    │ ──────→ │ Kernel pipe     │ ──────→ │  uniq -c  │
└───────────┘         │ byte buffer     │         └───────────┘
                      └─────────────────┘

Pipe là luồng byte; kernel không biết đâu là dòng, JSON record hay message. Các chương trình tự diễn giải byte.

MỤC 20

20. Pipe buffer và backpressure

Pipe có bộ đệm hữu hạn. Khi đầy, writer ở chế độ blocking phải đợi reader; khi rỗng mà còn đầu ghi mở, reader blocking phải chờ. Đó là backpressure, tương tự băng chuyền nhà máy đầy thì máy sản xuất phải chậm lại.

28. SIGPIPE và pipefail

bash
set -o pipefail
yes | head -n 1

head kết thúc sau một dòng, upstream có thể nhận SIGPIPE (signal 13); shell thường biểu diễn status kết thúc do signal là 128 + signal, tức 141. Đây có thể là kết thúc sớm có chủ đích, không nhất thiết là lỗi logic.

MỤC 29

29. tee: vừa xem vừa lưu

bash
command | tee result.txt
sort input.txt | uniq -c | tee counts.txt
command ──→ tee ──→ terminal
                └────→ result.txt

tee đọc stdin, ghi stdout và file. Tên gọi gợi hình chữ T chia nhánh dữ liệu.

MỤC 30

30. tee có lưu stderr không?

Mặc định command | tee log.txt chỉ đưa stdout vào tee. Stderr vẫn đi tới đích riêng, thường là terminal.

c
#include <stdio.h>
int main(void) {
  printf("Temperature: 30 C\n");
  fprintf(stderr, "ERROR: Sensor disconnected\n");
  return 1;
}
bash
gcc -Wall -Wextra sensor.c -o sensor
./sensor | tee sensor.log
cat sensor.log
./sensor 2>&1 | tee sensor.log
./sensor |& tee sensor.log
sensor stdout ──┐
                ├──→ pipe ──→ tee ──→ terminal + sensor.log
sensor stderr ──┘     (chỉ khi dùng 2>&1 hoặc |&)

Gộp hai luồng có thể làm hỏng định dạng dữ liệu như CSV. Nếu cần phân biệt, dùng ./sensor >data.csv 2>error.log.

bash
./sensor > >(tee data.log) 2> >(tee error.log >&2)
command | tee -a log.txt
set -o pipefail
false | tee output.txt
echo "$?"
Process substitution của Bash chạy các tiến trình tee phụ; status của lệnh chính không tự chứng minh mọi nhánh ghi log đã hoàn tất. Disk full cũng có thể làm tee thất bại.
MỤC 31

31. cp thực sự làm gì?

bash
cp firmware.bin backup.bin
stat firmware.bin
stat backup.bin
ls -li firmware.bin backup.bin
firmware.bin → inode A → data blocks A
backup.bin   → inode B → data blocks B

Hai bản sao thường có inode riêng. Trên filesystem hỗ trợ reflink, block vật lý có thể được chia sẻ copy-on-write. cp -a cố gắng giữ metadata, nhưng filesystem đích có thể không hỗ trợ toàn bộ.

MỤC 32

32. mv: rename hay copy?

bash
mv old.txt new.txt
mv /home/user/file.txt /mnt/usb/file.txt

Cùng filesystem: thường rename metadata nhanh, không cần chép toàn bộ byte. Khác filesystem: rename trả EXDEV, GNU mv thường phải copy rồi xóa; có rủi ro hết disk hoặc gián đoạn.

MỤC 33

33. Atomic rename và durability

Cách dễ lỗi: ghi trực tiếp file chính → có thể thấy file nửa chừng
Cách tốt hơn: ghi file tạm → kiểm tra → rename nguyên tử
bash
generate_config > /etc/myapp.conf.tmp &&
mv /etc/myapp.conf.tmp /etc/myapp.conf

Atomicity là tránh quan sát trạng thái đổi tên nửa chừng; durability là dữ liệu còn sau mất điện. Với yêu cầu nghiêm ngặt, cần fsync file tạm, rename rồi fsync thư mục, cùng kiểm tra lỗi và metadata.

34. rm thực sự xóa gì?

data.txt → directory entry → inode → data blocks
rm: unlink tên; FD đang mở vẫn có thể giữ inode tồn tại

Unlink bỏ liên kết tên. File có thể vẫn được đọc/ghi qua FD đã mở cho tới khi không còn hard link và tham chiếu mở.

MỤC 42

42. Tự redirect stdout bằng C

c
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
int main(void) {
    int fd = open("output.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd == -1) { perror("open"); return EXIT_FAILURE; }
    if (dup2(fd, STDOUT_FILENO) == -1) {
        perror("dup2"); close(fd); return EXIT_FAILURE;
    }
    close(fd);
    printf("Hello from C\n");
    if (fflush(stdout) == EOF) { perror("fflush"); return EXIT_FAILURE; }
    return EXIT_SUCCESS;
}
bash
gcc -Wall -Wextra redirect.c -o redirect
./redirect
cat output.txt

dup2 đặt FD 1 trỏ tới cùng open file description với fd; đóng fd gốc không làm mất FD 1.

MỤC 43

43. dup và dup2 khác nhau

c
dup(oldfd);
dup2(oldfd, newfd);

dup() chọn FD mới khả dụng nhỏ nhất. dup2() dùng đúng số FD đích và thay thế nguyên tử, tránh race giữa close(newfd) và dup(oldfd).

MỤC 44

44. Shell xây pipeline bằng system call

c
pipe();
fork();
dup2();
close();
execve();
waitpid();
Parent shell
  ├─ pipe() tạo read_fd / write_fd
  ├─ Child A: dup2(write_fd, 1) → exec(ls)
  └─ Child B: dup2(read_fd, 0)  → exec(grep)

Phải đóng các đầu pipe không dùng. Nếu còn writer FD mở, reader có thể không nhận EOF và bị chờ mãi.

MỤC 45

45. Buffering: log xuất hiện chậm

c
printf("Working...");
sleep(5);
fflush(stdout);

stdout nối terminal thường line-buffered, nối file/pipe thường full-buffered. Chuỗi không newline có thể nằm trong buffer. fflush() đẩy buffer user space, không tương đương fsync() để đồng bộ xuống lưu trữ.

MỤC 46

46. Gộp stdout/stderr có giữ thứ tự?

c
printf("A\n");
fprintf(stderr, "B\n");
bash
./program > combined.log 2>&1

Không đảm bảo A luôn trước B: stdout có thể buffered còn stderr ghi ngay. Với nhiều tiến trình, scheduling và các write() còn làm thứ tự khó dự đoán. Dùng timestamp, sequence number hoặc logging đồng bộ.

MỤC 47

Pipe và TCP stream đều không bảo toàn ranh giới từng lần write/send; ứng dụng phải tự framing.

MỤC 48

48. Pipe khác message queue

Pipe truyền byte liên tục. Message queue giữ ranh giới message theo API. UART/TCP thường cần delimiter, fixed-length frame hoặc length prefix; CAN đã có ranh giới frame trong giao thức.

MỤC 49

49. Production: backup báo thành công giả

bash
backup_command | gzip > backup.gz
echo "Backup successful"  # Có thể sai!

set -o pipefail
if backup_command | gzip > backup.gz; then
  echo "Backup successful"
else
  echo "Backup failed" >&2
  exit 1
fi

Backup production cần kiểm tra tính toàn vẹn, khả năng restore và không publish file chưa hoàn chỉnh.

MỤC 50

50. Production: log làm đầy filesystem

bash
./application >> application.log 2>&1
application.log → application.log.1 → application.log.2.gz

Cần logrotate, retention, giám sát disk và cơ chế reopen log. Rename log không làm FD cũ tự chuyển sang inode mới.

MỤC 51

51. sudo echo vẫn Permission denied

bash
sudo echo "value" > /root/config.txt  # redirect do shell thường thực hiện
printf "%s\n" "value" | sudo tee /root/config.txt >/dev/null

sudo nâng quyền cho chương trình được gọi, không thay đổi UID của shell cha đang thực hiện redirect.

MỤC 52

52. Command substitution có giữ mọi byte?

bash
value=$(printf "hello\n\n")
printf "<%s>\n" "$value"

Bash bỏ newline cuối trong command substitution; biến Bash không thể chứa byte NUL. Không dùng shell variable để giữ nguyên mọi dữ liệu nhị phân.

MỤC 53

53. Bài tập 1: dự đoán output

bash
echo "A" > file.txt
echo "B" >> file.txt
echo "C" > file.txt
cat file.txt
Đáp án: C, vì redirect cuối dùng > truncate nội dung trước đó.
MỤC 54

54. Bài tập 2: dự đoán stderr

bash
ls missing.txt 2>&1 > out.txt
Đáp án: stderr tới stdout cũ (thường terminal), stdout mới vào out.txt.
MỤC 55

55. Bài tập 3: pipeline status

bash
false | true | true
echo "$?"  # 0 mặc định
set -o pipefail
false | true | true
echo "$?"  # 1

Lệnh cuối thành công không có nghĩa upstream thành công.

MỤC 56

56. Bài tập 4: file đã xóa nhưng disk không giảm

bash
df -h
du -sh /var/log
sudo lsof +L1

Kiểm tra deleted-open files, đồng thời cân nhắc snapshot, reserved blocks, mount point và metadata filesystem.

MỤC 57

57. Bài tập 5: phân tích log

bash
grep "^ERROR " app.log | sort | uniq -c | sort -nr
2 ERROR sensor timeout
1 ERROR crc mismatch

Nếu timestamp thay đổi trên từng dòng, cần trích trường lỗi trước khi thống kê; đây là cầu nối sang grep/sed/awk/regex ở Bài 09.

MỤC 59

59. Năm câu hỏi của một senior

  1. Ai thực hiện thao tác: shell hay chương trình?
  2. FD nào đang được sử dụng?
  3. Dữ liệu đi tới đâu: terminal, file, pipe, socket?
  4. Thành công được xác nhận bằng status, checksum hay kiểm thử?
  5. Nếu lỗi hoặc mất điện giữa chừng, dữ liệu ở trạng thái nào?
MỤC 60

60. Liên hệ Bài 09

Program A → stdout → pipe → stdin → Program B

Bài 08 trả lời dữ liệu đi như thế nào. Bài 09 trả lời biến đổi và phân tích dữ liệu như thế nào: grep, sed, awk, sort, uniq, regex, parser và pipeline log lớn không cần tải toàn bộ vào RAM.

Kết luận: nắm mô hình FD, byte stream, status và filesystem sẽ giúp học shell scripting, IPC, networking và debugging production hiệu quả hơn.
